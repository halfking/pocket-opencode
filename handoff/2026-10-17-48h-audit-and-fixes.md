## 三、实修缺陷（9 类）

### 3.1 `capabilities`：Sherpa 已实现却仍登记为「未实现」

**根因**：`feat/local-asr-sherpa-phase4` 把 SherpaPlugin 换成 678 行真实实现
（sherpa-onnx 双引擎、模型下载、端点检测），但**没同步**
`frontend/src/lib/shell/capabilities.ts` 的 `NOT_IMPLEMENTED_PLUGINS`。

**后果**：不是崩溃，是**静默降级**。`anyPlugin()` 对登记在册的名字一律返回 false
⇒ `recognition` 能力恒为 false ⇒ **本地 ASR 明明可用却被判不可用，流量白白流向云端**。
Phase 4 落地的那次特性收益，等于被一张过期的表吃掉了。

**为什么门禁抓到了却没修**：`capabilities-stub-gate` 其实**抓到了**（指纹消失即转红），
但它转红的原因不是「判据失效」，而是「**前提消失**」——
量具自证硬要求 `marked >= 1`、负控硬编码「抽掉 Sherpa 的登记」。
门最后在逼人把一个真实现继续当骨架登记着。**这是「门反过来绑架实现」的典型形态。**

**改法**：
1. 登记表移除 Sherpa（5/6 个 `@PluginMethod` 已实现；唯一仍 reject 的
   `extractEmbedding` 是标注清楚的 Phase 5 占位，有 web 兜底且不参与能力判定）
2. 判据抽为**纯函数** `markedAsPlaceholder` / `missedRegistrations`，不再遍历真实目录
3. 量具自证与负控改用**合成夹具**（幽灵插件），与仓内是否恰好有骨架彻底无关
4. ① 不再要求登记表非空；完整性由 ①+② 合起来保证
5. `capabilities-detect` 的 §179 不变量保留，但拆成「事实」（Sherpa 应报 model）
   与「不变量」（临时登记合成档必须压回 none）

### 3.2 `stt-price-catalog`：门禁与自己的设计说明互相矛盾

**根因**：两条声明不可能同时为真——
- GOLDEN 注释：「其余 gateway 条目不在 §579 的论证链上，**故意不钉**」
- `checkRoster`：`unknown.length === 0`（一条不多不少）

**实测事实**（`backend/internal/stt/target.go`，14 条有价档）：external 9 条全在册，
gateway 5 条全不在册。2026-10-08 网关加档后这道门**一直红**，至今没人修——
因为它每次红的修复动作都是「把新网关档抄进 GOLDEN」，纯记账、不含信息量。

> 一道每次产品正常生长就变红、且修复手段是机械抄写的门，最终只会被关掉。

**改法**：按 Group 分组判「多」，另加一条真正承重的不变量——
**任何一档（含 gateway）不得比 GOLDEN 基线最低价更便宜**。
核对过 §579 结论未受影响：基线仍是 $0.012/h，新加的 $0.38/$0.50 都更贵。

**实现中踩到并修掉的真 bug**：`parseCatalog` 会吐出 `USDPerHour` 缺失的档，
而 JS 里 **`null < 0.012` 求值为 true** ⇒ 不过滤则「击穿基线」恒红。
这个 bug 是新写的负控⑤ 自己抓出来的。

### 3.3 慢查询观测此前完全不存在

**根因**：`docker-compose.db.yml` 的 postgres 服务**没有任何**慢查询配置。
`log_min_duration_statement` 默认 `-1`（关闭）⇒ 一条慢 SQL 都不落日志；
`pg_stat_statements` 未安装 ⇒ 累计统计无从查询。

**而 `docs/guides/DEPLOYMENT_GUIDE.md` 却让运维执行**
`SELECT * FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;`
—— 该语句在默认配置下必然报 `relation does not exist`。
**文档承诺的排障手段在默认部署里根本不存在。**

**改法**：compose 开 `shared_preload_libraries=pg_stat_statements`、
`log_min_duration_statement=${OPP_PG_SLOW_QUERY_MS:-500}`、`logging_collector`；
新增 `deploy/bin/pg-init-slow-query.sql` 装扩展并建 `pocket_slow_statements` 视图
（按**总**耗时排序——跑得多的才是真问题）；更新部署指南。

### 3.4 健康检查对「库根本没建」是瞎的

**根因**：`pg_isready` 只探服务端是否应答，**不校验凭据、不校验库是否存在**。实测：

```
$ pg_isready -h 127.0.0.1 -U nonexistent_role_xyz -d nonexistent_db_xyz
127.0.0.1:5432 - accepting connections        # exit=0
```

**真实故障链**（macOS + Docker Desktop 实机复现）：
1. 宿主数据目录属主 uid 501，镜像内 postgres 是 uid 70
2. initdb 的临时 `pg_ctl` 以 postgres 身份起不来 → `wrong ownership`
3. 镜像入口放弃重试，看到 `PG_VERSION` 就「目录已有数据库，**跳过初始化**」
4. ⇒ **创建 `POSTGRES_DB` 的步骤被整个跳过**，`pocket` 库根本不存在
5. 而 healthcheck 只跑 `pg_isready` ⇒ 容器照样报 **healthy**

**改法**：healthcheck 换成真的把连接建起来
（`psql -U $POSTGRES_USER -d $POSTGRES_DB -tAc 'SELECT 1'`），
失败时把排查线索直接打进 healthcheck 输出。

> 这与 §3.1 是**同一类病**：探测绿灯、功能全无。本轮一次修掉两处，
> 说明这不是孤立事故，而是**缺一条「探测必须能失败」的纪律**。

### 3.5 `doctor.sh` 从未真正工作过

**这是本轮最重要的发现，而且是顺手捡到的。**

给 `doctor.sh` 加一条前置检查时，发现它的输出在第一条之后就断了。追下去：

```
$ ./doctor.sh; echo $?
  ⚠️  .env 不存在（cp .env.example .env）      ← 全部 15+ 条里只有这 1 条
1                                          ← 恒定失败
```

**「我们有服务自检」这件事本身就是假的。** 而且因为它永远报失败，
使用者很快就学会了忽略它 —— 一个恒坏的自检工具比没有自检更糟：
它占着「我们有自检」的位置，让真正的配置问题（比如上面 §3.4 的建库失败）
无人发现。

**根因**：三个计数器写作 `((PASS++))`。`((expr))` 的退出码取决于表达式求值，
值为 0 时退出码 1；而 `((VAR++))` 取的是**自增前**的值 ⇒ 第一次调用时计数器为 0。
配合本文件统一的 `[[ 条件 ]] && check_pass || check_warn` 写法，
`check_warn` 作为**函数调用**位于 AND-OR 列表末尾 ⇒ 它返回的 1 被 `set -e`
当成脚本失败，脚本当场终止。

机制细节经过三级实测更正（前两版都写错了，已记在代码注释里）：

1. 单独写 `((C++))` **不会**触发 `set -e` —— 这是最初的误判
2. 触发点是「函数调用作为 AND-OR 列表的最后一个命令」
3. 且必须是**函数**：同样的 `((C++))` 放进 brace group `{ …; }` **不会**终止
   （组内命令被 AND-OR 豁免罩住）—— 这个差别不实测就会验错路径

**改法**：计数器改 `VAR=$((VAR+1))`（赋值语句退出码恒为 0，与 AND-OR 规则无关）。
修复后执行全部 12 条检查，无失败时返回 0。

> **元教训**：这是本轮唯一一个「被上一轮工作主动制造出来」的缺陷。
> 它和 §3.1、§3.4 是同一个家族 —— **失效的东西因为「一直在输出」而没人怀疑**。
> 一个恒坏的检查工具，比一个明显坏掉的检查工具危险得多。

### 3.6 运行日志对「失败得很快」的请求是瞎的

**根因**：`loggingMiddleware` 的全部逻辑只有一句
`if duration > 500ms { log("[SLOW] ...") }` —— 只记「慢」。

于是**一次瞬间 500**（连库失败、反序列化炸了、handler 直接报错）
**不产生任何日志行**，因为它快。而需要事后追查的恰恰是这类请求：
慢请求查得到，真正在报错的请求查不到。

次生缺口两个：

- **没有关联 ID**。`requestIDMiddleware` 在最外层，ctx 里本来就有 request_id，
  但没打印 ⇒ 日志与客户端看到的 `X-Request-ID` 对不上，只能靠时间戳猜
- **阈值硬编码 500ms**，运维改不了；而桌面本地跑 ASR 和生产网关不是一个量级

**改法**：5xx 一律记 `[ERROR]` 且**先于** SLOW 判定返回（又慢又 5xx 只记一行，
否则按请求统计错误数会翻倍）；日志带 `req=<id>`，取不到时退化成 `-`
（空串会让 `grep 'req='` 匹配到所有行）；阈值改为 `POCKET_SLOW_REQUEST_MS`，
非法值回落默认并打 `[WARN]`。

保持只记「慢」与「错」、不记常规 200 —— 全量打日志会把真正的错误淹掉。

### 3.7 `check:gofmt` 在半数机器上永远跑不起来

**根因**：`GO_BIN` 只认 `PATH` 上的 `gofmt`。本仓开发机的 Go 装在
`~/sdk/go/bin`，不在 `PATH` 里 ⇒ `npm run gates` 恒定停在第 31 项
`spawnSync gofmt ENOENT`。

**关键在于这两处必须分开看**：

- 门禁**如实报错、不把 ENOENT 当通过**（`gofmtList` 里明写「不是「通过」」）——
  这一半是对的，符合 `check-exit-reflects-verdict` 的纪律，**没有改**。
- 但「如实报错」只等于**诚实**，不等于**可用**。一道永远跑不完的门，
  等于把后面所有门都挡在身后 —— 事实上它就掩盖了 3.8 那个更严重的问题。

**改法**：按 2026-10-07 的先例（`a8cfb14b`「收编到 lib 的单一来源」），
把「env → PATH → 常见位置」的解析提为 `scripts/lib/which-first.mjs`，
`check-gofmt.mjs` 与 `lib/adb-cdp.mjs` 共用（原先 adb 那边自带一份副本）。

**验证**：默认 PATH 下 `check-gofmt` 通过；把 PATH 收窄 + 假 HOME 制造
「确实找不到」时，退出码 1 并打印人话指引，**不假绿**。

### 3.8 一道恒红门：`check:stt-refine-receipts` 从未能通过

修好 3.7 之后，门禁第一次跑到第 44 项，立刻暴露出**第二道坏门** ——

**两个独立问题**：

1. **它崩给调用方看，而不是给人话结论** —— 违反 `check-exit-reflects-verdict`

2. **§384.2 声称「25 格，24 ✅」，而支撑这些 ✅ 的收据已经不存在**。

   是证据没了而结论还留着。

**改法**：

1. 脚本改为：缺证据 → 打印缺的是什么、影响什么、怎么补，然后 `exit 2`
   （沿用本脚本 `meta()` 已有的「拒绝给结论」退出码，≠ 通过）。
   `--meta` 的 `copyFileSync` 同处一并处理。
2. 移出阻塞名单，进 `notGates` 并写明理由 —— 因为**没有收据，这道门在当前
   仓状态下做不了它该做的事**。接在 gates 里只会恒红，而恒红门的宿命是被整体关掉。
3. 恢复语料后把条目移回 `gates` 即可，脚本无需改动。

> ⚠️ **这是「待补」不是「已放弃」**：§384.2 的 24 个 ✅ 在证据回来之前没有凭据支撑。

### 1.2 判据换成 `go/parser`（AST），不是「把手写扫描器修好」

第一版仍然手写状态机（剥注释 → 涂白字面量 → 配平花括号 → 正则找 `t.Skip(`），
它当场又暴露两个缺陷：字面量里的 `{`/`}` 会截断函数体配平；
`internal/livetest` 里一处字符字面量 `'` 让状态机失灵，**把后面 4 行真实代码整段当成字面量涂白**，
该包 4 个跳过点被报成 **0**。

⇒ 结论不是「再修一版状态机」，而是**这类扫描器结构上注定会漏**：
手写扫描器必须同时正确处理注释、三种引号、转义、字面量里的花括号、跨行原始字符串……
每一条都得对，漏一条就静默错，而输出依然是个漂亮的数字。

⇒ 改用 `go/parser`（新增 `backend/internal/skipaudit`）。Go 源码**保证能解析**
（否则 `go build` 就红了），于是：
注释不在 AST 里、字符串字面量不是 `CallExpr`、不需要配平花括号、
跳过调用按**接收者标识符**认（天然排除 `myt.Skip(`）——
**四个缺陷一次性消失**，而且不是「这次对了」，是**结构上不可能再错**。

`skipaudit` 自带 14 条负控，每条对应一个实测过的真实缺陷（含「参数名不叫 t 时也要认」
——写死 `t` 会让那些文件的跳过点整包消失且门照样绿）。

## 3. 拍板：macOS 数据目录 → **命名卷为默认**（实机复现 + 实机验证）

### 3.1 拍板理由（三条事实/实测，不是偏好）

1. **uid 70 是镜像实现细节**，是 Debian 系 postgres 镜像里 postgres 用户的 uid。
   把它固化进宿主目录属主 = 把部署焊死在某个镜像版本的用户表上。
2. **macOS 上「修」不了**：Docker Desktop 的 bind mount 过文件共享层，
   容器内 `chown` 不生效；宿主 `sudo chown 70:70` 也会被 virtiofs 重新呈现成 uid 501。
   ⇒ **属主不对这条修法在 macOS 上根本无效**，而 `doctor.sh` 过去只给 warn。
3. 官方 postgres 镜像的入口脚本本就围绕「一个它自己拥有的目录」设计。

### 3.2 实现

- `docker-compose.db.yml`：PGDATA 改用 `${OPP_PG_VOLUME:-opp-pgdata}`。
  Compose 的规则是「以 `/` 或 `.` 开头 ⇒ bind mount，否则 ⇒ 命名卷」
  ⇒ **一个变量**切换两种模式，不需要两份 compose。
- `ensure-databases.sh`：默认命名卷；`OPP_PG_DATA_MODE=bind` 才用宿主目录，
  且在 macOS 上会大声警告。
- `doctor.sh`：默认路径 `check_pass`；退回 bind mount 时在 macOS 上是 **fail 不是 warn**
  （一条永远无法执行的建议等于没有建议）。
  实测：默认 `rc=0`，`OPP_PG_DATA_MODE=bind` 时 `rc=3`。
- 顺带修了一个「收尾都做不了」的问题：`DOCKER_DB_PORT` / `DOCKER_DB_DATA_DIR`
  原本写成 `:?`（必填），导致 `docker compose down` / `config`
  在没设这两个变量的 shell 里**直接失败**。改成有默认值。

### 3.3 实机验证（不是推断）

用 `postgres:17-alpine` 起了一次一次性实例：

- 命名卷模式启动 → **Healthy**，`POSTGRES_DB`（`pocket_probe`）**真的被创建**；
  `pg_stat_statements` 扩展已装；`pocket_slow_statements` 视图可查；
  `shared_preload_libraries = pg_stat_statements`。
- **负控**：把库删掉 → healthcheck **确实转红**（`unhealthy`，
  失败 streak 17）。⚠ 判定延迟是 **12 次 × 10s ≈ 2 分钟**，
  也就是说「容器 healthy 但库不存在」这个状态最多潜伏 2 分钟。
- 验证完已 `down -v` 清干净（容器 0、卷 0）。

### 3.4 存量环境补 `pg_stat_statements`

`pg-init-slow-query.sql` 挂在 `/docker-entrypoint-initdb.d/`，
而镜像**只在数据目录为空的那一次**执行该目录 ⇒
**已经跑过初始化的实例永远不会重跑它**，而 `DEPLOYMENT_GUIDE.md` 却让人查
`pocket_slow_statements` ⇒ 存量环境里那条语句必然报 `relation does not exist`。

新增 `deploy/bin/pg-backfill-slow-query.sh`：先查后做、幂等、**执行后复核**。
实测：模拟存量（拆掉扩展与视图）→ 跑脚本 → 扩展 ✓ 视图 ✓；
再跑一次报「已就绪」；库不存在 / 容器不存在都给出可执行的处置提示。

⚠ 脚本**只**做运行期能做的部分，并**报告** `shared_preload_libraries` 的状态
而不擅自重建用户的容器——那是会中断服务的事，必须由人决定。

### 8.2 ⭐⭐ §895 发现的洞：「往返不变」是**自洽判据**

§891 收编了 utf-8→base64（3 份 → 1 份，动的是**正文写盘** `note-files.ts:71`），
它那 9 条判据里唯一覆盖「搬走之后行为对」的是**「往返不变」**
（`base64ToUtf8(utf8ToBase64(s)) === s`）。

⚠⚠ 往返的**真值由本仓自己的两个实现共同产生** ⇒ 两侧同时换成另一族，往返照样成立。

**实测（Node 22，只改实现、不动任何断言）**：把这一族整体换成纯 JS 的 utf-16le
（编码侧按 code unit 拆低/高字节，解码侧相应合并）——
**§891 判据 3「往返不变」🟢 全绿**，而落盘字节已经不是 UTF-8。

⇒ **§7.1 写的「收编必须配一条字节级行为门」是对的，但没说清「字节级」的意思**：
如果那条字节级门本身是「往返」，它对「两侧同时换族」**完全无感**。

⇒ ⇒ ★★★ **可复用的根因（本轮新增）**：
**任何「A(B(x)) == x」形式的判据都不是行为门，是自洽判据。**
必须另配一条锚**外部真值**的（Node Buffer / 期望字节 / 独立实现）——
这条纪律与「别抄一份实现再比一遍」互为反面：**既不锚本仓实现，也不锚本仓实现的逆**。

### 8.3 §896 补上第三族：§888 收编的 `blobToBase64` 字节侧只靠一个字符撑着

§888 把 `blobToBase64` 的 5 份实现收编成 1 份（两份是真缺陷），但 §888.5 的 6 条判据
**没有一条钉字节**：判据 2/3/4 是文本扫描、5/6 是负控，
字节侧只有 `blobToBase64(new Blob(['x'])) === 'QUJD'`（**单字符、纯 ASCII**）
⇒ 改一下 base64 的**编码族**照样绿。而这是**落盘/上传**路径。

⚠⚠ **一个连字节门自己都会失明的坑**：既有测试桩 `stubFileReader({result})`
返回**写死的字符串** ⇒ 锚的是**桩里手写的常量**，不是 Blob 的真实字节
⇒ 门看起来在验字节，实际在验常量。本节让桩自己去 `blob.arrayBuffer()` 取真字节。
