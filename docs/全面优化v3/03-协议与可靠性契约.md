# 协议与可靠性契约

**版本**：v3.0（已批准设计）  
**日期**：2026-08-27  
**状态**：设计基线，按 `CURRENT` / `PLANNED` 管理实施差异  
**适用范围**：ACC、OpenPocket facade client、AgentCompanion/host、Codex/Claude/OpenCode coding agent、Memora、navop Public MCP，以及未来的跨自治 Agent 联邦

> 本文是 v3 的协议与可靠性契约。它修正早期文档中“ACC↔AgentCompanion 使用自定义 A2A”“ACP 自定义 capability.invoke”“用 JSON-RPC 2.0 作为稳定性方案”等表述。协议名称不等于可靠性语义：JSON-RPC 只规定消息的调用/响应格式，不提供持久化、重放、幂等、租约、fencing、顺序、交付或最终一致性保证。

## 1. 结论与不可妥协的边界

### 1.1 四条强制决策

1. **ACP（agent-client-protocol）只使用标准协议**。第一版仅用于 AgentCompanion/host 与本机 Codex、Claude Code、OpenCode 等 coding agent 之间的 `initialize`、session 生命周期、`prompt`、`cancel`、`update`、`permission` 交互。不得再定义第二个“ACP”、`capability.invoke`、`capability.stream` 或同名自定义方言。
2. **A2A 只用于跨自治 Agent 或外部联邦**。ACC 与本机 AgentCompanion 第一版不走 A2A，而走本文件定义的 Runtime Control API。未来为了接入外部自治 Agent，才提供 A2A adapter，暴露标准 Agent Card、`message/send`、`tasks/get`、`tasks/cancel`、SSE 等能力。
3. **MCP 只用于发现和工具/资源调用**。AgentCompanion/host 或 ACC 到 navop、IDE bridge、其他工具使用 MCP 的 `initialize`、tools/resources discovery 和 tools call。MCP 的可见工具、token 或 permission mode 都不是平台授权结论；授权由 ACC 的身份、租户、策略和审批门独立决定。
4. **REST/OpenAPI + SSE 是平台 canonical command/durable event**。命令以 REST/OpenAPI 定义，状态和事件持久化后以 SSE 投影；WebSocket 只用于反向控制、交互式终端、WebRTC/信令和 best-effort 实时提示，不承诺 durable delivery、exactly-once 或可重放。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| **ACC** | Agent Control Center，平台任务、编排、审批、审计和 durable event 的权威服务。 |
| **AgentCompanion/host** | 运行在开发机/服务器上的本机宿主或守护进程。它发现、启动和控制本机 coding agent，向 ACC 连接 Runtime Control API。本文不假定 workspace 中已经存在一个名为 AgentCompanion 的仓库。 |
| **coding agent** | Codex、Claude Code、OpenCode 等实际执行 prompt 的本机 Agent。 |
| **Runtime Control API** | ACC ↔ AgentCompanion 的第一版平台控制面；它是 HTTP REST 命令和 SSE durable event，不是 A2A，也不是自定义 ACP。 |
| **MCP server/tool** | navop、IDE bridge 或其他工具提供的能力发现/调用端。MCP permission 只描述工具自身的操作门控。 |
| **command** | 一次具有 `command_id`、幂等键、deadline 和目标的持久化意图。 |
| **event** | 命令状态、进度、审批、租约或执行结果的持久化事实；具有单调递增的序号。 |
| **artifact** | 大型或可下载输出的不可变引用，不把完整输出塞进命令响应或事件。 |
| **unknown outcome** | 客户端无法判断命令是否已被执行的明确状态；不能擅自等同于失败，也不能自动重放所有副作用命令。 |

### 1.3 协议选型的最终关系

```text
用户/客户端
    │ REST/OpenAPI command + SSE durable events
    ▼
ACC（任务、策略、审批、事件 SSOT）
    │ Runtime Control API（第一版；REST + SSE）
    ▼
AgentCompanion/host
    │ 标准 ACP（仅 coding agent 生命周期和交互）
    ▼
Codex / Claude Code / OpenCode

AgentCompanion/host ── MCP discovery/tools/resources ──► navop / IDE bridge / tools
ACC ── MCP discovery/tools/resources（受策略控制）──────► navop / tools

ACC ── A2A adapter（未来，仅外部/自治 Agent）──────────► 外部 Agent / 联邦
```

平台协议之间不得“套娃”：Runtime Control 的 `dispatch` 不是 ACP 的自定义方法；MCP `tools/call` 不是平台 `complete`；未来 A2A `message/send` 不是本机 Agent 的代替品。

## 3. 协议边界矩阵

| 连接/参与者 | 协议 | 允许的用途 | 可靠性/授权责任 | 明确禁止 |
|---|---|---|---|---|
| OpenPocket、Web、CLI ↔ ACC/facade | REST/OpenAPI + SSE | 创建任务、查状态、审批、订阅 durable event | ACC 持久化命令和事件；Bearer/HMAC、租户和 RBAC | 以 WS 消息作为任务 SSOT；把 HTTP 200 当成执行完成 |
| ACC ↔ AgentCompanion/host | Runtime Control API（REST + SSE） | register、lease、capabilities、dispatch、ack、progress、complete、cancel、resume | ACC 命令/事件 store、幂等、lease、fencing、reconcile | A2A；自定义 ACP；仅靠连接存活推断执行结果 |
| AgentCompanion/host ↔ Codex/Claude/OpenCode | **标准 ACP** | `initialize`、session、`prompt`、`cancel`、`update`、`permission` | ACP 标准生命周期；平台侧另以 Runtime Control 记录命令和结果 | `capability.invoke`、`capability.stream` 等第二 ACP；把 ACP request id 当 durable event id |
| AgentCompanion/host ↔ navop Public MCP | MCP（当前 raw TCP loopback） | initialize、tools/list、tools/call，以及协议支持的 resources discovery/read | navop MCP token + 本机 permission mode；平台授权必须先行 | 使用 MCP 当 ACC 授权系统；让 navop 直连 ACC canonical command store |
| ACC/host ↔ IDE bridge/tools | MCP（或工具原生 HTTP，按适配器契约） | discovery、tools、resources | 工具端输入约束；ACC policy/approval 决策 | 借 MCP tool schema 推导用户身份和租户权限 |
| ACC ↔ Memora | Memora HTTP v2 / ACC facade | memory/knowledge/QA 查询与写入 | Memora JWT、tenant/project scope、ACL；ACC 作为路由和审计边 | 将 Memora 当执行 Agent；将 MCP session 当 Memora session |
| ACC ↔ 外部自治 Agent/联邦 | A2A adapter（未来） | Agent Card、`message/send`、`tasks/get`、`tasks/cancel`、SSE | 联邦身份、对端 task 状态和 adapter 映射；跨边界审计 | 第一版本机链路使用 A2A；自定义 `task.delegate` 作为 A2A 方言 |

## 4. Runtime Control API（第一版）

### 4.1 传输与版本

- 基础地址由 ACC 发布，第一版使用 HTTPS；路径为 **PLANNED `/api/v2/runtime/*`**，OpenAPI 是唯一可生成客户端和测试的契约。
- Runtime Control 不使用 JSON-RPC 方法名作为 wire API。REST operation id 可使用 `runtimeRegister` 等稳定名称，但 HTTP body 不出现 `jsonrpc`、`method`、`result` 作为可靠性字段。
- AgentCompanion 可使用一条 SSE 连接接收 server-to-host 的 command projection，也可由 host 主动 POST ack/progress/complete；不得把 TCP/WS 连接视为租约。
- 每个请求使用 HTTPS 认证；身份、`tenant_id`、主体和权限从验证后的 token/mTLS 证书得到。body 中的 `tenant_id` 仅用于一致性校验，不得覆盖可信身份。
- 当前 ACC 的 `/api/v2/orchestration/*` 是可复用的 CURRENT 编排基础；下述 `/api/v2/runtime/*` 为统一 host 控制面的 **PLANNED** 兼容层/新入口。

### 4.2 方法总览

| 方法 | HTTP endpoint（PLANNED） | 调用方向 | 是否改变状态 |
|---|---|---|---|
| `register` | `POST /api/v2/runtime/register` | host → ACC | 是，注册 runtime/实例/连接 |
| `lease` | `POST /api/v2/runtime/lease` | host → ACC 或 ACC 内部 | 是，获取/续期/释放执行租约 |
| `capabilities` | `GET /api/v2/runtime/capabilities` | ACC/host → ACC | 否；返回已声明和策略过滤后的能力 |
| `dispatch` | `POST /api/v2/runtime/dispatch` | ACC → host（REST command） | 是，创建 durable command |
| `ack` | `POST /api/v2/runtime/commands/{command_id}/ack` | host → ACC | 是，确认接收/拒绝 |
| `progress` | `POST /api/v2/runtime/commands/{command_id}/progress` | host → ACC | 是，追加 durable progress event |
| `complete` | `POST /api/v2/runtime/commands/{command_id}/complete` | host → ACC | 是，终结命令并写结果 |
| `cancel` | `POST /api/v2/runtime/commands/{command_id}/cancel` | 用户/ACC → ACC，再投影给 host | 是，发出取消请求或终结取消 |
| `resume` | `POST /api/v2/runtime/commands/{command_id}/resume` | 用户/ACC → ACC/host | 是，按同一 command 或新 attempt 恢复 |

### 4.3 `register`

**用途**：声明一个 host 进程实例、它管理的 coding agent、连接方式和心跳能力。注册不是任务领取，也不是权限授予。

请求关键字段（PLANNED）：

```json
{
  "runtime_id": "runtime-dev-01",
  "instance_id": "runtime-dev-01-boot-20260827T120000Z",
  "host_id": "host-dev-01",
  "runtime_version": "0.1.0",
  "protocol_versions": ["runtime-control.v1"],
  "agent_inventory": [
    {"agent_id":"codex-01", "kind":"codex", "acp_version":"<negotiated-standard>", "state":"ready"},
    {"agent_id":"claude-01", "kind":"claude_code", "acp_version":"<negotiated-standard>", "state":"ready"}
  ],
  "mcp_endpoints": [{"name":"navop-public-mcp", "transport":"loopback_tcp", "discovery_ref":"file:///.../public-mcp.json"}],
  "observed_at": "2026-08-27T12:00:00Z",
  "heartbeat_interval_ms": 30000
}
```

规则：

- ACC 为 `runtime_id` 维护 epoch/instance generation；新 instance 注册会使旧 instance 的 lease 进入待回收状态。
- `register` 成功返回 `runtime_id`、`instance_id`、`registration_version`、`lease_policy`、`event_cursor` 和心跳要求。
- 重复 register 使用 `instance_id` 幂等；相同 instance 的 payload hash 不一致返回 `idempotency_key_reuse` 或 `version_conflict`，不可静默覆盖 agent inventory。
- 注册失败或 ACC 暂时不可用时，host 可以指数退避；不得在未注册状态执行平台 dispatch。

### 4.4 `lease`

租约保护的是某个 runtime/command 的执行权，不是 HTTP 连接。请求支持 `acquire`、`renew`、`release` 三种 action。

```json
{
  "action": "acquire",
  "runtime_id": "runtime-dev-01",
  "command_id": "cmd-123",
  "holder_id": "host-dev-01/agentcompanion-pid-42",
  "requested_ttl_ms": 30000
}
```

返回：

```json
{
  "lease_id": "lease-123",
  "holder_id": "host-dev-01/agentcompanion-pid-42",
  "fencing_token": 18,
  "issued_at": "2026-08-27T12:00:00Z",
  "expires_at": "2026-08-27T12:00:30Z",
  "renew_before_ms": 10000
}
```

- 每次重新取得同一资源的 lease 都产生严格递增 `fencing_token`；旧 holder 即使网络恢复，也不能写 ack/progress/complete。
- renew 必须提交 `lease_id`、`holder_id`、当前 `fencing_token`，过期、持有者不一致或 fencing 不匹配均拒绝。
- 默认 TTL 30 秒，允许范围由 server policy 限制；TTL 不是命令 deadline。命令 deadline 到期后不得靠 renew 延长副作用命令。
- release 是 best-effort，但服务端过期和新 token 抢占都必须安全；不能把 release 的 HTTP 成功当作执行停止。

### 4.5 `capabilities`

`GET /api/v2/runtime/capabilities?runtime_id=...` 返回三层结果（PLANNED）：

1. `declared`：host 注册的 Agent/MCP/工具事实；
2. `available`：当前进程、连接、会话和版本实际可用的能力；
3. `authorized`：针对当前租户、项目、主体和 policy evaluation 后可调能力。

示例：

```json
{
  "runtime_id": "runtime-dev-01",
  "registration_version": 7,
  "capabilities": [
    {
      "id": "agent.codex.prompt",
      "kind": "acp_agent_operation",
      "source": "codex-01",
      "available": true,
      "authorized": true,
      "input_schema_ref": "acp://standard/prompt",
      "requires_approval": false
    },
    {
      "id": "navop.terminal.write",
      "kind": "mcp_tool",
      "source": "navop-public-mcp",
      "available": true,
      "authorized": false,
      "requires_approval": true,
      "policy_reason": "production_write_requires_gate"
    }
  ]
}
```

`capabilities` 只做发现和决策输入；真正 dispatch 时仍重新做授权、审批和资源版本检查，防止 capability cache 过期。

### 4.6 `dispatch`

`dispatch` 创建 durable command，并将 command 投影到目标 host。它不直接调用 ACP/MCP。

请求（PLANNED）：

```json
{
  "idempotency_key": "tenant-a:task-7:attempt-1",
  "target": {"runtime_id":"runtime-dev-01", "agent_id":"codex-01"},
  "task_id": "task-7",
  "operation": "agent.prompt",
  "payload": {
    "session_id": "acp-session-9",
    "prompt": "运行测试并汇报失败原因",
    "approval_context": {"gate_id":"gate-22", "gate_version":3}
  },
  "requires_approval": false,
  "deadline_at": "2026-08-27T12:10:00Z",
  "lease": {"holder_id":"host-dev-01/agentcompanion-pid-42", "fencing_token":18}
}
```

响应：`202 Accepted`，返回 `command_id`、`status=accepted`、`status_url`、`events_url`、`event_cursor`。响应只表示命令已经被 ACC 接受/持久化，不表示 host 已收到，更不表示 coding agent 已执行。

对于同一个租户、资源和 operation，`idempotency_key` 必须保持相同以重试同一意图；不同意图不得复用 key。请求体 hash 不同必须返回冲突。

### 4.7 `ack`

host 对 command 的 durable 投影进行接收确认：

```json
{
  "delivery_id": "delivery-44",
  "runtime_id": "runtime-dev-01",
  "instance_id": "runtime-dev-01-boot-...",
  "accepted": true,
  "reason": null,
  "lease_id": "lease-123",
  "fencing_token": 18,
  "observed_at": "2026-08-27T12:00:02Z"
}
```

- `accepted=true` 只能推进到 `acked`，不可推进到 `running`。
- 无法执行、能力不存在、审批缺失时可以 `accepted=false`，写入拒绝原因；不能丢弃 command。
- ack 幂等；重复 ack 返回已记录的 event/result。

### 4.8 `progress`

progress 是可丢弃的细粒度输出与可持久化的阶段事实的组合：

```json
{
  "sequence": 12,
  "phase": "executing",
  "percent": 40,
  "message": "正在运行 5 个测试",
  "output": {
    "stream": "stdout",
    "chunk_ref": "artifact://tenant-a/cmd-123/chunks/12"
  },
  "checkpoint": {"name":"tests-started", "value_hash":"sha256:..."},
  "lease_id": "lease-123",
  "fencing_token": 18
}
```

- ACC 为 progress 事件分配 durable `event_id/sequence`；host 的 `sequence` 只用于检测重复/乱序，不作为平台 cursor。
- 大量 stdout/stderr 应写 artifact chunk；SSE 可只投影摘要、比例、chunk 引用。
- progress 不得把 terminal output 或 ACP update 当成最终结果；只有 complete 能终结命令。

### 4.9 `complete`

```json
{
  "outcome": "succeeded",
  "summary": "5/5 tests passed",
  "result": {"exit_code":0},
  "artifacts": [{"artifact_id":"art-1", "uri":"artifact://tenant-a/cmd-123/report.json"}],
  "metrics": {"duration_ms": 1234, "acp_turns": 2},
  "lease_id": "lease-123",
  "fencing_token": 18,
  "completion_token": "agent-observed-token"
}
```

允许的 `outcome`：`succeeded`、`partial`、`failed`、`cancelled`、`unknown`。complete 必须原子地写入命令终态、结果引用和 `command.completed.v1` 事件；重复提交同一结果返回已保存结果，不可以另一个结果覆盖终态。

当 host 无法确认 coding agent 是否已经产生副作用时，必须提交 `unknown` 或等待 reconcile，不得提交 `failed` 伪装网络错误。`unknown` 仍允许后续 `resume`/`reconcile`，但是否重新执行由 operation safety policy 决定。

### 4.10 `cancel`

cancel 是控制意图，不是强杀保证。它先记录 `cancel_requested`，投影到 host，host 再使用标准 ACP `cancel`（如果目标 coding agent 支持）或其受控进程终止机制。

- REST 响应 `202` 表示取消请求已持久化；`200` 仅表示已观察到已取消或已终态。
- 若命令已完成，cancel 返回当前终态和 `already_terminal=true`。
- 若 host 断开，ACC 仍写入取消命令；重连后必须先 replay 未确认 command，再执行 cancel。
- 取消不能撤销已发生的外部副作用；结果中应记录 `cancel_effective_at` 和已知副作用摘要。

### 4.11 `resume`

resume 用于网络中断、host 重启或 checkpoint 后继续：

- 优先恢复同一个 `command_id` 的未终结 attempt，使用新的 lease/fencing token；
- 若原操作不支持安全续接，创建新的 `attempt_id`，但保留 `parent_command_id` 和原 idempotency 记录；
- resume 请求必须带 `from_event_cursor` 或 `checkpoint_ref`，避免从未知状态盲目重做；
- `unknown` 命令只能在查询/对账证明“未执行”或 operation 明确声明可重复时自动 resume；生产写、发布、删除、资金/权限变化默认为人工确认；
- resume 也必须有独立幂等键，响应只承诺 resume intent 已落库。

## 5. 统一 envelope 与数据模型

### 5.1 Envelope 总结构

所有 Runtime Control command、response、durable event 使用同一逻辑 envelope；REST response 可以将 `payload` 放在 `data` 兼容既有客户端，但不得丢失这些语义字段。

```json
{
  "schema_version": "runtime-control.v1",
  "kind": "command|response|event",
  "type": "runtime.dispatch.v1",
  "id": "msg-uuid",
  "command_id": "cmd-uuid",
  "event_id": "evt-uuid",
  "sequence": 1042,
  "tenant_id": "tenant-a",
  "project_id": "project-1",
  "trace_id": "trace-uuid",
  "correlation_id": "corr-uuid",
  "causation_id": "msg-previous",
  "idempotency_key": "tenant-a:task-7:attempt-1",
  "source": {"type":"acc", "id":"acc-1"},
  "target": {"type":"runtime", "id":"runtime-dev-01", "agent_id":"codex-01"},
  "actor": {"type":"user|service|runtime", "id":"user-1"},
  "created_at": "2026-08-27T12:00:00Z",
  "observed_at": "2026-08-27T12:00:02Z",
  "deadline_at": "2026-08-27T12:10:00Z",
  "attempt": 1,
  "lease": {
    "lease_id":"lease-123",
    "holder_id":"host-dev-01/agentcompanion-pid-42",
    "fencing_token":18,
    "expires_at":"2026-08-27T12:00:30Z"
  },
  "cursor": {"stream":"run-1", "sequence":1042},
  "payload": {},
  "artifacts": [],
  "error": null
}
```

### 5.2 字段规则

| 字段 | 必须性 | 规则 |
|---|---|---|
| `schema_version` | 必须 | 只做向后兼容演进；不因 JSON-RPC version 改变。 |
| `kind/type` | 必须 | `type` 使用稳定版本后缀，例如 `command.accepted.v1`。 |
| `id` | 必须 | 当前消息唯一 ID；不能取代 command/event ID。 |
| `command_id` | command/command event 必须 | 一个意图的稳定标识，跨 retry/reconnect 不变。 |
| `event_id/sequence` | durable event 必须 | event_id 全局唯一；sequence 在 stream 内单调递增。 |
| `tenant_id/project_id` | 服务端可信上下文必须 | 由认证 claims 和资源关系派生/核对，不信任 body。 |
| `trace_id/correlation_id/causation_id` | 必须 | 分别表示链路、用户请求族、触发上一个事实；只用于关联，不赋予交付语义。 |
| `idempotency_key` | 所有有副作用 command 必须 | 租户+资源作用域唯一，保存 request hash 和结果。 |
| `created_at/deadline_at` | command 必须 | RFC 3339 UTC；服务端校验时钟偏差。 |
| `attempt` | command/event 建议 | 每次安全恢复或重试递增；不改变 command_id。 |
| `lease` | host 执行写入必须 | ack/progress/complete/cancel acknowledgement 必须带当前 fencing 信息。 |
| `payload` | 按 type | JSON Schema 受 OpenAPI/契约测试约束。 |
| `artifacts` | 可选 | 大型、敏感或二进制输出只能引用。 |
| `error` | 失败响应/事件 | 使用统一错误对象；不泄漏 token、secret、原始凭据。 |

Envelope 中的 `sequence` 只属于已持久化 stream；HTTP 请求序号、WS 帧序号、ACP request id、MCP JSON-RPC id 都不能充当 durable cursor。

### 5.3 HTTP 错误 envelope（CURRENT 基础，v3 统一）

```json
{
  "error": {
    "code": "lease_fenced",
    "message": "fencing token is stale",
    "retryable": false,
    "details": {"expected_fencing_token":19, "actual_fencing_token":18},
    "conflicts": []
  },
  "request_id": "req-uuid",
  "correlation_id": "corr-uuid"
}
```

该形状与 ACC `internal/httpapi/errors` 以及 OpenPocket facade parser 的 CURRENT 行为保持兼容。错误里的 `retryable` 只说明重试请求是否安全，不是“客户端重新发同一副作用操作”的授权。

## 6. 命令面与事件面

### 6.1 命令面（REST/OpenAPI）

命令面提供资源定位、校验、认证、幂等和同步确认：

| 类别 | PLANNED canonical endpoint | 说明 |
|---|---|---|
| runtime 注册 | `POST /api/v2/runtime/register` | 创建/更新实例 epoch |
| runtime 能力 | `GET /api/v2/runtime/capabilities` | 发现、过滤、授权视图 |
| command 状态 | `GET /api/v2/runtime/commands/{id}` | 查询当前状态、attempt、lease、artifacts |
| dispatch | `POST /api/v2/runtime/dispatch` | 创建 durable command，要求幂等键 |
| command ack/progress/complete | `POST /api/v2/runtime/commands/{id}/{ack|progress|complete}` | host 回报，带 fencing |
| cancel/resume | `POST /api/v2/runtime/commands/{id}/{cancel|resume}` | 控制意图，带幂等键 |
| run/task events | `GET /api/v2/orchestration/runs/{id}/events` | CURRENT durable list，可作为兼容投影 |
| approval decision | `POST /api/v2/approvals/{gate_id}/decision` | CURRENT OpenPocket facade 依赖；v3 扩展版本和幂等语义 |

命令响应的 HTTP 状态约定：

- `200 OK`：查询成功、已存在的幂等回放、已观察到目标终态；
- `201 Created`：创建了新资源；
- `202 Accepted`：意图/命令已持久化，执行尚未确认；
- `400/422`：参数或契约无效；
- `401/403`：身份或策略拒绝；
- `404`：资源不存在（不得把 unknown 当 404）；
- `409`：幂等冲突、资源版本、lease/fencing、非法状态迁移；
- `410 Gone`：cursor 已过期，需要 snapshot fallback；
- `429`：限流；
- `502/503/504`：上游或服务暂时不可用；是否可重试由 error.retryable 和 operation policy 共同决定。

### 6.2 事件面（SSE）

canonical stream（PLANNED）可按以下任一资源投影：

```text
GET /api/v2/runtime/commands/{command_id}/events?after=<sequence>
GET /api/v2/orchestration/runs/{run_id}/events/stream?after=<sequence>  (CURRENT)
```

SSE frame：

```text
id: 1042
event: command.progress.v1
data: {"schema_version":"runtime-control.v1","kind":"event","type":"command.progress.v1","event_id":"evt-...","sequence":1042,"command_id":"cmd-123","payload":{...}}

```

约束：

- `id` 为 server durable sequence；客户端同时保存 `event_id`、stream id 和 payload hash。
- 客户端重连同时发送 `?after=<last_sequence>` 和 `Last-Event-ID`；服务端以可验证的 cursor 规则去重，不能只信任 header。
- server 必须先 replay gap，再切 live tail；不能先推 live 再补历史而造成顺序歧义。
- keepalive comment（如 `: keepalive`）只防止代理关闭，不是事件、不推进 cursor。
- `projection.gap`/`cursor_expired` 要明确告诉客户端是否需要 replay 或 snapshot；不得静默丢事件。
- 事件 store 以 ACC durable store 为准；SSE 断开不改变命令状态。

### 6.3 WebSocket 限制

WS 可用于：

- 反向控制和交互式终端输入；
- PTY/终端的 best-effort 输出；
- WebRTC offer/answer/ICE 信令；
- UI 即时提示或 presence。

WS 不可用于：

- 创建/完成平台 canonical command；
- 审批决策、lease/fencing 更新、最终结果写回；
- 代替 SSE replay 或 cursor；
- 宣称 exactly-once、durable delivery、全局顺序。

若交互式终端输出与 command 结果有关，终态和可审计输出必须通过 REST `complete` + artifact/event store 落库；WS 只负责低延迟显示。

## 7. 状态机

### 7.1 Runtime/host 状态

```text
new → registered → healthy
registered/healthy → degraded（心跳超时、能力变化）
degraded → healthy（重新 register/heartbeat）
degraded → offline（超过失联阈值）
offline → registered（新 instance epoch）
```

`offline` 不自动把所有 command 标为 failed：正在执行的命令进入 `unknown` 或 `awaiting_reconcile`，是否可 resume 由操作类型策略决定。

### 7.2 Command 状态

```text
accepted
  ├─ rejected
  ├─ awaiting_approval → accepted（批准）
  │                    ├→ cancelled（拒绝/过期）
  │                    └→ accepted（重新批准）
  └─ delivered → acked → running
                         ├→ progress（非终态事件）
                         ├→ cancel_requested → cancelled
                         ├→ succeeded
                         ├→ partial
                         ├→ failed
                         └→ unknown → reconciling → succeeded/failed/cancelled/unknown
```

`resuming` 是执行事件/attempt 状态而非另一个可混淆的业务终态；外部 API 可返回 `status=resuming`，但最终仍必须落入上述终态或 `unknown`。

### 7.3 状态不变量

1. 状态只能由 ACC durable transaction 追加合法事件后推进，不能由 UI 本地状态覆盖。
2. `succeeded/partial/failed/cancelled` 为终态；终态 command 的相同幂等请求只能回放原结果。
3. `unknown` 不是终态完成，也不是普通失败；它必须携带 `unknown_reason`、最后观察时间、attempt 和 reconcile action。
4. `complete` 成功必须有合法 lease/fencing，除非是 ACC reconciliation worker 使用受控内部身份写入。
5. approval 未满足时，不得向 host 发出实际副作用 command；可以发送 `awaiting_approval` 事件。
6. ACP `update` 或 MCP tool result 只能成为 host 的输入事实，必须经 Runtime Control `progress`/`complete` 转换后才进入平台状态机。

### 7.4 与 CURRENT task state machine 的关系

ACC `/api/v2/tasks-pg` 当前已有 `todo`、`assigned`、`in_progress`、`blocked`、`paused`、`review`、`approved`、`revision`、`done`、`failed`、`cancelled`、`archived` 及 mission phases；它是 **CURRENT** 任务状态实现。Runtime command 状态是执行交付状态，不能直接用 task 的 `done` 表示 host 已完成某个 command。v3 需要建立 `task_id → command_id → attempt_id` 映射，并由 task projector 根据 command events 推进任务，而不是让两套状态互相写表。

## 8. 幂等、lease、fencing 与 unknown outcome

### 8.1 幂等键

- 所有产生副作用的 POST（dispatch、approval decision、cancel、resume、ack/progress/complete）都必须明确其幂等策略；客户端写请求沿用 OpenPocket facade 的 `Idempotency-Key`。
- ACC 按 `tenant_id + operation + resource scope + idempotency_key` 保存 request hash、首次响应、状态和过期时间。
- 相同 key + 相同 canonical request：返回首次结果（可为 200/201/202，响应体语义相同）。
- 相同 key + 不同 hash：`409 idempotency_key_reuse`，不得执行第二次。
- 自动生成 key 只能用于客户端确认“这是同一个 intent”的场景；网络超时后必须持久化并复用原 key，不能每次随机生成新 key。
- `GET` 查询本身不需要幂等键，但应使用 cursor/resource version 保证读取语义。

### 8.2 Lease 与 fencing

- lease 是“谁可以代表某个 attempt 写入执行事实”的短期授权；JWT scope、MCP token、ACP session 都不能取代 lease。
- fencing token 单调递增且由 ACC 产生；所有 host 写入携带 token，数据库条件更新必须类似 `WHERE fencing_token = current_token AND lease_expires_at > now()`。
- 旧 holder 的迟到 progress/complete 一律拒绝并记录 `lease_fenced` audit event；不能因为 payload 看起来更新就接受。
- lease 续期与命令 deadline 分离；deadline 到期后只允许取消、对账或人工 resume，不允许无限续期。

### 8.3 unknown outcome 处理矩阵

| 场景 | 平台状态 | 客户端动作 | 是否自动重放 |
|---|---|---|---|
| dispatch HTTP 超时，ACC 未知是否落库 | 查询 idempotency/status | 复用原 key 查询 | 仅同 key，不新建 command |
| ACC 已落库，host 未 ack | `accepted`/`delivering` | 等待 replay 或 cancel | 不重复创建 |
| host 调 coding agent 后断线，未 complete | `unknown` | 查询 host、ACP session 或 reconcile | 读操作可；副作用默认否 |
| complete 请求超时 | `unknown` 或保持 running | 复用 complete key/查状态 | 不提交另一结果 |
| lease 过期，旧 host 回报 | 保持当前状态 | 新 host claim、新 fencing token | 旧写入绝不重放 |
| MCP 工具返回超时 | `unknown` | 按工具 safety policy 对账 | destructive 默认人工确认 |

## 9. 审批命令与授权分层

### 9.1 三个不同概念

1. **平台授权**：ACC 根据已认证主体、tenant/project、RBAC/ABAC、资源 scope 计算“允许发起什么命令”。
2. **平台审批**：高风险命令需要人工 gate；审批记录、版本和决定持久化在 ACC。OpenPocket 当前 facade 已有 `POST /api/v2/approvals/{gate_id}/decision`，这是 **CURRENT** 入口。
3. **工具内部 permission**：navop Public MCP 的 `deny/ask/allow` 或 coding agent 的 ACP permission request；它是本机工具/Agent 的安全门，不可反向授予平台权限。

### 9.2 审批命令流程（PLANNED，复用 CURRENT approval facade）

```text
用户/策略 → dispatch intent
  → ACC policy evaluation
  → 无需审批：写 command.accepted
  → 需要审批：写 approval.requested + command.awaiting_approval
  → OpenPocket GET/SSE 呈现 gate
  → POST /api/v2/approvals/{gate_id}/decision
  → 校验 approver、tenant、scope、gate_version、expires_at、幂等键
  → approved：写 approval.approved，生成/释放 command
  → rejected/expired：写 approval.rejected/expired，command.cancelled
  → host 执行时仍做最终 policy check
```

审批决定请求至少包含：`decision`（approve/reject）、`expected_gate_version`、`reason`、`idempotency_key`。版本不一致返回 `409 version_conflict`。审批不能修改原始 command payload；若要改变命令，创建新的 intent/command，并保留 `causation_id`。

对于 `Ask` MCP 工具：ACC 必须在 dispatch 前完成平台 gate；host 触发 navop permission prompt 时，必须把 ACP/MCP 的本地询问映射为 `permission.requested` 事件并等待符合 policy 的决定，不能使用 host 上的 allow mode 绕过 ACC gate。

## 10. Cursor、replay 与 snapshot fallback

### 10.1 Cursor 规则

- 每个 durable stream 有独立 `stream_id`、`cursor_version` 和单调 `sequence`；sequence 只在该 stream 内有序。
- 客户端持久化 `{stream_id, last_sequence, last_event_id, payload_hash}`，收到事件后先校验 stream/schema，再原子更新 cursor。
- 重连传 `after` 和 `Last-Event-ID`；若两者冲突，服务端返回 `409 cursor_conflict` 或按更保守的较小 cursor replay，不得静默跳过。
- replay 返回事件按 sequence 严格升序；重复事件由客户端以 event_id/sequence 去重。
- projector 的内存缓冲溢出必须发 `projection.gap`，不能仅记录日志。CURRENT ACC SSE 已有 dropped/gap 提示，v3 需标准化为统一 envelope。

### 10.2 Snapshot fallback

当 cursor 早于保留窗口、event store compacted、租户恢复或 projector 无法补齐时：

1. REST/SSE 返回 `410 cursor_expired`，details 包含 `oldest_available_sequence`、`snapshot_url`、`snapshot_sequence`。
2. 客户端 GET snapshot，snapshot 必须包含 `stream_id`、`snapshot_sequence`、`resource_version`、完整资源状态和 `state_hash`。
3. 客户端校验快照后，将本地 cursor 设置为 `snapshot_sequence`，再以 `after=snapshot_sequence` replay 后续事件。
4. 若 snapshot 与增量 hash 不一致，停止自动合并，报告 `snapshot_inconsistent` 并重新拉取；不得以本地状态覆盖服务端。
5. 无法提供可靠 snapshot 的流必须保留足够 event retention；不能以返回空列表假装 replay 成功。

### 10.3 OpenPocket 兼容要求

OpenPocket facade 当前已经发送 `after`、`Last-Event-ID` 并在断线后重连。迁移到 ACC canonical stream 时应保留该行为，同时把当前 `/api/v2/runs/{id}/events` 与 `/api/v2/orchestration/runs/{id}/events/stream` 的路径差异通过明确 adapter/redirect 契约解决，不能依赖客户端猜测。

## 11. 错误码契约

错误码是稳定机器契约，message 可本地化。除表中 HTTP status 外，所有错误继续使用 `request_id` 和可选 `correlation_id`。

| code | HTTP | retryable | 含义 |
|---|---:|:---:|---|
| `invalid_request` | 400 | 否 | JSON、字段或 schema 无效 |
| `missing_required_header` | 400 | 否 | 缺少 `Idempotency-Key` 等必要 header |
| `unauthorized` | 401 | 否 | token/mTLS 无效或过期 |
| `forbidden` | 403 | 否 | 主体无平台权限 |
| `tenant_mismatch` | 422 | 否 | 资源与可信 tenant 不匹配 |
| `capability_unavailable` | 409/503 | 视情况 | 能力未注册、进程不在位或暂时不可用 |
| `approval_required` | 403/409 | 否 | 必须先创建/完成审批 |
| `approval_rejected` | 403 | 否 | 人工拒绝 |
| `approval_expired` | 409 | 否 | gate 已过期 |
| `version_conflict` | 409 | 是（重新读取后） | resource/gate version 不匹配 |
| `idempotency_key_reuse` | 409 | 否 | 同 key 不同 request hash |
| `command_not_found` | 404 | 否 | command 不存在 |
| `invalid_state_transition` | 409 | 否 | 不允许的状态迁移 |
| `lease_unavailable` | 409 | 是 | 资源被其他 holder 占用 |
| `lease_expired` | 409 | 是（重新 claim） | lease 已过期 |
| `lease_fenced` | 409 | 否（旧 holder） | fencing token 过旧 |
| `runtime_not_registered` | 409/503 | 是 | host 尚未有效注册 |
| `runtime_offline` | 503 | 是 | host 当前离线 |
| `deadline_exceeded` | 504 | 视操作 | command deadline 到期；副作用结果可能 unknown |
| `unknown_outcome` | 202/409 | 否（先对账） | 无法判断执行结果 |
| `cursor_expired` | 410 | 否 | 需要 snapshot fallback |
| `cursor_conflict` | 409 | 否 | stream cursor 不一致 |
| `snapshot_inconsistent` | 409/503 | 是 | snapshot/hash 与事件不一致 |
| `upstream_unavailable` | 502/503 | 是 | Memora、host、工具或其他上游暂时不可用 |
| `rate_limited` | 429 | 是 | 按 `Retry-After` 退避 |
| `artifact_not_found` | 404 | 否 | artifact 引用不存在/已过期 |
| `artifact_forbidden` | 403 | 否 | 无 artifact scope |
| `internal_error` | 500 | 否 | 未分类服务错误，细节仅日志 |
| `route_retired` | 404 | 否 | 已退役路径及 canonical replacement |

“retryable=true” 不得解释为“所有请求都可安全重做”。客户端必须同时读取 operation policy：`read_only`、`idempotent`、`at_most_once`、`reconcile_before_retry` 或 `human_confirmation_required`。

## 12. 超时、重试和背压

### 12.1 默认预算（PLANNED 基线）

| 环节 | 默认值 | 规则 |
|---|---:|---|
| ACC REST 普通请求 | 30s | 连接、header、body、handler 分开计时；查询超时返回 retryable/upstream |
| dispatch/ack REST | 10s | HTTP 超时不改变 command 的未知事实；必须以幂等 key 查询 |
| progress/complete REST | 15s | 超时后复用相同 completion/progress key 或查询，不新建结果 |
| SSE 建连 | 10s | 建连失败可退避；连接本身无固定 request deadline |
| SSE keepalive | 15s | 与 ACC CURRENT projector 的 keepalive 对齐；代理不应缓存 |
| SSE reconnect backoff | 0.5s 起，指数至 30s | 带 jitter，收到 429/503 遵循 Retry-After |
| runtime lease TTL | 30s | renew-before 默认 10s；受服务端上下限约束 |
| host heartbeat | 30s | 连续 3 个周期未收到进入 degraded/offline 评估 |
| ACP initialize/session | 10s | 失败不执行 prompt；按标准 ACP 生命周期重建 |
| ACP prompt turn | 由 command deadline 限制 | 不在平台外另设无限等待 |
| MCP discovery/tool call | 5s/30s（读/执行） | raw TCP 建连按 navop 实现；工具副作用超时进入 unknown |
| Memora HTTP v2 | 30s | 使用现有 client 的 retry policy；4xx 不重试，5xx/network 按策略重试 |

### 12.2 重试安全

- 只对连接前失败、明确未提交的只读操作自动重试。
- 对 dispatch、审批、cancel、resume、tool write，必须持久化 idempotency key；未知结果先 GET status/reconcile。
- host 接收到相同 command_id/attempt 时必须返回原 ack/result，不创建第二个 ACP session，除非策略显式允许。
- progress 可按 event key 去重；stdout chunk 不能因为重试被拼接两次，artifact 需 hash。
- 背压时 host 降低 progress 频率、上传 artifact chunk、保留 checkpoint；不得丢失 ack/complete/approval/lease 事件。

## 13. 输出与 artifact 引用

### 13.1 Artifact 结构

```json
{
  "artifact_id": "art-uuid",
  "uri": "artifact://tenant-a/commands/cmd-123/report.json",
  "kind": "stdout|stderr|report|diff|table|file|checkpoint|acp_transcript",
  "content_type": "application/json",
  "byte_size": 18420,
  "sha256": "sha256:...",
  "created_at": "2026-08-27T12:01:00Z",
  "expires_at": "2026-09-03T12:01:00Z",
  "retention_class": "task|audit|temporary",
  "access_scope": ["tenant:a", "project:project-1"],
  "download_url": "https://acc.example/api/v2/artifacts/art-uuid/content",
  "inline_preview": {"text":"5/5 tests passed", "truncated":false}
}
```

### 13.2 规则

- `uri + sha256 + byte_size` 是完整性和去重依据；`download_url` 可过期、可重新签发，不是稳定身份。
- 小结果可以 inline，但仍应提供 kind 和 schema；建议文本 8 KiB、JSON 64 KiB 以内，超出即 artifact 化。
- stdout/stderr、diff、截图、ACP transcript、MCP 原始响应、checkpoint 都应按敏感等级设置 retention/access scope；secret、token、cookie、私钥一律脱敏或拒绝落盘。
- artifact 下载必须重新校验 tenant/project/command 权限；知道 URI 不等于有权读取。
- `complete` 引用的 artifact 必须先完成不可变写入并可校验，或明确标注 `pending_upload`，不可把本地临时路径作为平台输出。
- 失败也可有 artifact（诊断报告、日志）；`failed` 不代表没有输出。

## 14. ACP、MCP、A2A 的实施契约

### 14.1 标准 ACP（CURRENT 能力基础；规范化为 PLANNED 平台边界）

navop 调研事实显示其 `agent_runtime` 已有面向 Codex、Claude Code、OpenCode 的 ACP 0.14 接入；但 workspace 当前没有 AgentCompanion 项目。因此：

- AgentCompanion/host 作为 ACP host/client，coding agent 作为 ACP server/peer，严格采用所选标准 ACP 版本的官方消息、字段和生命周期。
- 必须覆盖：`initialize`/能力协商、session 创建/加载/结束、`prompt`、标准 `cancel`、Agent 的 `update`/流式通知、`permission` 请求和决定。
- ACP session 的 id、request id、update id 只在 ACP 对端生命周期内有意义；host 必须把关键事实映射为 Runtime Control `command_id/event_id`。
- 不在 ACP 上加租约、fencing、平台 envelope、durable cursor 或审批字段；这些通过 Runtime Control REST/SSE 和 HTTP metadata 完成。
- coding agent 的 permission request 不能跳过 ACC policy；host 应拒绝不在授权 command scope 内的请求，并回报可审计的 permission event。
- 不创建第二个 `acp-protocol` crate 来定义 `capability.list/invoke/stream`。需要调用 navop/IDE 工具时走 MCP 或其既有原生接口。

### 14.2 MCP（CURRENT navop Public MCP；扩展按标准 MCP）

MCP 承担：

- `initialize`/server information；
- `tools/list`、tool schema discovery、`tools/call`；
- `resources/list`、`resources/read`（若 server 提供）；
- 工具返回的结构化内容、文本和资源引用。

调用前的强制顺序：

```text
ACC policy + approval（平台授权）
  → runtime capabilities（可用性）
  → MCP discovery（工具是否存在/当前 schema）
  → MCP tools/call（工具执行）
  → Runtime Control progress/complete（平台事实）
```

navop raw TCP 的 token 握手、loopback 限制和 `Deny/Ask/Allow` 模式只能保护 navop 本地边界。平台不得把工具列表当作权限列表，也不得因为 navop 处于 `Allow` 就跳过 ACC gate。

### 14.3 A2A adapter（未来 PLANNED）

仅当需要跨自治 Agent、外部组织或联邦时实现 adapter：

- 发布标准 **Agent Card**：身份、能力、认证、受支持任务/消息类型、SSE endpoint；不把本机 host inventory 全部公开。
- 支持 `message/send` 创建或追加外部 task；adapter 映射外部 task id ↔ ACC `command_id/run_id`，保留 correlation/causation。
- 支持 `tasks/get` 查询状态和结果，`tasks/cancel` 发出取消意图；外部 A2A task 不能直接写 ACC 状态，必须经 adapter policy、幂等和 fencing 层。
- 支持 SSE 状态/更新流；外部 stream 断线通过 A2A/adapter cursor 或 ACC snapshot 恢复。
- A2A 传输和 JSON-RPC framing 仍不提供本平台可靠性；adapter 必须落到 Runtime Control/ACC durable store。
- 第一版不实现 A2A adapter，不在 ACC↔本机 AgentCompanion 路径使用 `task.delegate`、A2A WebSocket 或自定义 A2A JSON-RPC。

## 17. 验收标准

### 协议边界

- [ ] 代码和 OpenAPI 中不存在平台自定义第二 ACP；不存在以 `capability.invoke/stream` 冒充 ACP 的新实现。
- [ ] ACC↔AgentCompanion 第一版所有命令均可用 REST/OpenAPI 表达，所有 durable 状态均可用 SSE replay 或 snapshot 恢复。
- [ ] A2A endpoint 在第一版不开放；未来 adapter 有 Agent Card 和标准 task/message/SSE 契约。
- [ ] MCP tool list、token、Deny/Ask/Allow 均不能单独改变 ACC authorization 结果。

### 可靠性

- [ ] 任意写 command 都有 idempotency key；相同 key 重试不会新建副作用，hash 冲突可检测。
- [ ] lease 过期、fencing token 过旧的 progress/complete 永不改变结果。
- [ ] 注入网络超时时能区分 `failed` 与 `unknown`，并能按策略 reconcile/resume。
- [ ] SSE 从任意 cursor 断线重连后不丢 durable event；过期 cursor 能完成 snapshot fallback。
- [ ] WS 断线不会丢失 command/approval/terminal completion 的 durable 事实。

### 代码事实对齐

- [ ] ACC canonical paths、OpenPocket facade contract paths、Memora native v2 paths 和 navop raw TCP Public MCP 的差异在 adapter/测试中明确记录。
- [ ] 所有实现状态标注 CURRENT/PLANNED；未实现 AgentCompanion 不以“已有 daemon”出现在运行时清单或部署验收中。
- [ ] Runtime Control、ACC orchestration、OpenPocket facade、Memora 和 navop 的契约测试覆盖成功、重复、超时、断线、拒绝、审批、artifact 和恢复场景。

## 18. 最终原则

**协议负责边界，持久化状态负责可靠性，策略负责授权，审批负责高风险人机门，租约/fencing 负责并发所有权，SSE/cursor/snapshot 负责可恢复观察，artifact 负责大输出。**

JSON-RPC 可以作为 ACP/MCP/A2A 内部的消息 framing 或标准协议组成部分，但它本身永远不被视为上述任何一项保证。
