# 2026-10-02 归类风暴、LLM 网关 429，以及对 IMAP 失败率的更正

本文件记录一次只读诊断的结论。**没有改动任何生产行为**，全部结论都能在
`logs/pocketd-18099-20261002-013559.err.log`（89 MB / 857,784 行）里复核。

## 1. 归类热循环：856,160 次失败，已随既有修复停止

日志里 99.99% 的内容是同一行：

```
[email/classify] em-<id>: llmbff: no provider configured
```

- 区间 **01:43:44 → 03:19:31**，共 **856,160 行**
- 峰值 **每分钟 37,590~39,046 行**（≈640 次/秒）
- 对端：本机 `127.0.0.1`（`Get-NetTCPConnection` 实测只有一条已建立连接），
  即一个打开着的浏览器标签页

### 机制

`server_email_classify.go:55` 用 `ListUnclassifiedScoped` 取未归类邮件
（默认 20 封），逐封 `classifyOneEmail`；失败时**只在 `out.Error` 里记一笔、
不落任何数据库状态**（`server_email_classify_gateway.go:161`）。于是这批邮件
永远留在「未归类」里，客户端下一轮又取到同一批。服务端没有任何退避、
失败记忆或调用方节流，一个热循环客户端就能把端点打成永动机。

### 为什么它停了

| 时间 | 事件 |
|---|---|
| 01:35:53 | 当前 pocketd 二进制构建 |
| 01:43:44 | 风暴开始 |
| 02:34 | `48ae6aad` fix(email): 归类循环空转——零进展连续 2 轮即停并如实上报 |
| 02:58:29 | `frontend/dist` 重建 |
| 03:19:31 | 风暴最后一行 |

**如实标注不确定性**：风暴停止的时间点在重建之后 21 分钟，这与「修复生效」
一致，但也与「那个标签页被刷新或关掉」一致。**本次没有做对照实验，无法断言
因果关系**。能确定的只是：风暴已经不在继续。

### 仍然存在的缺口

客户端侧的「零进展即停」已修，**服务端侧仍无任何保护**：失败不落状态、
无退避、无单封失败记忆。再来一个热循环客户端，同样的 89 MB 会再来一次。
加服务端护栏属于生产行为变更，未擅自实施。

## 2. 重要邮件提醒仍写不进 importance —— 但原因换了

- 04:12:38 → 07:28:03 共 **106 次** `llm-gateway chat 429`：

  ```json
  {"error":{"code":"rate_limit_exceeded","message":"Rate limit exceeded",
            "type":"rate_limit_error"}}
  ```

- 这 106 次来自 **13 个** `POST /api/emails/classify` 请求（`[SLOW]` 埋点），
  单个请求耗时 37s ~ 2m0s（打满 2 分钟上限）。**不是风暴，是慢请求。**
- **成功 0 次。**

这推翻了之前「AI 路径报 `no provider configured`，网关没配」的结论：
**网关是通的**，只是每次调用都被限流拒绝。`llm-gateway`（`internal/llmgateway/client.go:179`）
对非 200 直接返回错误、不重试，所以 429 是终态。

叠加另一条已确认的事实：5 个账户的 `rules` 全为 NULL，`ParseRules("")` 返回 nil，
`fetcher.go:756` 的 `len(rulesParsed) > 0` 守卫不成立 ⇒ **本地规则路径一次都没执行过**。

**结论：当前部署下，importance 仍然没有任何一条生产写入路径。** 这需要网关
侧配额/凭证，与飞书凭证同属「等用户」的阻塞项。

### 4.1 更正：89 MB 是历史存量，当前几乎不再增长（2026-10-02 09:47 实测）

原表述「一次失控循环就能把磁盘写满」需要限定：那个循环**不是常驻的**。

| 测量项 | 值 |
|---|---|
| 单文件 `pocketd-18099-20261002-013559.err.log` | 93,416,646 B（09:47:01） |
| 60 秒后 | 93,416,882 B（09:48:01） |
| 增长速率 | **236 B/分钟 ≈ 0.014 MB/小时** |
| 最后一条 `[email/classify]` | **09:15:49**（测量时刻 09:48:32，即 33 分钟前无归类） |
| 最后一条 `[email/fetcher]` | 09:48:01（即测量时刻，仍在正常收信） |

即 03:19 停过的那轮热循环**在 09:15 前后又复发过一次**，随后自行停止。

**结论修正**：磁盘当前**没有**紧迫风险；但热循环是会**间歇复发**的，而零
轮转意味着任何一次复发都可能是几十 MB 量级且无自限。所以「加轮转」从
「紧急」降级为「有复发窗口的潜在风险」——不是可以因为「现在没在涨」就
永久搁置的那类。该结论属运维策略，仍未擅自实施。

## 5. 已查明：login 挂死为什么是精确 80s（2026-10-02 09:39 更新）

**这一节原来的结论（「运行进程的行为与当前源码常量对不上，机制未查明」）是
错的，已推翻。**

53 次 SLOW 事件耗时**全部**落在 `1m20.000s`（32 次 `1m20.001s`、
11 次 `1m20s`、10 次 `1m20.002s`），60s 的一次都没有。

### 5.1 先排除：不是常量对不上

- 运行二进制 `backend/.verify-bin/pocketd.exe` 构建于 10-02 01:35:53；
- `git log -S imapHardTimeout` 全历史只有 `b4da251c`（10-01）一处引入，
  取值**恒为 45s**，从未改过；
- `git log -S imapIdleTimeout` 同理，**恒为 60s**；
- 并发会话那条线的工作区（`C:\workspace\openpocket`，HEAD=`bdb09074`）的
  `fetcher.go` 也是 60/45/70，且 git 状态干净。

**当时那句「本地实测两种形态都产不出 80s」本身没错，错的是据此推断
「运行进程的常量与源码对不上」。**

### 5.2 实测：用生产常量打一台「accept 后永不写入」的黑洞服务器

| | 值 |
|---|---|
| 模型 `ceil(hard/tick)*tick`（699c1b0c 当时写进测试的公式） | 1m0s |
| **实测有效截止** | **1m20.001s** |
| POP3 兜底可用余量 | **-10.001s** |

三次独立测量 80.002 / 80.001 / 80.001，与线上 80.1xx 吻合。

### 5.3 真实机制（给看门狗循环加临时日志打出来的四拍）

```
t=20s   since=20s      now-hard=-25.001s  -> REFRESH  (deadline -> t0+80)
t=40s   since=40s      now-hard=-4.999s   -> REFRESH  (deadline -> t0+100)
t=60s   since=1m0.001s now-hard=+15.001s  -> HARD, set past   <- 判定正确
t=80s   since=1m20s    now-hard=+35.001s  -> HARD, set past
实测断开 = 1m20.001s
```

第 3 拍**已经**正确判定越界、也确实调用了 `SetDeadline(now-1s)`，但那次调用
**没能打断已经阻塞的读**；读一直活到**第 1 拍**刷进去的那个 OS 截止到期。
第 2 拍的 REFRESH（t0+100）同样没生效。**只有第 1 拍的 `SetDeadline` 真正
生效**，之后无论把截止钉到过去还是刷到更远，都不再改变已在等待中的读的到期
时刻。

于是实测不变式：

```
有效硬截止 = 首个 tick + imapIdleTimeout = idle/3 + idle = 4/3 · idle = 80s
```

### 5.4 两条被推翻/新增的结论

1. **`TestIMAPLeavesBudgetForPOP3Fallback` 的公式已被证伪。** 它按
   `ceil(hard/tick)*tick` 算出 60s、余量 +10s，于是通过；但实测占用 80s、
   余量 -10s。**不要再把它的通过当成 POP3 兜底可达的证据。**（已在
   `0d96d936` 给该用例加显著注释，未改其断言。）
2. **「降 imapHardTimeout 至 30s / LOGIN 15s 重试」这个方案前提不成立。**
   因为有效截止与 `imapHardTimeout` **无关**——只要 `hard > 首个 tick`，
   硬截止分支就来不及生效，兜底的反而是第 1 拍刷下的 idle 滚动截止。
   45s→30s、→15s 都仍有 `hard > 20s`，都不会提前断开。要真正生效必须
   `hard <= idle/3 = 20s`，或调大 `syncBudget`，或给 `syncPOP3Fallback`
   保底预算，或让看门狗越界时直接 `Close()` 而非 `SetDeadline`。

### 5.5 连带发现：POP3 兜底 76 次全部没跑成

858,241 行日志里 fetcher/pop3 的非信息类错误**只有一种形态**、共 76 条，
全部是 `… i/o timeout — trying POP3 fallback (budget -10s left)`。
`syncPOP3Fallback` 在 `budget <= 0` 上直接返回，所以一次都没真正降级过。
`c459400a` 给 POP3 路径补的 `UpdateSyncState` 因此目前是「正确但不可达」。

以上均属生产路径行为变更（待决清单里挂着「是否处理 IMAP 挂死」），本轮
只加诊断不改行为。测量方法与四拍日志已固化在
`backend/internal/email/diag_hard_deadline_test.go`（门禁
`POCKET_DIAG_HARDDEADLINE=1`，约 80s；它断言「实测占用 >= syncBudget」时
**转红**，已验证确实会红）。
