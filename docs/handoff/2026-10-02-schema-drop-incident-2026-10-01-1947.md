## 真实机制：整表被重建，不是被删了几行

幸存账户的 `created_at` **全都是同一秒** `1790855713`（19:55:13），id 连号
`acct-1790855713…-1` 到 `-5`。若只是删了 2 个账户，不会 5 个同秒重建、id 从
`-1` 重新连号。

⇒ 是 `email_accounts` 整表被 DROP 后由在跑的服务重新建表并重新导入。
`emails` 的 120 行则是 maildeploy 那个实例的调度器重新抓取的结果
（账户 3/5 的 `last_synced_at` = 22:18:02 / 22:19:02，即 18099 端口那个进程
此刻仍在抓取——它是唯一能解开 IMAP 凭据的实例）。

## 机制：PG 测试助手的 cleanup

仓库里当时已有一个这样的助手——`internal/server/server_auth_extended_test.go`
的 `mustTestPool` 原实现是「DSN 带了 `search_path` 就用它，否则才生成一次性
schema」，而 cleanup 会 `DROP SCHEMA … CASCADE`。于是
`POCKET_TEST_POSTGRES_DSN` 一旦带上生产 schema（本仓库的惯例是同一个 DSN
既喂服务也喂测试），跑一次测试就会在**报告 ok 的同时**把整个生产 schema
连表带数据删光。

紧邻事发时刻的那条查询也确实是测试形态：

```
19:45:06  SELECT 'email_accounts', count(*) FROM opencode_pocket.email_accounts
          WHERE user_id LIKE '%invalid.test%' OR workspace_id LIKE '%invalid.test%'
          UNION ALL … 'notes' …
```

该缺陷已在 `da4b5bb` 修复，并做了献祭 schema 对照实验：修复前跑一个用例输出
`ok` 而献祭 schema 与其中的 canary 表一并消失；修复后 PASS、献祭 schema 存活。

### 同步动作：只 checkout 一个文件，不动任何历史

```

```

这条命令的两个性质都已核实：

- **有效**：`origin/main` 上该文件已**无条件自生成** schema
  （`schema := fmt.Sprintf("c8_auth_test_%d", ...)`，不再读 DSN 的 search_path），
  且 DROP 前有前缀断言 `if !strings.HasPrefix(schema, "c8_auth_test_")`。
- **无风险**：逐个 worktree 跑 `git diff --numstat` 与
  `git diff --cached --numstat`，**6 个全部为空**——没有任何人在这些工作区里
  对该文件有真实的未提交改动。`wt-stt` 的 `git status` 曾把该文件标成 `M`，
  那是 stat-cache / 行尾（LF↔CRLF）造成的假象，`--numstat` 为空即证明无内容差异。
