# 2026-10-01 19:47:12 整个 schema 被 DROP：机制已确认，责任人无法从日志判定

日期：2026-10-02
对象：本地 PostgreSQL 的 `opencode_pocket` schema

## 现象

复查生产数据时发现邮件数据减少：`emails` 138 → 120，`email_accounts` 7 → 5。
一开始我按「被删了几条」查，方向就错了。

## 真实机制：整表被重建，不是被删了几行

幸存账户的 `created_at` **全都是同一秒** `1790855713`（19:55:13），id 连号
`acct-1790855713…-1` 到 `-5`。若只是删了 2 个账户，不会 5 个同秒重建、id 从
`-1` 重新连号。

⇒ 是 `email_accounts` 整表被 DROP 后由在跑的服务重新建表并重新导入。
`emails` 的 120 行则是 maildeploy 那个实例的调度器重新抓取的结果
（账户 3/5 的 `last_synced_at` = 22:18:02 / 22:19:02，即 18099 端口那个进程
此刻仍在抓取——它是唯一能解开 IMAP 凭据的实例）。

## PG 日志里的直接证据

`C:\workspace\openpocket\logs\pg\pg.err2.log` 未开启 `log_statement`，所以 DDL
本身查不到；但表消失的瞬间留下了痕迹——**同一时刻整个 schema 的表全部报错**：

```
19:47:12.325 ERROR: relation "email_accounts" does not exist
19:47:12.326 ERROR: relation "email_vacation_replies" does not exist
19:47:12.332 ERROR: relation "rss_sources" does not exist
19:47:12.359 ERROR: relation "scheduled_tasks" does not exist
19:47:12.459 ERROR: relation "tasks" does not exist
```

一次性丢掉 5 张互不相关的表，只可能是 `DROP SCHEMA … CASCADE`。
按分钟统计全天的同类报错，只有这一次级联：

```
2026-10-01 18:27  1
2026-10-01 18:29  1
2026-10-01 19:47  12
2026-10-01 19:48  14
```

**单次事件，不是反复发生。**

## 机制：PG 测试助手的 cleanup

仓库里当时已有一个这样的助手——`internal/server/server_auth_extended_test.go`
的 `mustTestPool` 原实现是「DSN 带了 `search_path` 就用它，否则才生成一次性
schema」，而 cleanup 会 `DROP SCHEMA … CASCADE`。于是
`POCKET_TEST_POSTGRES_DSN` 一旦带上生产 schema（本仓库的惯例是同一个 DSN
既喂服务也喂测试），跑一次测试就会在**报告 ok 的同时**把整个生产 schema
连表带数据删光。

紧邻事发时刻的那条查询也确实是测试形态：

```
19:45:06  SELECT 'email_accounts', count(*) FROM opencode_pocket.email_accounts
          WHERE user_id LIKE '%invalid.test%' OR workspace_id LIKE '%invalid.test%'
          UNION ALL … 'notes' …
```

该缺陷已在 `da4b5bb` 修复，并做了献祭 schema 对照实验：修复前跑一个用例输出
`ok` 而献祭 schema 与其中的 canary 表一并消失；修复后 PASS、献祭 schema 存活。

## 责任人：无法判定，如实记录

`log_statement` 未开启，PG 日志里没有发出 DROP 的连接信息，所以**不能证明
是哪一次 `go test` 造成的**。可以确定的只有机制与时刻。

我能确定的自己的相关行为：19:45:06 那条 `.invalid.test` 核对查询是我做的
（清理我自己留下的 `probe-auth@invalid.test` 探针账户），19:47:12 的 DROP 距它
两分钟。但那两步之间是否有一次 PG 测试运行，**日志里没有记录，我不据此下结论**。
同时段还有另一个会话在往生产 `emails` 表写 `mail-dirty-*` 约束探针数据
（19:40:28 与 19:46:53 各一批），说明当时确实有多个会话在动这个库。

这条记录的价值不在于追责，而在于：**「测试跑一下就删库」这条路径真实存在过，
且输出是 `ok`。** 任何一次拿生产 DSN 跑后端测试的尝试都要当成高危操作看待。
