## 一、第三次撤回：3 张「腾讯云发票」是自发自收的 E2E 注入

### 1.1 错在哪

round36 的结论链条是：

| 当时的推断 | 实际情况 |
|---|---|
| `file_source=attachment` ⇒ 附件来自邮件 | ✅ 对，但只说明**落盘**忠实 |
| 仓库里没有代码生成该文案 ⇒ 是上游生成的 | ❌ **不成立**：生成者不在仓库里，不代表生成者是腾讯云 |
| PDF 正文自称 `This is a system-generated e-invoice.` ⇒ 是上游的摘要页 | ❌ 这句话**谁都能写**，包括我们自己 |

我把「不是我们仓库的代码生成的」当成了「是供应商生成的」。这两者之间没有任何
逻辑关系 —— 那是**判据只覆盖了一种可能来源**的又一次实例（同「grep 不到 ≠ 不存在」
同族：判据只认「本仓库 vs 上游」二分，没考虑「本仓库之外的自造数据」）。

## 二、新增判据 0：台账引用的文件「不是真票面」的三种形态

`backend/internal/email/diag_invoice_handoff_integrity_test.go` 原来只查
「台账有·磁盘无 / 磁盘有·台账无 / 字节重复 / 日期打架」四类。
这四类**都假定台账里的行是真凭证** —— 而 1.2 证明这个假定不成立。
`classifyOrphanPDF` 明明能区分夹具，但它只查**无主**文件，永远看不到有主的那几张。

### 2.1 判据拆成三条（因为它们各自会失效）

| 判据 | 依据 | 失效形态 |
|---|---|---|
| **0a 自发自收** | `from_address = email_accounts.email_address`（纯 DB 事实） | 只认地址相等；若用别的方式自注入（如 SMTP 改 From）就漏 |
| **0b 夹具/退化件** | 复用 `classifyOrphanPDF`（会解压 Flate 流） | 只认 `IMAP fixture` / `Fixture Cloud` / `Demo Co` 三种字样 |
| **0c 摘要页** | 正文含 `system-generated` | **只认这一种英文写法**，改文案即完全漏判 |

**0c 我明确降级为「佐证，不单独作结论」**，理由写在函数注释里：
第一版把它当判据时，它的危害不是漏判而是**恒亮** —— 只要命中就报，
读日志的人会以为「抓到证据了」，而真正硬的 0a 反被这条弱判据盖住。

### 2.2 自检：判据自报的数必须和肉眼可数的事实对得上

第一版汇总行写的是 `自发自收 3 + 夹具 0 + 退化件 0 + 摘要页 3 = 6 行`，
**这是错的**：0a 与 0c 命中的是同一批 3 个文件，被数了两遍。
读者照着 6 去目录里核对会核不出来，从此不再信这条诊断。
已改为按文件去重：

```
[diag] 判据 0：自发自收 3 行 / 夹具 0 / 退化件 0 / 摘要页 3；按文件去重后实际待定性 **3** 个
[⚠ 口径] downloaded 行合计 4038.01；剔除自发自收的 513.40 后 = 3524.61；其中 invoice_date 为空的 0 行
```

### 2.3 负控（证明 0a 不是恒暗）

把谓词改成 `strings.EqualFold(c.fromAddr, c.mailbox) && false`，同一台设备、同一份真实数据：

| | 自发自收 | 口径合计 | 0c 摘要页 |
|---|---:|---:|---:|
| 正常 | **3** | 剔除后 3524.61 | 3 |
| 负控（0a 关掉） | **0** | 回到 4038.01 | 3 |

⇒ 0a 确实由那个谓词驱动；0c 独立成立（它没跟着归零），
两者命中同一批 3 个文件，所以去重后仍是 3 —— 与 2.2 的自检一致。

跑 `TestPGTestsNeverTargetTheProductionSchema` 时报红。第一件事是判定

```go

}
cfg.ConnConfig.RuntimeParams["search_path"] = schema
```

（`POCKET_DIAG_HANDOFF` 等十几个诊断都靠它）—— 两边一撞就是
**「谁带着真实 DSN 跑一次全量 `go test`，谁就在生产 `emails` 表插两行再删掉」**。

### 3.2 我做了什么 / 没做什么

**做了**：抽出 `upsertGuardSchema(t)`，缺省即 `t.Skip`、显式点名
`opencode_pocket` 即 `t.Fatalf`，并把它登记进 `pgAllowlistedWrites`
（它有写语句，按规则 4 不能进 `pgSafeWithoutIsolation`），理由写明
「缺省指向哪里、被哪几道开关挡住」。

**没做**：守卫的**规则 2 仍然判红**，因为该文件确实没有自建 `*_test_` schema。
修法要么让它自建隔离 schema（用 `pgscope_test.go` 的 `newScopedPool` +
跑迁移，会改变该测试「借真实 `email_accounts` 行解外键」的语义），
要么把理由写宽松让它变绿 —— 守卫自己的报错文本就写着
「**不要靠把 pgSafeWithoutIsolation 的理由写宽松来绕过——那是让冲突变沉默**」。
我选了不动：`internal/server` 目前**只有这一条红**，是真实信号，
留给该文件的作者收尾。

### 3.3 这不是新问题

`pgSafeWithoutIsolation` 里 20 多条登记理由都在反复写同一句话：
「写路径拒绝 schema 缺省值（缺省=生产库 `opencode_pocket`）」。
**本仓的默认失败模式就是「新写库路径把生产库当缺省值」**，这条登记是第 N 次。

## 八、00:5x：闭掉「A4 能不能剪裁」这个挂了好几轮的未验证项 —— **并发现真缺陷**

### 8.1 之前为什么判「查不了」

前几轮的理由是「要判墨迹就得栅格化，pdfcpu v0.11 没有渲染 API」。

**这个理由不成立。** 判墨迹不是必需的，判一个**充分条件**就行：

```
PDF 只有落在页面框（MediaBox/CropBox）内的内容才会被渲染/打印
⇒ 可见墨迹 ⊆ 页框
⇒ 只要每个票面的页框 ⊆ 它自己那一格，就必然不会跨格
```

于是问题变成「页框有没有出格」，而那只需要一个矩形包含判定。

而且 2×2 那两张还印到了纸外。

### 8.3 判据为什么不依赖「这是哪张票」

诊断不靠猜配对。判定式是：

```
该缩放下要装进 cellW，源页宽必须 ≤ cellW / a
2×2：297.640 / 0.55904 = 532.41pt，而目录里最宽的票是 595.28pt ⇒ 必然越界
3×3：198.427 / 0.37269 = 532.42pt，同上
```

⇒ 只要发票目录里**没有任何一张票**满足这个宽度约束，就判出格，
**与具体是哪张票无关**。这是它能当缺陷报告的唯一理由。

### 8.4 我自己把判据跑红了两次（都记在这里）

## 九、01:2x：8.2 那个「未定位」已经定位并修掉了

### 9.1 根因（精确到算术）

真实票面「交通-浙江高速公路智能收费运营服务有限公司-19.00-…pdf」的页面字典：

```
/MediaBox [0 0 594.96 841.92]
/CropBox  [34.7568 452.726 567.168 807.055]      ← 宽 532.4112
/SMask    24 0 R
/Rotate   0
```

pdfcpu 的 NUp **用 CropBox 算「这张票多大」，却按 MediaBox 尺寸把页摆进格子**：

```
fit       = 297.638 / 532.4112 = 0.559037    ← 产物里的 cm 正是 0.55904
实际页宽   = 0.559037 × 594.96 = 332.79  >  格子 297.64
越界      = 35.15pt = 12.4mm
```

`1.118 = MediaBox 宽 / CropBox 宽`。那个看起来莫名其妙的系数就是它。
全仓 Go 代码没有任何一处设置 CropBox —— 它来自**源票面文件本身**。

### 9.2 复现（诊断 `diag_nup_scale_repro_test.go`，门禁 `POCKET_DIAG_NUP_SCALE=1`）

| 输入 | 修前 | 修后 |
|---|---|---|
| 单张真实交通票过生产函数 | **a=0.55904**（越格 35.15pt） | a=0.49998 |
| 生产目录全部 9 张真实票面 | 出现 2 处 0.55904 | **0.49993–0.50000，出格 0** |
| gofpdf 造的同尺寸合成页 | 0.49998（正确） | 0.49998 |

⇒ **合成页永远复现不出来**：gofpdf 生成的页 CropBox == MediaBox。
这个缺陷只能靠真实票面暴露，任何「按尺寸构造的用例」都是假绿。

### 9.3 修法

归一化阶段对每张 PDF 把 CropBox 对齐到 MediaBox：

```go
api.CropFile(src, dst, nil, &model.Box{Inherited: true, RefBox: "Media"}, nil)
```

- 裁失败**回退用原文件** —— 宁可它仍可能越格，也不让用户的发票凭空消失；
- 裁完**复验页数不变**，页数变了说明裁坏，宁可回退也不能把「少了几页的发票」
  塞进 A4（那会让财务少看到票）；
- 取舍：票面外圈空白不再被裁掉，**票面在格子里会略小于裁掉时**。
  选它而不是「按内容裁」是因为后者一旦内容框算错就会切掉票面边缘。

### 9.4 两个自己踩的坑（都写进注释了）

1. **`api.CropFile` 的 box 传 nil 不是「按内容自动裁」，是 nil 解引用 panic**
   （pdfcpu v0.11 `model/box.go:1040`）。第一版就是这么写的，
   `recover` 兜住后回退原文件 ⇒ 导出结果与修前一模一样。
   形态极坏：**表现为「改了没反应」，而代码看上去完全合理**。
2. 复现诊断第一版在真实模式下忘了清空 `sizes`，`minSrcW` 用了合成页的 420
   而不是真实票面的 594.96 —— **判据的输入与被测对象不是同一批**，
   出格判定因此失真（真实数据那次它就漏报了）。

### 9.5 现状

`internal/email` 全量 14.3s 绿；gofmt 门禁真债 0。
**已修的是代码；那批已经生成的历史 A4 文件仍在磁盘上、内容不变**，
要不要重出由用户决定（重出需要 App 里点导出，或授权我调导出端点 ——
它有 admin 口令保护，我没有那个口令）。

## 十、剔除 3 行的操作**不持久** —— 删完下一轮会长回来

第九节之前我只做了「粘性检查」（重跑抽取逻辑看会不会重建），
当时结论是「若那 3 封邮件被重新处理，行会按同样金额重建」。
本节把它从「会不会」变成「一定会，且窗口很长」。

### 10.1 先核一遍：库里没有第 4 张自注入票

自发自收邮件 13 封，其中带附件的 QQ Wallet 只有 3 封，与台账 3 行 1:1 对应：

| email_id 后缀 | 收信时间(UTC+8) | has_attachments | 死信 | 对应发票行 |
|---|---|---|---|---|
| `ZL0007_FRTNZ46M7rAuaWoAsYyR010` | 2026-09-07 08:18:31 | t | 否 | `inv_1791011450357733400_3` 58.90 |
| `ZL0007_Z2bNm3KM7bMuaWoAWMVN310` | 2026-10-02 16:10:44 | t | 否 | `inv_1790957532670968300_1` 126.00 |
| `ZL0007_nJ3NZ46M7rAuaWoAgoE1610` | 2026-10-02 16:10:44 | t | 否 | `inv_1790957532673098600_2` 328.50 |

其余 10 封自发自收是验证码 / SMTP 配置测试 / `[urgent-e2e]` 两封告警，
都不带附件、不进台账。⇒ 剔除对象就是这 3 行，**没有遗漏的第 4 张**。

### 10.2 为什么删了会长回来（三条代码事实）

第 1.5 步「发票候选扫描」是**每轮定时重跑**的增量扫描，不是只在收信时跑一次：

1. `pipeline.go:534` `lookbackSince = rep.StartedAt - 90*86400`
   （`invoiceCandidateLookbackDays = 90`，`pipeline.go:780`）
   ⇒ 回看窗口 **90 天**。这 3 封是 2～27 天前的邮件，**整段都在窗口内**。
2. `pipeline.go:596` 幂等跳过的前提是**行还在**：
   `if _, err := p.Store.GetInvoiceByEmailID(ctx, e.ID); err == nil { continue }`
   ⇒ 删掉行 = 跳过条件不再成立 = 这封邮件重新进入判定链。
3. `pipeline.go:599` `ExtractInvoice(e, "")` 对 envelope 判定：主题
   `[QQ Wallet] Electronic Invoice Issuance Notice` 含 invoice 关键词 ⇒ 命中；
   随后 `pipeline.go:688` `ExtractInvoiceLoose` 拿正文里的附件解析出金额，
   `pipeline.go:710` `UpsertInvoice` 按**同样金额**重建行。

⇒ **单纯删行是无效修复**：下一轮（明天 08:00）就会原样长回 513.40，
口径又会从 3524.61 弹回 4038.01。窗口要到 2026-12-06 前后才自然消失。

### 10.3 闸必须放在「账号已解析」那一层

`ExtractInvoiceLoose` 里现成的 `admitDebtNotice`（`invoice.go:450`，
被 `invoice.go:669` 调用）拿到的只是 `joined` 文本 + `hasInvoiceAttachment`，
**拿不到账号自身地址** ⇒ 自发自收这道闸加不进它里面。
可用的拦截点是 `pipeline.go:583` 的循环：那里 `e.AccountID`、`e.FromAddress`
与 `accounts` 表里的 `email_address` 同时在手（`accounts` 在 `pipeline.go:557-562`
刚遍历过），比对 `FromAddress == email_address`（不区分大小写、去空白）即可。

### 10.4 这是财务语义，不代决

「自发自收今后彻底不入账」与「入账但标记、合计排除」是两种不同的账务口径，
且自发自收里**可能混有真实情形**（用户把外部发票转发给自己留存）。
叠加 10.2 的结论，剔除授权这个待拍板项的选项变了：

- 只删行 → 无效（会再长回来），**不能选**；
- 删行 + 加闸 → 闸的宽严仍需用户定，且是长期行为；
- 先加「标记后合计排除」→ 口径立刻干净，行还留着可追溯。

**未获授权前不动库。** 10.1 的 3 行 / 10.2 的三条代码位置均已实测，
排除项已列全（未被否掉的方案：见 10.4 末三项）。

## 十一、「墨迹越界未验证」这条尾巴：结论**未定**，而且我原先的说法要收回

第九节留的尾巴是「页框已证出格，墨迹是否也真的越过去仍未判定，
需栅格化」。本节把工具做出来了（不需要栅格化），但**没有拿到可用结论**，
而且顺带查出第九节的一句话站不住。

### 11.1 栅格化从来不是必需的

本机实测无 mutool / pdftoppm / gs / magick / PyMuPDF（2026-10-04）。
但墨迹位置**可以从内容流算出来**：解析算子、维护 CTM 栈与文本矩阵、
把每次绘制变换到 A4 页空间。落地为两个文件：

- `backend/internal/email/diag_a4_ink_support_test.go`（内容流解释器）
- `backend/internal/email/diag_a4_ink_overflow_test.go`（判据 + 负控）

门禁 `POCKET_DIAG_A4_INK=1` + `POCKET_DIAG_EXPORT_DIR`（真实 exports 目录）。

### 11.2 一条定理，改变了这个判据的定位

form XObject 的内容按 `/BBox` 裁剪（PDF 32000-1 8.10.1），所以

    可见墨迹 ⊆ 页框  ⇒  页框不出格 ⇒ 墨迹必不出格

⇒ **墨迹判据不可能发现页框判据发现不了的越界**。它的唯一价值是**降级**：
把「页框出格」里那些其实只是票面白边的格子挑出来。

我第一版的负控是「页框在格内、墨迹越界」——**那是不可能存在的形态**，
被裁剪逻辑打回。**判据是对的，用例是假的。**

不裁剪的后果实测过：交通票面内容流里有
`118.75 118.75 2243.95 3272.02 re`（坐标远大于 841.92 高的页框），
不裁就报「墨迹越界 1284pt」——而那部分**根本不会印出来**。

### 11.3 判据自证：13 条变异全部转红

负控 7 条（几何组 4 + 文字组 3），另跑 13 条变异逐一确认判据不是摆设：
hScale 归零、CTM×文本矩阵顺序反转、`/FirstChar` 被忽略、form 判据查
`/Type` 而非 `/Subtype`、不记录墨迹、越界深度恒 0、外扩系数归 0、
忽略 `/Matrix`、不递归 form、不 Decode 内容流、归格写死第 0 格、
以及**吞掉任一条负控**。全部转红。

过程中判据自己有 4 个真 bug（不是用例的问题）：
① 零值 `inkRect{0,0,0,0}` 的 `valid()` 为 true ⇒ 墨迹盒子恒为空，
   「未越界」是假的（改用反向哨兵 `inkEmpty()`）；
② form 的标志在 `/Subtype` 而非 `/Type`；
③ `DereferenceStreamDict` 不保证 `Content` 已解码，不显式 `Decode()`
   会让内层流是空的；
④ 文本矩阵与 CTM 相乘顺序反了（PDF 是行向量约定），且 `Tm` 已把
   `tlm` 同步成 `tm`，再乘一次等于平移加两遍。

### 11.4 一个会让「0 越界」彻底无意义的存储缺陷

判定原本写进**格子表**（一格一条）。同一格里有多个放置时后者覆盖前者，
于是 3x3 那份里的 Fm4/Fm5 被静默吞掉。改成**逐个放置一条判定**后，
同样的 20 个文件，统计到的放置数从 **39 → 116**。

> 「少算了几条」与「一条都没越界」在输出上完全一样。

### 11.5 真数据上的结论：**有 4 张票的墨迹真的越过了裁切线**

先修判据的一个归组错误：pdfcpu NUp 把一张票整体放成**一个顶层 form**，
而票面内部还有**嵌套 form**（背景条、表格线、文字块）。实测一页 A4 上
顶层只有 4 个放置，嵌套碎片却有 21 个。按碎片各自归格会得到一堆 y 为负、
归不到任何格子的小框（一度报出 116 处放置 / 14 处出格 / 6 处无法归格）。

改成**按顶层放置归组**后，同一批 20 个文件：

    38 处放置（= 一张票一个被测对象），出格 4，无法归格 0

`38 次放置 / 出格 4` 与既有 `diag_a4_cell_fit_test.go` 的读数**完全一致**。

4 处越界明细（页框越界深度与墨迹越界深度**逐条相等**）：

| 文件 | 格子 | 越界 | 页面内容流里写着 |
|---|---|---|---|
| `invoices-a4-2x2-20261003-161137.225387500.pdf` p1 | (1,0) | **88.20pt ≈ 31.1mm** | `q 0.55904 0 0 0.55904 297.64 111.43 cm /Fm4 Do Q` |
| 同上 p2 | (0,1) | **88.20pt** | `q 0.55904 0 0 0.55904 0 532.375 cm /Fm5 Do Q` |
| `invoices-a4-3x3-20261003-161137.304896000.pdf` p1 | (0,0) | **21.80pt ≈ 7.7mm** | 帧宽正好等于格宽 198.42，但整体左移 21.80pt（x0 为负） |
| 同上 p1 | (1,0) | **21.80pt** | 同上 |

⇒ **这 4 处沿格线剪裁会切到邻格的票面**，不是「页框出格但只是白边」。
`ink` 深度恰好等于 `frame` 深度，说明票面内容铺满了页框边界。

**两个不同形态**：0.55904 是**缩放**错（第九节那根因）；
21.80pt 是**整体平移**错（帧宽对、位置偏）。两者的共同特征都是
「form 的 /BBox 原点 ≠ 页原点」——第九节的 `cropPDFToContentBox`
把 BBox 归一成 `[0 0 W H]`，**推测**能同时消掉两个形态。
**未验证**：需要重出后重跑本诊断才能确认。

### 11.6 与 cell_fit 的数字差异不是矛盾

cell_fit 报 23.43pt，本判据报 21.80 / 88.20pt。原因：cell_fit 在
「候选票面无法配对」时（真实目录里 7 张 A4 尺寸票彼此无法区分）用
**目录里最宽的票**反推一个上界；本判据量的是**实际 BBox**。
**「哪几处、多少处」两者完全一致**（38 / 4），差的是「多大」的取数口径。

### 11.7 字宽：改成上界，而不是「未知」

产物里 pdfcpu 把票面的 CJK **Type0/Identity-H** 字体换成了
**Type1 / WinAnsiEncoding / 无 `/Widths`** 的子集（`/BaseFont` 是
标准 14 的 `Helvetica` / `Helvetica-Bold`）。`pdfcpu` 的内置宽度表在
`internal/corefont/metrics` 里，**导不出来**。

但**精确宽度在这里并不需要**：判据问的是「有没有越过裁切线」，
把宽度算大只会让墨迹盒变大 ⇒ 可能**误报**，绝不会**漏报**。
所以对解析不出精确字宽的绘制，改用**每码位 1 em** 的上界
（前提：标准 14 字体任何字形宽度 ≤ 1 em；这是本判据唯一的字体假设，
写在 `inkFont.boundPerCode` 字段注释上）。真数据 618 次绘制走这条路。

⇒ 11.5 的结论**不依赖**这个上界：那 4 处的墨迹深度等于页框深度，

## 三十七、A4 是**手动**产物：08:00 若新增发票，现有 A4 立刻过时

### 37.1 查实：A4 不在定时流水线里

全仓 `ExportInvoiceGrid(Detailed)` 的调用方只有：

- `internal/email/export_pdf.go` 自身（包一层）
- 大量 `_test.go`（诊断与单测）
- **`handleEmailInvoiceExport`** —— `POST /api/emails/invoices/export`

流水线 `Pipeline.Run` 的步骤里**没有 A4**。它生成的是
`BuildInvoiceSummaryDocs` 的 MD/CSV（`invoices-summary-*.md|csv`），
A4 网格 PDF 只能由人在界面上点导出。

⇒ 路由清单（`server_email_pipeline.go:5-11`）也印证这一点：
summary 是 `GET` 一行说明，export 是 `POST` 带 `{ids,grid}`。

### 37.2 为什么这一条现在重要

第 1.5 步的积压里还有 **16 封**待拉 IMAP 原文的邮件，
预算 `maxInvoiceBodyFetches=24/轮` ⇒ **08:00 那一轮一轮就能清完**。
其中有几封**有可能**是真发票：

- `invoice+statements+acct_…`「Your receipt from X #2662-4636-8457」
- `noreply@github.com`「[GitHub] Payment Receipt for halfking」

而信用卡电子账单（平安/招商）会被 `admitDebtNotice` 拒掉
（`f20ed001` 已在运行二进制里），小米扣款通知之类也没有发票语义。

⇒ **台账行数在 08:00 之后可能不再是 7 行。** 若真的新增了票：

1. 汇总 MD/CSV 会自动重出（**表头仍是「文件」**——见第三十四节，旧二进制）
2. **A4 不会自动重出** ⇒ 盘面上 `invoices-a4-*-20261003-161137.*`
   那对（已验证正确的 6 张）就**只覆盖到 08:00 之前**，需要手动重出

### 37.3 复核时怎么判「有没有新增」

不要只看行数变没变，按顺序：

1. 读 `email_invoices` 的 `created_at`，看有没有**今天 08:00 之后**的行；
2. 有新增就跑一次金额溯源诊断（门控 `POCKET_DIAG_AMOUNT_PROV=1`
   + 显式 DSN/SCHEMA/DATA_DIR），确认新行的金额能回到来源、
   且**没有**「信用额度/应还款」这类语义告警；
3. 有新增且溯源通过 ⇒ 提醒用户「A4 需要在界面重出一次」。

**别把「A4 没跟着变」当成缺陷**——它是手动产物，本就不自动更新。
