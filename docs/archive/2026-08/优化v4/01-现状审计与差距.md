# 优化 v4：现状审计与差距

> **范围与边界**：本文只描述当前仓库可由代码、迁移、测试及既有审计记录支持的事实，并提出下一阶段方案。不宣称任何问题已经因本文得到修复；不执行凭据轮换、历史清理或源码改动。
>
> **证据标记**：
> - **现状事实**：可直接由当前 `HEAD` 或既有审计报告确认。
> - **推断建议**：基于事实提出的目标设计或实施动作。
> - **待验证**：需要真实环境、集成测试、威胁建模或产品决策确认。

## 1. 结论摘要

当前产品已经形成“移动端个人助理 + Pocket 控制面 + OpenCode/Agent/Plugin 执行面”的雏形，但仍是**两套数据与执行语义并存**：

1. **本地优先轨**：前端 Capacitor SQLite/SQLCipher 承载笔记、邮件、密码箱、会议、聊天及新 Asset；本地 schema 以 `workspace_id`、软删除、字段/Blob 加密和 FTS 为主。
2. **云端控制轨**：Go `pocketd` 通过 PostgreSQL 保存任务、身份、邮件配置、审计、Agent、Vault/Asset 加密镜像，并代理 OpenCode、LLM、RedClaw、OAuth、SMTP、SSE/WS。
3. **执行轨**：OpenCode 实例由 Registry 路由；Agent Bridge 创建 session 并发送 prompt；Plugin Hub 负责 WS 命令；迁移服务把源 session 重建并异步下发到目标实例。

核心优点是模块已经有明确的隔离意识、真实 JWT、路由认证、Asset 密文镜像、事件流 workspace 复合键、请求体/出站 URL 基础防护，以及多轮真实 PostgreSQL/IMAP 验证记录。核心断点是：统一模型尚未覆盖旧业务；JWT 的 workspace claim、成员资格和实例归属还未成为所有路径的强制不变量；前端 token 与 SSE/WS query token 存在泄露面；离线队列仍是内存级消息队列；Asset/CAS/冲突恢复尚未形成完整可证明协议；审计记录未覆盖每个敏感 Action 的统一链路。

## 3. 前后端双轨与关键断点

### 3.1 本地优先轨

**现状事实**：`frontend/src/native/local-db.ts:12-91` 将本地 DB 封装为单例，`DB_VERSION = 2`，通过 `setEncryptionSecret`/`secret` 模式打开 SQLCipher，并以 `local_schema_migrations` 记录迁移。`frontend/src/native/schema.ts:13-350` 定义了旧业务表和 `local_assets`、`local_asset_blobs`、`local_asset_vectors`。Asset 默认 `e2ee_local_first`，有 `client_rev/server_rev/dirty/deleted_at`（`frontend/src/native/schema.ts:268-349`）。

**关键优点**：数据可离线使用；软删除墓碑便于同步恢复；敏感 body/blob 可 AES-GCM；workspace 及 FTS 索引位置已有明确约束。

**断点**：`local_assets` 的 `get()`/`softDelete()` 是按 id 的便利 API，而 scoped 版本才带 workspace（`frontend/src/native/asset-store.ts:156-191`）；`listDirty()` 未显式 workspace 过滤（`264-273`）；因此 workspace 切换、跨账户本地缓存和同步编排必须由上层严格包住。旧表 `local_vault_entries` 甚至没有 workspace 字段（`schema.ts:171-183`），不能假设本地全库天然具备租户隔离。

### 3.2 云端控制轨

**现状事实**：`backend/internal/server/server.go:337-491` 集中注册认证、业务、OpenCode、Agent、迁移、Gateway、SSE、Plugin、RedClaw、Audit 路由；请求体大小、恢复、日志、CORS、安全头、长连接 middleware 组合在同一 Handler。PostgreSQL stores 通过模块自带 `CREATE TABLE IF NOT EXISTS`/`ALTER TABLE` 迁移，例见 `backend/internal/lobster/store.go:54-93` 与 `backend/internal/vault/store.go:22-64`。

**关键优点**：路由集中、认证入口统一、数据库作用域逐步显式化、出站 HTTP 已有防 SSRF 基线。

**断点**：模块自迁移难以统一排序、回滚和灰度；handler 直接编排多个 store/上游，跨模块事务及事件写入不一致；部分兼容 fallback（`default` workspace、`userID=local`）容易掩盖认证缺口（`backend/internal/server/server_assistant.go:71-77`）。

### 3.3 双轨交界

1. **事实**：Vault 旧同步接口是按 workspace/user 保存多版本密文（`backend/internal/vault/store.go:30-177`），Asset 镜像另有 `asset_mirrors`/`asset_sync_log`（`backend/internal/lobster/store.go:66-93`）；二者不是同一协议。
2. **事实**：前端通用 WS hub 只在内存保存 `offlineQueue`（`frontend/src/services/websocket-hub.ts:28-37,107-116`），而 Asset dirty 列表在 SQLite；两种“离线”语义并不等价。
3. **建议**：将本地变更、服务端变更、执行命令和实时通知都收敛到统一 `Event`/`Action`/`Run` 协议；UI 只订阅投影，不直接依赖某条 WS 消息一定送达。
4. **待验证**：真实断网、进程杀死、重复提交、时钟漂移、workspace 切换中断同步时，是否会产生脏数据、重复执行或错误归属。

## 4. 差距地图

| 差距 | 影响 | 优先级 | 依赖 |
|---|---|---:|---|
| 作用域未成为所有实例/session/迁移/插件路径的不变量 | 跨 workspace 读取、控制或凭据串用 | P0 | Identity、Registry、统一 policy |
| query token 出现在 WS/SSE URL，且前端 token 持久于 localStorage | 代理/浏览器历史/日志泄露后可重放 | P0 | Cookie/BFF、WS ticket、日志脱敏 |
| tracked secret/二进制/备份文件仍在 Git 跟踪集合中 | 历史克隆者可取得密钥或可执行产物 | P0 | 取证、密钥轮换决策、Git 历史治理 |
| Action 没有统一审批、幂等和审计 | 高风险工具/迁移/发信难以追责和恢复 | P1 | Action/Approval/Event 模型 |
| Asset 只有部分 CAS 意义，服务端 Push 可接受旧版本并覆盖 | 多设备并发可能丢改动 | P1 | CAS、版本保留、冲突 UX |
| 离线队列仅内存，且 WS 消息可重复/无效载荷 | 重启丢任务、重连重复执行 | P1 | SQLite outbox、幂等键、回执 |
| 成员 expiry 未 enforced | 撤销成员可继续使用 JWT 至过期 | P1 | 每请求 membership check 或 token epoch |
| OAuth/SMTP/IMAP 尚有真实外部链路未验证 | 绑定/抓取/发信失败或凭据越界 | P1 | 沙盒邮箱、provider contract test |
| 迁移、审批、Audit、通知各有独立语义 | 无法端到端回放 | P2 | 统一 Event store、关联 ID |
| 旧业务表向 Asset 迁移未完成 | 加密、同步、检索和删除策略重复 | P2 | 数据字典、双写/回填、回滚 |

## 5. 优化 v4 目标架构

1. **唯一作用域上下文**：请求/任务/事件/本地命令均携带 `user_id`、`workspace_id`、可选 `session_id`、`agent_id`、`plugin_id`；服务端禁止从 body/header 覆写认证 claims。
2. **统一执行生命周期**：`Task` 描述业务目标，`Run` 描述一次执行，`Action` 描述意图，`Approval` 描述授权，`Event` 描述不可变事实，`Audit` 描述合规记录。
3. **资产与执行分离**：`Asset` 存内容/附件/向量；`Task/Run/Event` 存控制和过程；通过引用关联而不是把 prompt/密文散落在多个表。
4. **默认拒绝出端**：只有具备 capability 且满足 data-classification policy 的字段可发送到 IMAP/SMTP/OAuth provider/LLM/OpenCode/插件；默认发送摘要或脱敏片段，不发送 Vault 明文。
5. **可恢复同步**：本地 SQLite outbox + 服务端 Event/Asset CAS；每次 push/pull/Action 都有 idempotency key、server cursor、重试上限和死信/人工恢复入口。

## 6. 分阶段路线、依赖与验收

### P0（上线阻断）

- 先完成 Git 跟踪敏感文件的取证与阻断；**不得在本方案执行轮换或历史清理**。
- 收紧 WS/SSE 凭据：普通 HTTP 只接受 Authorization；实时通道使用一次性短期 ticket 或 HttpOnly SameSite cookie；移除 URL 中长寿命 token。
- 形成 `ScopeContext`/`Policy`，覆盖实例、session、agent、plugin、migration、asset、audit；所有跨对象查询必须带 workspace 条件。
- P0 验收：跨 workspace 的 GET/POST/dispatch/migrate/plugin command 全部返回不可区分的 404/403；token 不出现在访问日志/代理日志/浏览器历史；安全回归测试覆盖每条入口。

### P1（可运营性）

- 落地统一模型、Action/Approval/Event/Audit 关联；高风险动作（发信、迁移、插件命令、shell/tool、凭据变更）默认 pending approval。
- 把 WS 内存队列迁为本地 outbox；实现指数退避、幂等 key、服务端回执、死信和用户可见恢复。
- Asset/Task/Run 使用 CAS；服务端拒绝 `base_server_rev` 不匹配的写入，保留冲突版本；完成成员有效期、OAuth provider、IMAP/SMTP 沙盒测试。
- P1 验收：杀进程/断网/重复请求不产生重复副作用；冲突可展示、选择版本、恢复并留 Audit；所有 Action 可按 correlation id 回放。

### P2（收敛与演进）

- 旧 notes/emails/meetings/vault 逐类适配到 Asset，保留可回滚双读，不直接删除旧表。
- 统一通知、SSE/WS 投影和可观测性；迁移服务增加 resumable pack、目标能力校验、补偿和回滚。
- P2 验收：新旧数据迁移抽样可逆；同一事件在列表、通知、SSE、审计中关联一致；关键指标和保留策略可查询。

## 7. 全局验收标准

- **作用域**：每个持久化实体均有明确 owner/workspace 组合键或明确的系统级归属；未带作用域的内部 API 只允许在启动装配层调用。
- **安全**：P0/P1 风险有测试、日志和运行时告警；敏感值不进普通日志、URL、错误响应或前端调试输出。
- **一致性**：每次修改都有 client/base/server revision；CAS 失败不静默覆盖；删除墓碑在同步完成前保留。
- **可恢复**：网络失败、进程重启、上游超时、审批过期、目标实例离线均有明确状态、重试和人工恢复。
- **可审计**：可按 `workspace_id + actor + action + resource + correlation_id` 查询，审计记录本身不可由普通成员删除或改写。
- **不变量验证**：CI 必须真实执行 PostgreSQL/实时通道集成测试，不能因 DSN 缺失静默 skip；既有审计已记录该类误报风险（`docs/audits/2026-08-09-email-pipeline-audit.md:212-225`）。
