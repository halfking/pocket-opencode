# 07 AI 编排与智能体控制面

**版本**：优化 v4（方案）
**范围**：AI 运行、typed action registry、审批中心、OpenCode/ACP/ACC connector、统一状态机、API/事件和安全验收。

> 本文是控制面专项设计。产品入口和核心流程见 `docs/优化v4/03-产品蓝图与信息架构.md`；目标分层、领域边界、数据所有权和兼容策略见 `docs/优化v4/04-目标架构与领域拆分.md`。

## 1. 目标与边界

### 1.1 目标

把“用户一句话 → LLM 输出 → 某个系统发生副作用”拆成可观察、可暂停、可审批、可重试的控制链：

```text
Capture / UI
  → Intent
  → Plan
  → Typed Action
  → Policy decision
  → Dry-run / Approval
  → Connector execution
  → Run events
  → Read model / Audit
```

控制面不训练、不运行编程 agent，不直接替代 OpenCode、ACP 或 ACC。它做四件事：

1. 规范化用户意图与模型输出，拒绝自由格式工具调用。
2. 以 user/device/workspace 为边界执行授权、能力、风险、配额和幂等检查。
3. 把 OpenCode、ACP、ACC、邮件、账本和 Asset 同等视为受限 connector。
4. 用 Run、Approval、Question、Event 和 Audit 让移动端看到真实状态。

### 1.2 事实边界

- `backend/internal/agent.AgentAdapter` 已定义会话、prompt、事件等统一接口；`PermissionCapable` 和 `QuestionCapable` 是可选接口。
- `backend/internal/agentbridge/bridge.go` 当前是单 agent dispatch：resolve agent/instance、create session、send prompt、可选 attach task；多 agent DAG 仍是后续能力。
- `backend/internal/opencode/permission_manager.go` 和 `question_manager.go` 已有事件优先、轮询兜底的待处理请求管理。
- `backend/internal/websocket/mobile_hub.go` 已把 permission/question/session 事件发给移动端，但控制面仍需统一 read model、事件游标和审批策略。
- OpenCode 官方资料确认终端、桌面和 IDE 形态；本方案不称 Pocket 是官方 OpenCode 移动端。
- OpenAI Codex 官方资料确认 CLI、IDE、桌面和云端形态；本方案不声称存在官方独立 Codex 移动端或手机审批能力。Pocket 手机审批只控制已通过本后端 connector 接入、且 capability 可验证的目标。
- ACP 官方资料确认编辑器/IDE 与 agent 的角色和本地 stdio transport；远程 HTTP/WebSocket 需握手和能力探测，不能按“ACP”名称直接假设可用。

```text
       │ Read models  │ │ Event/outbox  │ │ Usage/limits  │
       │ Today/Runs   │ │ cursor/replay │ │ llmbff record │

               │                │               │
┌──────────────▼────────────────▼───────────────▼───────────────┐
│ Connector runtime                                               │
│ OpenCode HTTP · ACP stdio/HTTP/WS · ACC MCP/HTTP               │
│ Email OAuth/IMAP/SMTP · Asset sync · LLM BFF · RedClaw/kxmemory │
└──────────────┬────────────────┬─────────────────┬──────────────┘
               │                │                 │
        registry/health   target protocols   credentials in backend
```

### 2.1 绝对约束

- LLM 只返回 `Intent`、`ActionProposal` 或结构化参数，不返回可直接执行的 shell/HTTP/SQL。
- 客户端传入的 `connector`、`target`、`workspace_id`、`approval_id` 都是未信任输入。
- connector 不得从请求体自行拼接任意目标 URL；OpenCode 目标必须经 `registry.Registry` 解析，ACC 目标必须经 connector 配置解析。
- approval 的决定只在后端写入成功后生效；前端的“已批准”状态不具有授权效力。
- 每个副作用 action 必须可 dry-run，或明确声明“不可预览”的原因并提高风险等级。

## 3. 核心对象

### 3.1 Intent

用户或系统想完成的目标，非执行命令：

```json
{
  "intent_id": "intent_01J...",
  "kind": "meeting.extract_tasks",
  "source": {"type": "meeting", "id": "mtg_..."},
  "request_text": "把决定变成任务",
  "workspace_id": "ws_...",
  "created_by": "user",
  "confidence": 0.88
}
```

Intent 可以失败、需要澄清或生成多个 ActionProposal；不能因为 confidence 高就跳过 policy/approval。

### 3.2 Action

Action 是版本化、可验证、可审计的执行意图：

```json
{
  "action_id": "action_01J...",
  "type": "agent.prompt",
  "version": 1,
  "workspace_id": "ws_...",
  "input": {},
  "source": {"type": "intent", "id": "intent_..."},
  "risk": "high",
  "mode": "dry_run",
  "state": "queued",
  "idempotency_key": "idem_..."
}
```

Action 与 Run 的区别：Action 是“做什么”；Run 是“这次尝试怎么运行、产生了哪些事件、最终结果”。重试可以产生新的 Run，但必须关联同一个 action 和 retry policy。

### 3.3 Approval

Approval 是针对一个 action payload hash、目标和权限范围的一次性授权：

```json
{
  "approval_id": "apr_01J...",
  "action_id": "action_...",
  "scope": {
    "workspace_id": "ws_...",
    "connector": "opencode",
    "target_ref": "inst_...",
    "capabilities": ["session.prompt", "file.write"]
  },
  "payload_hash": "sha256:...",
  "risk": "high",
  "reason": "将向远程项目写入文件并运行测试",
  "expires_at": "2026-08-14T10:35:00Z",
  "state": "pending"
}
```

修改收件人、目录、文件 glob、命令参数、Vault 字段或 ACC external ID 都会改变 `payload_hash`，必须重新审批。

### 3.4 Run

```json
{
  "run_id": "run_01J...",
  "action_id": "action_...",
  "connector": "opencode-http",
  "target_ref": "inst_...",
  "state": "waiting_approval",
  "attempt": 1,
  "started_at": null,
  "last_event_cursor": "cur_...",
  "result_ref": null,
  "error": null
}
```

Run 保存摘要和引用，不默认保存完整敏感 payload；原始内容按领域数据策略落在 Asset/业务 store。

### 3.5 Question

Question 是 connector/agent 需要用户提供信息才能继续的结构化请求，与 Approval 不同：

- Approval：用户授权已经确定的副作用。
- Question：目标需要用户选择/填写参数或澄清意图。

OpenCode `question.asked` 映射为 Question；用户回答后继续同一 Run，但回答内容仍需按 workspace policy 脱敏和审计。

## 4. 状态机所有权与 UI 映射

四类对象分别持有状态，禁止以任一对象的状态替代另一对象：

| 对象 | 状态所有权 | 关键语义 | UI 聚合规则 |
|---|---|---|---|
| Action | 计划与政策服务 | 做什么、是否可进入执行 | `approved` 只表示 Action 可排队，不表示执行成功 |
| Run | 执行器/connector | 某次尝试的实际生命周期 | Today/Session 的运行状态以 Run 为权威 |
| Approval | 审批服务 | 对固定 payload hash 的一次性授权 | `approved` 只会推动 Action/Run 继续；不等同 `succeeded` |
| Question | connector/read model | 等待用户补充的结构化信息 | 被回答后恢复同一 Run，不能当作 Approval |

移动端的 `session.waiting_user` 只是聚合状态：Run 为 `waiting_approval` 时显示“等你授权”，Run 为 `waiting_question` 时显示“等你回答”；页面必须同时保留具体 Approval 或 Question 引用。前端只消费服务端状态事件，不能用本地 PATCH 直接写成功状态。

### 4.1 Action 状态

```text
created
  └→ validated
       ├→ rejected_policy
       ├→ needs_clarification
       ├→ dry_run_ready
       │    ├→ waiting_approval
       │    │    ├→ approved
       │    │    ├→ rejected
       │    │    └→ expired
       │    └→ queued
       └→ queued

queued → running → succeeded
             │  ├→ failed
             │  ├→ cancelled
             │  ├→ waiting_approval → running
             │  └→ waiting_question → running
```

### 4.2 Action 状态转换规则

| 当前 | 事件 | 下一个 | 必须条件 |
|---|---|---|---|
| `created` | `action.validated` | `validated` | schema、scope、预算通过。 |
| `validated` | `policy.denied` | `rejected_policy` | 记录 policy rule 和 reason。 |
| `validated` | `dry_run.completed` | `dry_run_ready` | payload hash 固定。 |
| `dry_run_ready` | `approval.created` | `waiting_approval` | action 风险需要审批。 |
| `waiting_approval` | `approval.approved` | `queued` | hash、scope、expiry、actor 全匹配。 |
| `waiting_approval` | `approval.rejected/expired` | `rejected/expired` | connector 不得被调用。 |
| `queued` | `run.started` | `running` | 幂等锁成功、connector health 可用。 |
| `running` | `question.asked` | `waiting_question` | Question 属于同一 run/target。 |
| `waiting_question` | `question.answered` | `running` | 回答 schema 与 expiry 通过。 |
| `running` | `run.succeeded` | `succeeded` | connector 返回可验证结果。 |
| `running` | `run.failed` | `failed` | 分类 retryable/permanent。 |
| `queued/running` | `run.cancelled` | `cancelled` | connector 支持 interrupt 或明确取消未送达。 |

状态机存储层必须拒绝非法跃迁；前端只能根据事件渲染，不能通过 PATCH 直接把状态改成 `approved/succeeded`。

### 4.3 Run、Approval 与 Question 的最小状态

```text
Run:       queued → running → succeeded | failed | cancelled | indeterminate
                         ├→ waiting_approval → running
                         └→ waiting_question → running
Approval:  pending → submitting → approved | rejected | expired | failed
Question:  pending → submitting → answered | expired | failed
```

Action 在 `waiting_approval` 时只记录“等待授权”；Run 可以尚未创建，或在 connector 已受理后等待补充授权。实现阶段必须在 E0-S1 的状态转移表中选定其中一种，并明确事件与持久化边界，不能混用两种含义。

### 4.4 重试策略

- schema/policy/ownership 错误：不可重试，要求修改 action。
- connector timeout/暂时不可达：指数退避，受 `max_attempts` 和 action TTL 限制。
- 远程执行结果未知：进入 `indeterminate`（目标可能已执行），禁止盲目重试；先 query external operation/status。
- approval 过期：新建 approval 或重新 dry-run，不复用旧 token。
- 事件重复：按 `event_id` 去重；Run 结果按 connector `operation_id` 去重。

## 5. Typed Action Registry

### 5.1 Registry 契约

每个 action type 是后端注册的不可变 schema/handler 组合：

```go
type ActionDefinition struct {
    Type               string
    Version            int
    InputSchema        []byte
    Risk               RiskLevel
    RequiredCapabilities []string
    RequiresApproval   ApprovalMode
    SupportsDryRun     bool
    IdempotencyScope   string
    MaxRuntime         time.Duration
    Handler            ActionHandler
}

type ActionHandler interface {
    Validate(ctx context.Context, in ActionContext, input json.RawMessage) error
    DryRun(ctx context.Context, in ActionContext, input json.RawMessage) (*Preview, error)
    Execute(ctx context.Context, in ActionContext, input json.RawMessage) (*ExecutionResult, error)
    Cancel(ctx context.Context, in ActionContext, operationID string) error
}
```

实现应位于新的 control-plane package，先在 `backend/internal/server/` 以 facade 接入；不把 handler 逻辑塞进 LLM client 或前端 store。

### 5.2 最小 action 清单

| Action type | 用途 | 风险 | 默认审批 |
|---|---|---:|---:|
| `note.create` | 创建草稿/笔记 Asset | low | 否（私密 workspace 仍过 scope） |
| `note.update` | 修改笔记 | medium | 共享/外部来源需是 |
| `meeting.extract_tasks` | 从会议生成任务候选 | low | 否，先生成候选 |
| `task.create` | 创建任务 | medium | 个人 workspace 可策略放行 |
| `task.update` | 修改任务状态/截止日 | medium | 共享 workspace 按策略 |
| `finance.entry.propose` | 生成账本候选 | medium | 否，必须人工确认后入账 |
| `finance.entry.confirm` | 确认账本事实 | high | 是 |
| `email.draft.create` | 创建回复草稿 | medium | 否 |
| `email.send` | 发送邮件 | high | 是 |
| `vault.read` | 读取指定 Vault 字段 | critical | 是，字段级 scope |
| `agent.prompt` | 向 OpenCode/ACP agent 发 prompt | medium/high | 取决于目标 capabilities 和 prompt 影响 |
| `agent.interrupt` | 中断远程 session | medium | 可按 user policy 放行 |
| `agent.file.write` | 远程写文件 | high | 是 |
| `agent.command.exec` | 远程执行命令 | critical | 是；命令/目录/环境绑定 |
| `permission.reply` | 回复 OpenCode permission | high | 是（可配置安全 allowlist） |
| `question.answer` | 回答 agent question | medium | 通常否，但敏感答案需是 |
| `acc.task.create` | ACC 新建任务 | high | 是 |
| `acc.task.update` | ACC 更新任务 | high | 是 |
| `asset.sync.push` | 推送加密 Asset 镜像 | low/medium | 否；不能改变明文边界 |

### 5.3 Action 输入约束

- JSON Schema 校验字段类型、枚举、最大长度和嵌套深度。
- 输入规范化后再计算 hash：邮箱地址 canonicalize、路径清理、命令参数数组化、外部 ID trim。
- 禁止把“任意 URL”“任意 shell string”“任意 SQL”“任意 provider admin operation”作为通用字段。
- `agent.command.exec` 只能引用 policy 允许的 command class、workspace directory 和环境变量白名单；必要时由目标 agent 自己继续请求 permission。
- `vault.read` 只接受 field reference，不接受“导出整个密码箱”。
- `email.send` 明确账户、收件人、主题、正文、附件 hash；不允许从模糊上下文自动选账户。

### 5.4 Registry 版本与兼容

- `type + version` 是稳定合同；字段新增只能向后兼容，语义改变必须升 version。
- 未知 action type 返回 `action_type_not_supported`，不回退到自由文本执行。
- 旧 `/api/agents/{id}/send` 可在 facade 内生成 `agent.prompt@1`，但将 legacy source 标记为 `compat`，仍过新的 workspace/policy/审计；不因为旧接口绕过审批。
- connector capability 与 action definition 交集为空时，action 进入 `rejected_policy` 或 `needs_clarification`。

## 6. AI 编排流水线

### 6.1 单步编排（第一阶段）

```text
用户输入
  → Context assembler（当前 workspace、选中 Asset、最近任务、允许的工具摘要）
  → LLM BFF（/api/llm/stream，仅生成 Intent/Proposal）
  → Schema validator
  → Action registry resolve
  → Policy evaluate
  → Dry-run
  → UI preview / approval
  → Executor
  → Connector
  → Event outbox + read model
```

LLM BFF 沿用 `backend/internal/llmbff/service.go` 的 provider 抽象和 usage recorder；`frontend/src/api/llm-bff.ts` 继续只处理流式文本/摘要，不持有 provider/admin secret。

### 6.2 受限多步编排（第二阶段）

允许一个 Run 包含有限依赖图，但每个节点仍是 registry action：

```text
meeting.extract_tasks
        ↓ 用户确认候选
task.create ───────────────┐
                            ├→ agent.prompt (dry-run)
finance.entry.propose ─────┘
```

规则：

- 依赖节点的输出只能通过 typed output schema 传给下游；不把完整 prompt/日志拼接给下游。
- 任一高风险节点暂停整个依赖链或按 policy 允许安全节点继续；UI 必须显示 DAG 的阻塞点。
- 计划变更会使后续 payload hash 失效，需要重新 dry-run/审批。
- 初期最多 8 个节点、2 层并行、15 分钟 TTL；超限转人工或拆成多个 Run。
- 不在 v4 初期引入通用 DAG/工作流引擎；用 PostgreSQL run/action 表和 worker 队列实现可回滚切片。

### 6.3 上下文策略

`Context assembler` 只取：

- 当前 workspace 中用户明确选择的资源。
- action 所需的最小字段。
- LLM provider policy 允许发送的字段。
- 近期事件摘要和来源引用，而非无界历史。

必须记录 `context_manifest`（资源 ID、字段名、脱敏策略、hash），但不把原文全部写进 audit。用户可在预览页看到“AI 使用了哪些来源”。

### 6.4 Token、成本和限额

- 每个 Run 有 `max_tokens`、最大执行时长、最大 connector 调用数和最大重试数。
- 使用 `llmbff` 的 workspace usage 记录作为成本事实；action 级补充 `run_id/kind` 标签。
- 预算耗尽进入 `failed`/`needs_clarification`，不自动切换到未授权 provider。
- 远程 agent 的工具输出按摘要/大小上限回传；原始日志若需保存，写入受保护 Asset 或目标引用。

## 7. 审批中心

### 7.1 何时必须审批

默认需要审批：

1. 向外部地址发送邮件、消息、文档或上传文件。
2. 远程写文件、执行命令、创建/删除资源、改变 CI/部署/权限。
3. 写入确认账本、提交报销、调用外部账户或支付类接口。
4. 读取 Vault 明文、OAuth/SMTP token 或把敏感字段发送给 LLM/agent。
5. 代表用户接受 OpenCode/ACP permission 请求，尤其是 write/exec/network 类。
6. ACC 写操作，除非 connector capability 明确为低风险且 workspace policy 显式允许。

可按策略免审批：个人 workspace 中的 `note.create`、本地草稿、加密 Asset 镜像同步、`agent.interrupt`、低风险 question answer。但免审批也要做 scope、幂等和审计。

### 7.2 Approval policy 输入

```text
user + device trust
workspace + role
resource owner
action type/version
connector + target + capabilities
risk level
payload hash / preview
source (user/assistant/schedule/external event)
time/TTL
sensitivity labels
previous approvals (只作策略输入，不自动继承)
```

策略输出：`allow_without_approval`、`require_approval`、`deny`、`require_reauth`、`require_clarification`。

### 7.3 审批卡片必须显示

- **动作**：明确动词，例如“发送邮件”“在 `repo/app` 写入 3 个文件”。
- **目标**：账户、收件人、instance、session、ACC external ID、目录/文件 glob。
- **变更**：before/after 或规范化 diff；命令以参数列表展示。
- **原因**：来自用户请求、会议行动项、agent permission 或系统规则。
- **风险**：风险等级、不可逆性、可能影响范围。
- **范围**：一次、当前 Run、固定资源；本方案默认只支持“一次”。
- **期限**：过期时间和目标当前 health/capability。
- **证据**：来源 Asset/Message/Session 以及审计 ID。

### 7.4 API 交付阶段与决策接口

`/api/v4` 是目标 control-plane 契约，不是当前已存在的 P0 API。若 P0a 决定引入它，必须先完成任务拆解中的 E0-S5 / PR2：建立只覆盖 Action、Run、Approval、Question、Event 的 facade、持久化/迁移边界和旧接口兼容规则。若未完成该任务，P0 继续通过既有受限端点修复 scope/确认语义，`/api/v4` 推迟到 P1；不得让前端先依赖未落地的 v4 路由。

### 7.5 决策接口

```http
POST /api/v4/approvals/{approval_id}/decision
Idempotency-Key: idem_approval_...
Authorization: Bearer <jwt>

{
  "decision": "approve",
  "expected_payload_hash": "sha256:...",
  "comment": "确认发送"
}
```

后端事务：

```text
load approval FOR UPDATE
  → verify JWT user + workspace + device
  → verify state=pending and not expired
  → verify expected_payload_hash
  → re-evaluate policy/capability/target health
  → persist decision + audit
  → enqueue action once
  → emit approval.updated + run.queued
```

### 7.5 OpenCode permission 与统一 Approval 的映射

| OpenCode 事实对象 | Control plane read model |
|---|---|
| `permission.requested` | `Approval` pending，source=`opencode_permission` |
| `permission.resolved` | `Approval` resolved；记录 reply once/always/reject 等原始结果 |
| adapter permission request | `scope.capabilities/resources`，做资源摘要和风险归类 |
| 目标 session/instance | `target_ref={instance_id,session_id}`，workspace 从后端解析 |
| polling fallback | 与事件入口相同的 upsert/idempotent key，避免重复卡片 |

Pocket 只能把用户决定转发给实现 `PermissionCapable` 的 connector；未实现时显示“目标不支持远程回复”，不能伪造成功。

## 8. ACC Connector

### 8.1 现状与定位

仓库已有 ACC 任务来源：`backend/internal/server/server.go` 的任务聚合在 `source=acc` 时调用 MCP client，`backend/internal/mcp/client.go` 提供协议客户端边界。目标不是把 ACC 重新实现一遍，而是增加 connector facade，使 ACC 的远端任务、能力、状态和写操作遵守同一控制面合同。

ACC 在 v4 中是“外部远程智能体/任务系统 connector”，不是移动端本地 agent，也不是 Codex 手机端。任何 ACC 能力都必须由实际连接握手/探测返回；不能仅凭服务名称宣称能执行命令、审批或跨项目写入。

### 8.2 Connector 接口

```go
type Connector interface {
    ID() string
    Kind() string // opencode_http, acp_stdio, acc_mcp, email_smtp...
    Capabilities(ctx context.Context, scope Scope) (Capabilities, error)
    Health(ctx context.Context, scope Scope) Health
    Preview(ctx context.Context, action Action, scope Scope) (*Preview, error)
    Execute(ctx context.Context, action Action, scope Scope) (*ExecutionResult, error)
    Cancel(ctx context.Context, operationID string, scope Scope) error
    Subscribe(ctx context.Context, cursor string, scope Scope) (<-chan ConnectorEvent, error)
}
```

`Scope` 必须包含经过验证的 `user_id/workspace_id/device_id`，但 connector 不接受客户端传入的任意 secret/endpoint。

### 8.3 ACC 映射

```text
local Task / Intent
  → acc.task.list (read)
  → external_ref(connector=acc, external_id=...)
  → acc.task.get (read)
  → acc.task.create/update (typed write, policy + approval)
  → cursor/poll reconciliation
```

- 读操作尽量使用 ACC 的外部 cursor/更新时间；不支持事件时用定时 poll，并记录 `last_synced_at`。
- 本地 task 与 ACC task 不共享主键；重复导入使用 external ID 幂等。
- ACC 返回字段先映射到稳定 read model；未知字段放 `extensions`，不驱动执行。
- ACC 连接失败返回 `connector_unavailable`，不把远端任务标记为删除；连续失败只更新 health。
- ACC 写操作必须保存 request/operation ID；结果未知时先 query 再决定是否 retry。

### 8.4 ACC 审批边界

Pocket 的审批只证明“当前用户授权 Pocket 发起这次 action”。如果 ACC 自己还有审批/人工门禁，connector 必须把其状态映射为 `waiting_external_approval`，不能向手机显示已完成。若 ACC 不提供审批能力，Pocket 仍不得因此放宽本地风险策略。

## 9. OpenCode 与 ACP Connector

### 9.1 OpenCode HTTP

继续复用：

- `backend/internal/adapter/opencode_http.go` 和相关 types 负责 HTTP 细节。
- `backend/internal/registry/registry.go` 负责 instance、API base、health、capabilities、origin 和 workspace scope。
- `backend/internal/agent/adapter_opencode.go` 把 OpenCode 映射到 `AgentAdapter`。
- `backend/internal/agentbridge/bridge.go` 负责现有单 agent dispatch。

v4 新增 facade：

```text
agent.prompt
  → Agent Bridge scoped lookup
  → Registry resolve API base
  → capabilities/health check
  → create/load session
  → send prompt
  → subscribe session events
  → create/update Task link if requested
```

`agent.file.write`/`agent.command.exec` 不直接由 Pocket 拼装“模拟 prompt”绕过 OpenCode permission；若目标能返回 permission，统一进入 Approval；若目标没有该能力，按 policy 拒绝高风险动作。

### 9.2 ACP

`backend/internal/agent/adapter_acp_stdio.go`、`transport_stdio.go`、`transport_http.go`、`transport_ws.go` 已提供/预留 adapter/transport 形态，但应以实际实现和握手能力为准。

- ACP local stdio：connector 负责子进程生命周期、JSON-RPC request ID、超时和 stderr 隔离。
- ACP HTTP/WS：只有 endpoint 被后端 allowlist/connector store 信任且 handshake 宣布能力时才启用。
- 不把 ACP 的 session、permission、question 细节在未确认协议合同前写死；统一 read model 可先承接后端已观测的事件。
- transport 断开时 Run 进入 `connector_lost`/`indeterminate`，按 operation/session query 能力决定恢复方式。

### 9.3 Registry 与能力

`backend/internal/agent/registry.go` 负责 `AgentRef → AgentAdapter`，并保留旧 `instance_id` 映射；`backend/internal/registry/registry.go` 负责 OpenCode 实例发现/注册。v4 不合并两个 registry，而是增加：

```text
control connector registry
  ├── connector_id
  ├── kind
  ├── target_ref
  ├── owner/workspace scope
  ├── observed capabilities
  ├── health/heartbeat/last_error
  └── credential reference（仅后端）
```

控制面 registry 只引用底层 agent/instance，不复制 secret 和完整连接配置。

## 10. API 与事件合同

### 10.1 Action API

```http
POST /api/v4/actions
GET  /api/v4/actions/{action_id}
POST /api/v4/actions/{action_id}/dry-run
POST /api/v4/actions/{action_id}/cancel
GET  /api/v4/runs/{run_id}
GET  /api/v4/runs?cursor=...
```

提交响应示例：

```json
{
  "action_id": "action_...",
  "run_id": "run_...",
  "state": "waiting_approval",
  "preview": {
    "summary": "向 2 位收件人发送邮件",
    "target": "acct_work@example.com",
    "diff": {"to": ["a@example.com"], "subject": "会议跟进"}
  },
  "approval_id": "apr_...",
  "policy": {"decision": "require_approval", "rule": "external_send"},
  "expires_at": "2026-08-14T10:35:00Z"
}
```

### 10.2 Event envelope

```json
{
  "event_id": "evt_...",
  "type": "run.progress",
  "workspace_id": "ws_...",
  "aggregate_type": "run",
  "aggregate_id": "run_...",
  "aggregate_version": 4,
  "cursor": "cur_...",
  "occurred_at": "2026-08-14T10:20:00Z",
  "payload": {
    "phase": "tool",
    "summary": "正在运行测试",
    "redacted": true
  }
}
```

### 10.3 事件来源映射

| 底层来源 | 标准事件 |
|---|---|
| OpenCode session update | `session.updated` / `run.progress` |
| OpenCode permission event | `approval.created` / `approval.updated` |
| OpenCode question event | `question.created` / `question.resolved` |
| Agent Bridge dispatch result | `run.created` / `run.failed` |
| Registry heartbeat | `connector.health.changed` |
| ACC poll/event | `acc.task.updated` / `connector.sync.progress` |
| LLM BFF stream | `run.progress`（摘要） |
| Asset sync | `sync.progress` / `sync.conflict` |

所有来源都保留 `source_connector`、`source_event_id`，用于去重和诊断。

### 10.4 移动端重连

```text
WSS connect(last_cursor)
  → auth + workspace check
  → if cursor retained: replay events
  → else: resync read models + new watermark
  → live events
```

事件处理必须是幂等的：客户端可把 `approval.updated`、`run.progress`、`task.updated` 当作 upsert，不能把每次事件都当作新增实体。

## 11. 观测、审计和故障处理

### 11.1 指标

- `action.validation.count / denied.count / approval.wait_seconds`
- `run.duration / connector.latency / connector.retry_count`
- `event.replay_lag / cursor_expired / duplicate_event`
- `approval.stale_hash / approval_expired / cross_scope_denied`
- `llm.tokens / llm.cost / action.kind`
- `acc.sync_lag / external_operation_unknown`

### 11.2 日志

日志只记录 redacted summary、hash、ID 和错误分类；不记录：

- Vault 明文、OAuth/SMTP token、完整 cookie。
- 未脱敏邮件正文/附件。
- 远程 agent 的完整 secret-bearing environment。
- 可重放的完整 command secret。

### 11.3 用户可恢复故障

| 故障 | 状态 | UI 操作 |
|---|---|---|
| LLM 不可用 | `failed`，retryable | 保留原文/草稿，重试或手动编辑。 |
| OpenCode offline | `connector_unavailable` | 查看实例健康，切换 agent 或稍后重试。 |
| event cursor 过期 | `resync_required` | 自动拉快照，提示可能丢失实时细节但不丢最终状态。 |
| approval hash 过期 | `stale` | 重新预览和审批，不能复用。 |
| ACC 结果未知 | `indeterminate` | 查询外部 operation，不直接重复写。 |
| 邮件发送部分失败 | `partial` | 显示逐收件人结果，禁止盲目全量重发。 |

## 12. 分阶段实施

### S0：统一模型，不改变执行路径

- 定义 Action/Run/Approval/Question/Event 的 Go 类型和 JSON schema。
- 从 `PermissionManager`、`QuestionManager`、Agent Bridge、现有 notes/email/task handler 生成 read model。
- Today/Approval/Run 页面先消费聚合 API；旧 endpoint 继续工作。

### S1：Typed action 与单步 executor

- 接入 `note.*`、`task.*`、`email.draft.create`、`agent.prompt`、`agent.interrupt`。
- 先实现 dry-run、policy、幂等和 audit；不接远程写文件/命令。
- 用 feature flag 按 workspace 开启。

### S2：OpenCode permission/question 与外发审批

- 将现有 permission/question 事件映射到统一模型。
- 接入 `email.send`、`finance.entry.confirm`、`vault.read` 的审批路径。
- 测试重复点击、过期、hash 变更、跨 workspace、connector offline。

### S3：ACC connector 与事件游标

- 只读 ACC 列表/详情/健康，再做 action preview。
- 增加 outbox/replay/cursor；移动端断线补偿。
- ACC 写操作默认关闭，完成 capability/审计/回滚验证后按 workspace 灰度。

### S4：受限多步编排

- 支持会议→任务→agent prompt 等有限依赖链。
- 每个节点 typed、可暂停、可重试；超限转人工。
- 不引入通用自治系统，不把手机变成未经授权的远程执行器。

## 13. 控制面验收标准

### 13.1 安全

- 任意 action 在后端生成并校验 `workspace_id`，客户端篡改无效。
- 远程写文件、命令、邮件发送、账本确认、Vault 读取、ACC 写操作没有 approval 就不能调用 connector。
- approval 绑定 `payload_hash + target_ref + workspace + expiry`；任一改变都拒绝。
- 重放同一个 `Idempotency-Key` 返回同一结果；connector operation unknown 时不会产生重复副作用。
- LLM、手机和 WebSocket 客户端永远拿不到 provider admin token、SMTP/OAuth secret 或 OpenCode 任意 endpoint secret。

### 13.2 正确性

- OpenCode permission/question 的事件与轮询重复到达时只生成一条 pending read model。
- 不支持 `PermissionCapable`/`QuestionCapable`/对应 ACC capability 的 connector 明确返回 unsupported，不伪造成功。
- Registry 健康变化能更新 Agent/Connector read model；离线不会把历史 Run 标为 succeeded。
- Event replay 后移动端状态与实时处理一致；重复事件不重复执行 action。

### 13.3 体验

- 用户能在审批卡片看到动作、目标、diff、原因、风险、期限和来源。
- 用户能取消 queued/running Run，或看到为什么不可取消。
- AI 建议可逐项接受/修改/忽略；没有“黑盒自动全选”。
- 远程 agent 的工具输出以摘要为默认，完整输出可按权限展开；错误提供下一步。

### 13.4 兼容

- 现有 `/api/agents/{id}/send`、OpenCode session、notes/email/task/assets API 的测试继续通过。
- 老前端能忽略新 event envelope 的附加字段；新前端能读取旧 `type/payload` 事件。
- Asset 与旧表并存时无重复用户内容；迁移可回滚，冲突进入 repair queue。
