# 优化 v4：数据模型与本地云同步

> **目标**：在不把现有“本地加密库、云端控制面、OpenCode 执行面”强行合并为一库的前提下，建立统一的 Asset/Task/Run/Event/Action/Approval/Audit 语义，以及可恢复、可审计、可做 CAS 的同步协议。
>
> **口径**：现状事实来自当前代码与既有审计；方案内容是推断建议；真实并发、迁移和恢复行为均标为待验证。本文不修改源码、不执行数据迁移。

## 1. 当前数据事实

### 1.1 本地数据库

**现状事实**：`frontend/src/native/local-db.ts:12-91` 以单例连接 SQLCipher，`DB_VERSION = 2`，通过 `local_schema_migrations`（`184-213`）执行本地迁移。`frontend/src/native/schema.ts:13-350` 同时存在：

- 旧业务表：`local_notes`、`local_email_accounts`、`local_emails`、`local_vault_entries`、`local_meetings`、聊天和待办表；
- 新统一资产：`local_assets`（`268-288`）、`local_asset_blobs`（`319-331`）、`local_asset_vectors`（`339-349`）；
- 本地同步状态：`local_sync_state`（`241-246`）。

`local_assets` 已有 `workspace_id`、`kind`、`meta_json`、`sync_mode`、`client_rev`、`server_rev`、`dirty`、`deleted_at`；软删除墓碑和 workspace 索引已定义。`local_vault_entries`（`171-183`）没有 workspace 字段，这是旧业务与统一租户模型的明确断点。

### 1.2 云端数据库

**现状事实**：

- Vault 云端 `vault_sync` 按 `(workspace_id,user_id,version)` 保存密文多版本，`PutLatest/GetLatest/ListVersions/MarkCurrent` 有事务或作用域谓词（`backend/internal/vault/store.go:30-177`）。
- Asset 云端 `asset_mirrors` 保存 opaque `cipher_blob`、`client_rev/server_rev/deleted_at`，`asset_sync_log` 保存 push/pull/conflict 摘要（`backend/internal/lobster/store.go:35-93`）。
- Task 模型已有 workspace、source、pending approvals、session count（`backend/internal/task/task.go:4-24`），并通过 `task_session_links` 关联执行会话（`backend/internal/agentbridge/bridge.go:49-53` 的 TaskAttacher 接口）。
- OpenCode 事件当前由 `EventStreamManager` 在内存按 `instanceID + workspaceID + directory` fan-out；每个 subscriber 有 bounded channel，缓冲满时丢事件（`backend/internal/opencode/event_stream.go:23-82,194-389`）。

### 1.3 同步客户端

**现状事实**：`frontend/src/native/asset-store.ts:110-151` upsert 时先查当前 revision，再自增 `client_rev` 并置 `dirty=1`；`listDirty/markSynced` 位于 `263-281`。`frontend/src/api/assets.ts:15-55` 约定 push/pull mirror；`frontend/src/features/vault/sync-store.ts:22-80` 对 Vault 仍采用整库 blob 的 push-first/LWW 语义。前端 WS hub 另有内存 `offlineQueue`（`frontend/src/services/websocket-hub.ts:28-37,107-116`）。

**结论**：已有“Asset 增量镜像”和“Vault 整库版本”两套同步协议；不能把它们的 revision 或冲突规则混为一谈。

## 2. 统一领域模型

以下字段是逻辑模型；具体落地可分 PostgreSQL 表、SQLite 表和事件投影，但字段语义必须一致。

### 2.1 公共 Envelope

| 字段 | 约束 |
|---|---|
| `id` | 全局不可猜测 ID；服务端生成或使用带命名空间的 UUID/ULID |
| `workspace_id` | 必填；系统级对象显式使用 `system`，禁止空字符串兼容隐式共享 |
| `actor_type/actor_id` | user/device/service/plugin/worker；后台任务保留原始 actor |
| `correlation_id` | 一次用户意图贯穿 request/action/run/event/audit |
| `causation_id` | 触发当前对象的上一个事件或 action |
| `created_at/updated_at` | 服务端时间为审计基准；客户端时间仅作展示/冲突辅助 |
| `schema_version` | 事件和密文 envelope 可演进；旧版本拒绝静默解释 |

### 2.2 Asset：内容与附件

```text
Asset
  id, workspace_id, kind, title_ref, body_ref, meta_ref
  source, classification, sync_mode
  client_rev, server_rev, base_server_rev
  content_hash, dirty, deleted_at
  created_at, updated_at
AssetBlob
  id, asset_id, idx, media_type, size, cipher_ref, hash
AssetVector
  id, asset_id, chunk_idx, model, dim, embedding_ref
```

**规则**：

1. `classification` 至少有 `public/workspace/confidential/secret/regulated`；Vault、OAuth refresh token、SMTP/IMAP password 只能是 `secret`。
2. `title_ref/body_ref/meta_ref` 不是“是否加密”的布尔推断；每个 ref 标明 `plaintext`、`ciphertext`、`redacted`，并带 key version。
3. Asset 的本地和云端 key 都是 `(workspace_id, asset_id)`；跨 workspace 不允许同 id 覆盖。
4. Blob 默认分块 AES-GCM，hash 用于去重/完整性，不把明文 hash 误当保密措施。
5. `sync_mode`：`e2ee_local_first`、`cloud_authoritative`、`cloud_readonly`；策略决定谁可写，不由客户端任意切换。

### 2.3 Task：业务目标

```text
Task
  id, workspace_id, source(acc|opencode|local)
  title, description, status, priority, workstream_id
  owner_id, policy_id, pending_approval_count
  created_at, updated_at, completed_at
TaskLink
  task_id, asset_id|session_id|run_id, relation, created_at
```

**规则**：Task 不直接表示一次执行；它可以关联多个 Run、Session、Asset 和 Approval。任务来源 `Source` 现已存在（`backend/internal/task/task.go:14-19`），下一步应把 ACC/OpenCode/local 的 provider 标识与归属策略显式化。

### 2.4 Run：一次执行

```text
Run
  id, workspace_id, task_id, session_id, agent_id, plugin_id
  requested_by, capability_snapshot, input_digest
  state(queued|running|waiting_approval|succeeded|failed|cancelled|partial_failure)
  attempt, idempotency_key, started_at, finished_at, error_code
```

Run 绑定执行上下文快照：实例、目录、model/provider、允许的 capabilities、数据出端决策。后续策略变化不应篡改已经批准的快照；重新执行必须创建新 Run。

### 2.5 Event：不可变事实

```text
Event
  id, workspace_id, aggregate_type, aggregate_id
  type, seq, payload_ref, payload_digest
  actor, correlation_id, causation_id, occurred_at
```

建议事件类型：`task.created`、`run.queued`、`action.approved`、`run.started`、`session.message.received`、`asset.pushed`、`sync.conflict`、`run.partial_failure`、`run.recovered`。payload 默认密文/脱敏；大正文不直接放 Event。

当前 OpenCode `DomainEvent` 只有 `InstanceID/WorkspaceID/Directory/SessionID/Type/Raw/ReceivedAt`（`backend/internal/opencode/event_stream.go:71-82`），可作为适配层输入，不应直接当 durable Event。

### 2.6 Action：可产生副作用的意图

```text
Action
  id, workspace_id, run_id, type, resource_ref
  input_ciphertext, input_digest, requested_capabilities
  state, idempotency_key, approval_id
  attempt, next_attempt_at, expires_at
  result_ref, error_code, created_at, completed_at
```

Action 类型包括 `session.dispatch`、`plugin.command`、`email.send`、`oauth.exchange`、`asset.sync`、`migration.start`、`credential.rotate`。每个类型必须声明幂等性、最大重试、出端数据分类和补偿方式。

### 2.7 Approval：明确授权

```text
Approval
  id, workspace_id, action_id, requested_by
  scope, reason, decision(pending|approved|denied|expired|revoked)
  decided_by, expires_at, policy_version, created_at, decided_at
```

Approval 绑定不可变 Action digest；Action 输入变化后原 Approval 失效。高风险操作不以“用户已经能调用 API”代替 Approval。

### 2.8 Audit：合规摘要

```text
Audit
  id, workspace_id, actor, action, resource_type, resource_id
  decision, result, correlation_id, ip/device_summary
  input_digest, output_digest, redaction_profile, occurred_at
```

Audit 与 Event 不同：Event 用于产品状态回放，Audit 用于责任、策略和合规查询；均不应保存 Vault、refresh token、邮件正文或完整 prompt。

## 3. 本地模型与云端镜像

### 3.1 本地表建议

在现有 `local_assets` 基础上增加同语义的本地投影：

- `local_runs`、`local_actions`、`local_approvals`、`local_events`、`local_outbox`；
- 每表含 `workspace_id`、`client_rev`、`server_rev`、`deleted_at` 或适用的状态字段；
- `local_outbox` 保存待上传/执行的加密 payload、幂等 key、attempt、next retry、last error、expires；
- `local_events` 只保存可重放的必要 envelope；大内容引用 Asset/Blob，不复制正文。

现有 `local_sync_state`（`frontend/src/native/schema.ts:239-246`）可作为 cursor 投影，但不能替代逐 Action 的状态和幂等 key。

### 3.2 云端表建议

- `assets`/`asset_versions`：服务端权威或密文镜像；唯一键 `(workspace_id, asset_id, server_rev)`。
- `tasks`、`runs`、`actions`、`approvals`、`events`、`audit_entries`：所有表有 workspace 复合索引；高风险资源增加 owner/resource policy。
- `sync_cursors(workspace_id, device_id, stream, cursor)`：每设备、每 workspace 独立 cursor。
- `outbox_dispatch`/`dead_letters`：服务端执行队列和失败保留；不能依赖内存 WS channel。

**迁移依赖**：现有模块自带 migration（例如 `lobster.NewSyncStore` 构造时执行 `migrate`，`lobster/store.go:54-93`），统一模型落地前必须建立 migration version table、顺序、锁、预检查、回滚/前向兼容和可观测结果。

## 4. CAS 协议

### 4.1 Push

客户端提交：

```text
workspace_id
asset_id
base_server_rev
client_rev
payload_ciphertext / payload_hash
deleted_at
idempotency_key
```

服务端事务：

1. 校验 actor 对 workspace 和 Asset 的权限；
2. 以 `(workspace_id, asset_id)` 锁定当前版本；
3. 若 `base_server_rev != current_server_rev`，返回 `409 conflict`，保留当前版本和 incoming candidate；
4. 若 idempotency key 已完成，返回原结果；
5. 否则写新 `asset_version`、递增 server rev、写 `asset.sync.accepted` Event 与 Audit；
6. 客户端只有拿到 accepted/rejected/conflict 结果后才更新 `dirty/server_rev`。

### 4.2 Pull

客户端按 `(workspace_id, stream, cursor)` 拉取 server events/asset versions；先写入临时版本，再校验 hash/AEAD tag，再原子更新本地投影。拉取不能依据客户端 `updated_at` 猜测增量。

### 4.3 冲突策略

| 数据类型 | 默认策略 | 人工恢复 |
|---|---|---|
| 普通文本 Asset | 三方合并或字段级合并 | 展示 base/local/remote，生成新 revision |
| 结构化 Task/Action | 字段策略 + 状态机校验 | 不允许直接覆盖状态，走新 Action |
| Vault/OAuth/SMTP 凭据 | 禁止自动合并 | 选择版本或重新录入，旧版本保持不可用/可审计 |
| 音频/PDF/图片 | content hash + 版本选择 | 保留两份 Blob，用户选择主版本 |
| 删除 vs 更新 | tombstone 优先但保留更新版本 | 允许显式恢复，恢复本身生成 Event |

**现状与断点**：服务端 `lobster.Push` 当前会接受旧版本并 upsert（`backend/internal/lobster/store.go:105-157`），且冲突行为与注释中的 LWW/“最高 client_rev”语义并不等价；必须先补集成测试和协议冻结，再改实现。

## 5. 离线队列

### 5.1 入队

只有产生服务器副作用的 Action 进入 `local_outbox`；普通 UI notification、已可由 cursor 重放的 Event 不入队。入队与本地业务写入在同一事务中，避免“界面已显示但没有待同步记录”。

### 5.2 调度

- 状态：`queued → sending → acked` 或 `retry_wait/dead_letter/cancelled`；
- 指数退避 + 抖动，按错误码区分 5xx/网络可重试与 4xx/策略拒绝；
- 每 workspace、每 capability 限制并发；切换用户或 workspace 立即暂停旧队列；
- 收到 server result 后以 idempotency key 原子确认；超时不能直接判定失败，应查询 Action 状态。

### 5.3 恢复

应用启动扫描 `sending` 超时记录，转为 `retry_wait`；服务端按 key 返回原状态；dead letter 要展示原因、原始摘要、可重试按钮和所需 Approval。不得把 payload 明文写日志。

**待验证**：当前 WS hub 的 `flushOfflineQueue()` 会直接逐条发送（`frontend/src/services/websocket-hub.ts:222-235`），需要模拟断网、进程杀死、重复回执、服务端处理成功但客户端超时四类场景。

## 6. Event、SSE、WS 与顺序

1. 业务写入先产生 durable Event，再由 SSE/WS 投影；不能把“发送到 channel”作为业务成功。
2. 每个 workspace/stream 使用单调 `seq`；SSE reconnect 带 `after` cursor；cursor 不足时返回 `gap`，客户端重新拉 projection。
3. WS 只承载 command request/ack 或实时提示，不承载唯一事实；命令 ack 带 action id、attempt、server state。
4. subscriber 缓冲满时不能静默丢关键 Event；当前 `event_stream.go:379-388` 的 drop 行为只能适用于可重建的低价值进度事件。
5. Event payload 采用分类策略，敏感正文引用 Asset/Blob；客户端只在有 capability 时解密。

## 7. 迁移、回填和恢复计划

### 7.1 旧表到 Asset

按风险从低到高：notes → meetings → emails → vault。每一类先建立映射表（legacy id、asset id、workspace、classification、content hash），再双读/只读回填，最后灰度双写。旧表保留回滚窗口，不做隐式删除。

### 7.2 Session/Task/Run 对齐

为已有 `task_session_links` 生成 Run/TaskLink 投影；历史 OpenCode event 只能作为“导入事件”而非伪造原始 occurred_at。Agent Bridge 的 attach 失败场景生成 `partial_failure`，由补偿任务重试。

### 7.3 Schema migration 操作门槛

- 预检查：行数、重复 key、空 workspace、孤儿 link、密文 key version；
- 分批、可暂停、幂等；每批写 migration audit；
- 先建索引/约束兼容结构，再切读写；
- 失败保留 staging 和 checkpoint，不自动删除历史；
- 验收后才启用新 writer，至少保留一次反向回滚演练。

现有邮件迁移已证明顺序很重要：先按 workspace 去重再替换唯一约束（`docs/audits/2026-08-08-cross-workspace-audit.md:62-72`）；这一原则适用于所有旧数据回填。

## 8. 验收矩阵

| 场景 | 预期 | 证据 |
|---|---|---|
| 同一 Asset 两设备并发更新 | 一方 accepted，另一方 409；两版本均可恢复 | PG 并发集成测试 + 本地模拟 |
| 断网后修改并强杀 App | 重启后 outbox 仍在，恢复后只执行一次 | Android/iOS/浏览器测试 |
| 服务端已执行但客户端超时 | 查询 Action 得到原结果，不重复执行 | idempotency contract test |
| workspace A/B 相同 id | 查询、push、pull、恢复完全隔离 | 跨租户 PG 测试 |
| 删除与更新竞争 | tombstone/版本按策略处理，可显式恢复 | 冲突测试 |
| 迁移源/目标离线 | Run 进入 waiting/retry/partial 状态，不能假报成功 | plugin/registry fault injection |
| SSE 丢事件 | 收到 gap 后按 cursor 补拉投影 | SSE replay 测试 |
| Vault/凭据同步 | 服务端只见密文；冲突不自动合并 | 密文/日志/抓包审计 |

## 9. 实施顺序

1. 冻结 Envelope、scope、revision、Event/Action 状态机和错误码。
2. 先补服务端 CAS/幂等/作用域和集成测试，再接本地 outbox。
3. 将 WS/SSE 改为 Event 投影，保留旧通道兼容但不再以其作为事实源。
4. 迁移 Task/Session/Agent/Plugin/Approval/Audit 关联。
5. 最后按业务风险逐类从旧表迁到 Asset，并开展恢复演练。

**总验收**：不存在“写入成功但没有 Event”、“发送成功但没有 Run/Audit”、“同步成功但无法解释版本”、“冲突被静默覆盖”、“重试造成第二次副作用”这五类状态。
