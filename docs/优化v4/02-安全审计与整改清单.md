## 2. P0 整改清单

### SEC-01：跟踪凭据与高风险工件

**现状事实**：仓库跟踪集合中存在 `backend/data/email_master.key` 与 `data/email_master.key`；另有 `deployment-test-20260706-131715/token.txt`、备份源码和可执行文件。该事实只说明“已跟踪”，不推断文件内容当前仍有效。

**推断建议**：

1. 先做只读取证：识别文件类型、历史提交、CI artifact、镜像层、备份和部署主机副本，记录 hash 与暴露时间。
2. 由密钥负责人决定是否轮换；本文不执行轮换、不删除历史。
3. 将运行时 secret 改由 secret manager/部署注入；仓库只保留无值模板。
4. 增加 pre-commit/CI secret scanning、artifact allowlist 和二进制跟踪阻断。
5. 对 `*.bak`、运行 token、私钥、数据库 DSN、生产二进制制定 allow/deny 规则，误报通过显式例外且不含 secret 值。

**验收标准**：

- 新提交中禁止 key/token/私钥/真实 DSN；扫描能命中测试 fixture 并正确识别安全占位符。
- 取证清单包含 Git refs、CI、镜像、备份和部署节点；每个已暴露凭据有“是否仍有效/是否需要轮换”的负责人结论。
- 运行时启动在缺失 secret 时 fail closed，不从仓库文件回退读取。

**依赖与风险**：依赖安全负责人、部署平台和供应商；轮换会导致 IMAP/SMTP/OAuth/Gateway/旧客户端短暂失效，必须有双 key 重叠窗口和回滚预案。

### SEC-02：JWT、WS、SSE 凭据边界

**现状事实**：`backend/internal/server/auth_helper.go:31-70` 普通 HTTP 优先读取 Authorization，但实时路径允许 URL query token；`frontend/src/api/sse.ts:71-84`、`frontend/src/api/websocket.ts:19-24` 通过 URL 传 token；`frontend/src/stores/auth.ts:14-24` 持久化 token 到 localStorage。

**推断建议**：

- 普通 HTTP：仅 `Authorization: Bearer` 或受控 HttpOnly cookie；禁止任何业务 query token。
- WS：先以 HTTPS 请求换取一次性、绑定 `user/workspace/channel`、30–60 秒过期、单次消费的 handshake ticket；URL 只带 ticket，不带 JWT。
- SSE：优先改为 `fetch` + `ReadableStream` 携带 Authorization；若必须 EventSource，使用 HttpOnly cookie 或短期 ticket。
- 日志 middleware、反向代理、APM、错误页对 `token/access_token/Authorization/cookie` 做结构化脱敏；禁止打印 `message.data` 中的凭据字段。
- 移动端 token 迁移到原生 Keystore/Keychain 封装；localStorage 只保留非敏感 session hint。

**兼容与切换计划**：先发布日志脱敏和 `message.data` 清洗，降低旧 query token 暴露面；随后服务端同时支持 ticket/cookie 与旧 query JWT 的明确兼容窗口。兼容窗口必须绑定客户端/服务端版本、截止日期、owner、监控告警和拒绝策略，不能无限期保留；新客户端默认使用 ticket/cookie，生产环境不得静默降级到长寿命 JWT query。截止日期后服务端 fail closed；回滚只允许恢复旧客户端读取路径，不恢复日志明文或扩大 token TTL。

**验收标准**：URL、Referer、access log、前端 console、异常堆栈中无 JWT；ticket 重放、跨 workspace、过期、错频道均失败；WS/SSE 重连自动换新 ticket；JWT 过期或 membership revoke 后实时通道关闭；兼容窗口的开始/结束版本和拒绝策略有 owner 签字。

## 3. P1 整改清单

### SEC-03/04：跨 workspace/session/agent/plugin 授权

**现状事实**：JWT claim 在 `auth/jwt.go:15-20`；插件 WS 已从 claims 设置 metadata（`server_plugin_ws.go:17-74`）；Agent handler 使用 `GetScoped`/workspace（`server_agentbridge.go:197-259`）；但成员有效期未检查（`identity/store.go:251-264`），迁移源解析和部分 Manager 仍存在未 scoped 调用风险。

**推断建议**：统一 `authorize(actor, resource, action)`：

- `workspace`：actor 必须是有效 member；owner/admin 才能管理成员、设备、审计。
- `session`：session 必须经 `(workspace_id, instance_id, session_id)` 解析；禁止仅凭 session id 或 instance id 访问。
- `agent`：Agent 所属 workspace、绑定 instance workspace、目标 directory、model/provider 和 capability 必须同时满足策略。
- `plugin`：PluginConnection/ManagerConnection 注册时写入 workspace、user、device、capabilities；命令路由按 workspace + instance + plugin 三元组校验。
- `migration`：源/目标实例均 scoped；源 session 读取、迁移包生成、目标命令下发、task link 回填全部带同一 correlation id 和 workspace。
- `shared instance`：`WorkspaceID == ""` 不得自动混入普通租户读写；若保留共享语义，只允许系统级 admin policy 生成显式、只读或租户隔离的 capability。

**验收标准**：每个资源的跨 workspace 测试至少覆盖 get/list/update/delete/dispatch/subscribe/migrate；外部 workspace 的 session subscribe 在建立上游连接前拒绝；拒绝响应不泄露资源存在性；membership expiry 立即阻断，或通过 token epoch/revocation check 达到同等效果。

### SEC-05：Action/Approval/审计

**现状事实**：Agent `Send` 的副作用顺序是创建 session、发送 prompt、更新 agent 状态、可选 attach task（`agentbridge/bridge.go:138-181`）；attach 失败不回滚已发 prompt。迁移命令在目标端异步完成（`migration/service.go:125-159`）。

**推断建议**：所有副作用统一写 `Action`：

- `action_id`、`idempotency_key`、actor、workspace、resource、requested capability、input digest、policy decision、approval id、state、attempt、created/updated/completed_at。
- 高风险动作先 `pending_approval`；批准记录 actor、scope、过期时间和 reason；拒绝/过期不可执行。
- 执行器先原子 claim action，再调用上游；同一 idempotency key 返回原结果，不重复发 prompt/邮件/插件命令。
- `Event` 记录 accepted/approved/started/progress/succeeded/failed/cancelled/compensated；`Audit` 只记录不可变、脱敏的合规摘要。
- attach/link 失败必须进入 `partial_failure`，提供补偿 action 或人工重试，不能只返回 `Attached=false` 后消失。

**验收标准**：重复 HTTP 请求、WS 重放、worker 重启均最多产生一次外部副作用；审批前无外部调用；所有敏感 Action 可由 correlation id 找到 request、approval、run、event、audit；失败有重试上限和死信。

### SEC-06：离线队列与重试

**现状事实**：`frontend/src/services/websocket-hub.ts:36` 的队列为进程内数组；断线时 `send()` 入队，连接后直接逐条 flush（`107-116,222-235`），没有持久化、过期、幂等或失败回执。

**推断建议**：新增本地 `outbox` 逻辑（可复用 LocalDB，不等于新增另一套队列）：`id`、workspace、action/event type、payload ciphertext、idempotency key、created_at、next_attempt_at、attempts、state、last_error、expires_at。只把“可重试 Action”入队；UI 通知不入队。服务端返回 accepted/result cursor，客户端收到确认后原子删除或标记完成。

**验收标准**：应用强杀、系统重启、断网 24 小时后队列可恢复；同一 key 不重复产生 prompt/邮件/命令；永久 4xx 进入 dead-letter 并可人工重试；切换 workspace 不发送旧 workspace 队列。

### SEC-07：CAS 与同步冲突

**现状事实**：本地 Asset 在 `asset-store.ts:124-151` 先 query 再用 `existing.client_rev + 1` update；服务端 `lobster/store.go:115-141` 先读当前 mirror，再 upsert，并会接受旧 client revision；`asset_mirrors` 以 asset id 主键，`GetMirror` 不带 workspace 条件（`192-205`）。

**推断建议**：

- Push 请求必须带 `workspace_id`、`asset_id`、`base_server_rev`、`client_rev`、payload hash、idempotency key。
- 服务端使用事务/行锁或 `UPDATE ... WHERE server_rev = base_server_rev`；0 行更新返回 `409 conflict`，不静默覆盖。
- 主键改为 `(workspace_id, id)` 或等效唯一约束；所有 Get/Push/Pull 都要求 workspace。
- 保留冲突版本和墓碑；冲突策略按 kind 配置：文本可三方合并，凭据/二进制只允许人工选择，不做隐式合并。
- `server_rev` 是服务器全局/工作区单调游标，`client_rev` 只描述设备/实体版本；不能把两者混用。

**验收标准**：两个设备基于同一版本并发更新必有一方收到 409；冲突版本可下载、比较、合并/选择、恢复；重复 push 返回同一结果；跨 workspace 相同 asset id 不互相覆盖。

### SEC-08：SSRF 与出站 capability

**现状事实**：`backend/internal/server/ssrf.go:123-187` 对 URL、私网、metadata、DNS 解析和重定向做限制；网关私网访问由 `POCKET_LLM_GATEWAY_ALLOW_PRIVATE` 放宽（`24-29,73-75`）。

**推断建议**：把“出站 URL 可访问”从通用布尔开关升级为注册节点 capability：目标 host/port、用途（health/models/chat/stream）、允许 workspace、允许 credential class、最大响应/超时、是否允许私网。每次 DNS 解析与连接记录目标摘要，不记录 query 中 secret。禁止用户直接提供 arbitrary instance API URL；Registry 注册时做管理员批准和周期复检。

**验收标准**：localhost、RFC1918、link-local、metadata、IPv6 私网、DNS rebinding、重定向到内网全部被测试；私网例外只能匹配已登记节点和用途；任意用户无法把 Gateway URL 改成内部管理端点。

### SEC-09：OAuth/SMTP/IMAP

**现状事实**：OAuth 使用随机 state、PKCE S256 和真实 client id（`email/oauth.go:16-65`）；审计仍将真实 provider flow、SMTP 发信和假期回复列为未闭环（`docs/audits/2026-08-09-email-pipeline-audit.md:212-224`）。

**推断建议**：state 绑定 user/workspace/provider/redirect/nonce 并一次性消费；callback 不信任 query 中 workspace/user；token exchange 使用固定 allowlist redirect；refresh token 仅密文存储，按最小 scope；SMTP 发信 action 必须经过 workspace/account ownership、recipient policy、内容分级和审计。IMAP sync 只从 account row 派生 workspace，不接受客户端 email/account 归属。

**验收标准**：真实沙盒 provider 完成 start/callback/refresh/revoke；state 重放、错 workspace、错 redirect 全拒绝；邮件同步/发信/SMTP probe 均有账户 scoped 测试；不在响应、日志或前端列表回传密码/refresh token。

## 4. P2 整改清单

- **统一 Audit**：覆盖登录、workspace 切换、凭据读写、OAuth、SMTP probe/send、LLM、STT、session dispatch、plugin command、migration、sync conflict、恢复和管理员操作；字段只存摘要/hash，不存明文 payload。
- **日志安全**：结构化日志字段分级，默认禁止 prompt、邮件正文、Authorization、cookie、API key、refresh token、Vault body；异常只返回稳定 error code。
- **WebSocket/SSE**：服务端 durable event cursor 与 replay 窗口；缓冲溢出发 gap event，客户端不得把“消息丢弃”当作成功；设置连接数、单帧、每 workspace 速率和并发上限。
- **Capability registry**：能力命名采用 `asset.read:kind`、`asset.export:class`、`session.dispatch`、`plugin.command`、`network.egress:purpose` 等，策略拒绝未知能力。
- **安全回归门禁**：所有 DB-gated 测试必须在 CI 显示“执行”而不是静默 skip；已有审计指出这是曾导致 `InsertEmail` 缺陷长期存活的原因（`docs/audits/2026-08-09-email-pipeline-audit.md:224-226`）。

## 6. 安全验收总表

- P0：无真实凭据进 Git/镜像/日志；实时通道不接受长寿命 query JWT；跨 workspace 全路径拒绝。
- P1：成员撤销/过期在下一请求生效；高风险动作审批前不出端；Action 幂等且可恢复；CAS 冲突不覆盖。
- P2：所有出端都有 capability、数据分类和审计；日志/指标可定位但不泄密；历史保留、删除、恢复均可演练。
