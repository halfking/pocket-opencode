# 04 目标架构与领域拆分

**版本**：优化 v4（方案）
**目标**：在不重写当前 OpenCode Pocket 的前提下，把移动控制面演进为个人 AI 助手平台。架构以 `localDB + Asset + workspace + LLM BFF + Agent Bridge + OpenCode registry` 为骨架，以后端为信任边界，以 connector 和事件协议承接 OpenCode、ACP、ACC、邮件与同步。

> 产品导航、用户流程和体验验收见 `docs/优化v4/03-产品蓝图与信息架构.md`；AI 控制面与 typed action/审批的细节见 `docs/优化v4/07-AI编排与智能体控制面.md`。

---

## 1. 现状基线与设计原则

### 1.1 现状基线（代码事实）

- 前端是 Capacitor + Vue，业务位于 `frontend/src/`，已存在 notes、meetings、tasks、email、vault、agents、workspace 等 feature/store/api。
- `frontend/src/native/local-db.ts` 是本地 SQLite 连接的单一入口，初始化 SQLCipher secret，并通过 `frontend/src/native/schema.ts` 创建 `local_*` 表。
- `frontend/src/native/asset-store.ts` 已定义 `Asset`、blob、vector、`syncMode`、`clientRev/serverRev/dirty`；`frontend/src/api/assets.ts` 对接 `/api/assets/sync`。
- `backend/internal/lobster/store.go` 保存 e2ee Asset 的密文镜像和同步日志；其注释明确服务端不解密 `e2ee_local_first` 内容。
- 任务、agent、notes、email、vault 等后端 store 已部分使用 PostgreSQL 和 workspace scope；`backend/internal/meeting/store.go` 当前仍为内存实现，不能在方案中伪称为稳定云端事实库。
- `backend/internal/llmbff/service.go` 提供统一 Chat/Stream/Embed Provider，并按 `workspace_id` 记录用量；provider/admin token 留在后端。
- `backend/internal/agentbridge/bridge.go` 已实现“按 agent 找 instance → 创建 OpenCode session → 发送 prompt → 可选 attach task”的单 agent dispatch。
- `backend/internal/agent/registry.go` 已提供 `AgentRef → AgentAdapter` 查找，并兼容旧 `instance_id`；`backend/internal/registry/registry.go` 维护 `PocketInstance`、API base、health、capabilities、origin 和 workspace 过滤。
- `backend/internal/opencode/permission_manager.go` 与 `question_manager.go` 已通过事件优先、轮询兜底的方式缓存待处理请求；`backend/internal/websocket/mobile_hub.go` 已向按 session 订阅的移动端推送权限/question/会话事件。
- 任务聚合在 `backend/internal/server/server.go` 已有 `source=local|opencode|acc` 的事实入口；ACC 目前应被视为现有 MCP/任务来源适配，而不是已经抽象完成的统一远程执行协议。

### 1.2 设计原则

1. **渐进式而非大爆炸**：新增 facade、read model、adapter 和事件映射，不先替换已有 store/路由。
2. **后端是信任边界**：客户端提供意图、展示证据和发送用户操作；后端负责身份、workspace、能力、策略、凭证、幂等和审计。
3. **内容与动作分离**：Asset 是数据；Action/Run 是意图与执行记录；Approval 是授权记录；三者不能混成一张“AI 消息表”。
4. **本地优先但不一概本地**：私密个人内容默认 `e2ee_local_first`；共享任务、邮件状态和远程运行状态由后端作为云端权威或事件权威。
5. **能力探测优于类型猜测**：OpenCode、ACP、ACC 都必须返回 capabilities；没有能力就显示不可用，不用名称推断行为。
6. **事件可重放**：所有移动端关键状态变更有 `event_id + cursor + aggregate_version`，断线可补偿，不依赖一次 WebSocket 推送必达。
7. **兼容优先**：保留老 `/api/*` 端点、旧前端 store 和 `instance_id` 查询；新 API 通过 `/api/v4` 或兼容 facade 增量接入。

### 2.1 哪些组件是现状，哪些是目标

| 层 | 现状 | v4 目标 |
|---|---|---|

## 3. 领域拆分与边界

### 3.1 Identity & Workspace

**职责**：用户、设备、JWT、workspace membership、角色和请求上下文。

**拥有**：`user_id`、`workspace_id`、membership、device_id、session claims。

**不拥有**：业务实体正文、LLM secret、connector 的任意目标权限。

**现有路径**：`backend/internal/auth/`、`backend/internal/identity/`、`frontend/src/stores/auth.ts`、`frontend/src/stores/workspace.ts`。

**不变量**：workspace 必须从已验证 JWT/服务端会话解析。客户端 body/query 的 `workspace_id` 只能作为一致性提示，不能成为授权依据。

### 3.2 Personal Content / Asset

**职责**：统一承载笔记、语音 memo、会议音频/转写、票据图片/PDF、附件、截图和未来个人知识块。

**拥有**：Asset metadata、blob、vector、revision、sync mode、source、tombstone。

**现有路径**：`frontend/src/native/asset-store.ts`、`frontend/src/native/schema.ts` 的 `local_assets/local_asset_blobs/local_asset_vectors`；`backend/internal/lobster/store.go` 的 `asset_mirrors/asset_sync_log`。

**边界**：

- `e2ee_local_first`：手机明文/密钥为权威；后端只看 workspace、asset ID、kind 和密文镜像（若标题需要搜索则使用显式允许的可见元数据）。
- `cloud_authoritative`：服务端可保存明文，例如共享任务或邮件标签，但不应误用 Asset 代替任务/邮件的业务表。
- `cloud_readonly`：客户端缓存外部内容，不把缓存写回外部系统。

**兼容策略**：`local_notes`、`local_emails`、`local_vault_entries`、`local_meetings` 不删除；以 `source_record_id` 和 migration marker 建立 Asset adapter，分阶段把新写入切到 Asset。

### 3.3 Knowledge / AI Enrichment

**职责**：转写、分类、摘要、embedding、关联、任务候选和检索；输出必须标注模型、时间、置信度和来源。

**拥有**：Enrichment job/read model，不拥有用户原始内容的所有权。

**现有路径**：`backend/internal/notes/classifier.go`、`backend/internal/meeting/summarizer.go`、`backend/internal/kxmemory/client.go`、`backend/internal/llmbff/service.go`、`frontend/src/api/llm-bff.ts`。

**边界**：LLM provider 只通过 `llmbff.Provider`；模型不能直接调任意外部 API、写数据库或发邮件。高敏内容须在 policy 中决定是否允许脱敏后发送。

### 3.4 Work Management

**职责**：Task、待办、工作流来源、截止日期、优先级、来源链、session link。

**现有路径**：`backend/internal/task/store.go`、`frontend/src/features/tasks/`、`frontend/src/native/schema.ts` 的 `local_todos`。

**边界**：

- Task 是目标和承诺，不等同于一次 AI Run。
- `task_session_links` 只记录关联，不代表 session 已成功完成 task。
- `source=local|opencode|acc` 是现有聚合语义，v4 为其增加 `source_ref`、`connector` 和同步游标，而不是立即合并外部系统主键。

### 3.5 Finance / Ledger

**职责**：票据、金额、币种、商户、分类、账本分录、确认状态和审计。

**现有路径**：`backend/internal/finance/`、`backend/internal/server/server_finance.go`、前端 finance 相关页面/adapter（如存在）。

**边界**：OCR/LLM 只能产出 candidate；`confirmed_by` 和 `confirmed_at` 之前不得把模型抽取值当作会计事实。涉及外部报销/账户写入/转账的 action 必须审批。

### 3.6 Mail

**职责**：账号、OAuth/IMAP 同步、邮件、线程、标签、草稿、SMTP 发送和规则。

**现有路径**：`backend/internal/email/`、`backend/internal/server/server_assistant.go`、`backend/internal/server/smtp_send.go`、`frontend/src/features/email/`、`frontend/src/api/email.ts`。

**边界**：

- OAuth/IMAP/SMTP 凭证只能在后端或受保护存储边界使用。
- LLM 处理使用最小字段集；原文附件需要单独授权。
- 草稿可以自动生成；发送是副作用，必须走 typed action + approval + 后端 connector。

### 3.7 Vault & Security

**职责**：凭证/密码箱、Keystore、生物识别、本地加密、敏感读取的授权和审计。

**现有路径**：`frontend/src/features/vault/`、`frontend/src/native/keystore.ts`、`frontend/src/native/crypto.ts`、`backend/internal/vault/`。

**边界**：后端不是用户主密钥的持有者；服务器可以保存版本化密文同步镜像，但不能因为拥有 JWT 就读取 Vault 明文。向 agent/LLM 暴露 Vault 字段是单独的高风险 action。

### 3.8 Agent Control Plane

**职责**：Agent、Instance、Session、Run、Permission、Question、Tool progress 和人工控制。

**现有路径**：`backend/internal/agent/`、`backend/internal/agentbridge/`、`backend/internal/opencode/`、`backend/internal/registry/`、`backend/internal/websocket/mobile_hub.go`、`frontend/src/stores/agent.ts`、`frontend/src/stores/session.ts`。

**边界**：控制面不实现编程 agent 本身；它解析/验证 action，选择 connector，持有目标 endpoint 和凭证，接收事件并将最小必要数据送回手机。

### 3.9 Connector / Integration

**职责**：把统一 action/event 映射到 OpenCode HTTP、ACP、ACC MCP/HTTP、邮件、LLM、RedClaw/kxmemory 和资产镜像。

**拥有**：connector identity、capabilities、health、external reference mapping、retry/backoff、protocol errors。

**不拥有**：跨 workspace 的授权；每次调用必须接受后端传入的 scoped context 和 policy decision。

## 4. 数据所有权与一致性

### 4.1 Source of truth 矩阵

| 数据 | 权威源 | 手机本地 | 后端 | 同步/一致性 |
|---|---|---|---|---|
| 私人笔记正文/录音/密码 | phone Asset（e2ee） | 明文解密后可用 | 密文 mirror | client_rev/server_rev，冲突显式解决 |
| 共享任务 | PostgreSQL task store | 缓存/离线命令 | 明文权威 | API 写入 + event cursor |
| OpenCode instance health | registry/connector probe | 缓存 | 后端权威 | TTL + heartbeat + replay |
| OpenCode session stream | 目标 agent + control-plane event log | 最近摘要/游标 | 事件 read model | event_id/cursor，重连补发 |
| 权限/question | 目标 agent 请求 + 后端 Approval read model | 展示/用户选择 | 后端权威处理状态 | nonce + expiry + idempotency |
| 邮件账户/邮件 | 后端 email store/外部邮箱 | 可选加密缓存 | 账号范围内权威 | UID/message-id 去重，状态事件 |
| 账本确认分录 | finance store | 离线草稿 | 已确认记录 | 草稿→确认事务，外部提交需审批 |
| LLM 用量 | `model_usage`/BFF recorder | 展示缓存 | 后端权威 | best-effort recording，查询可重算 |
| ACC 远端任务 | ACC | 缓存 | connector read model | external_id + cursor/poll + source=acc |

### 4.2 ID 规则

所有跨领域引用使用带前缀的 opaque ID：

```text
ws_...      workspace
ast_...     Asset
run_...     AI/connector run
action_...  typed action
apr_...     Approval
q_...       Question
agent_...   Agent Bridge entity
inst_...    registry instance
sess_...    agent session
task_...    local task
ext_...     external reference
```

客户端不得通过递增 ID 猜测另一个 workspace 的资源；后端对“不存在”和“跨 workspace”统一返回 404/NotFound 语义。

### 4.3 事件与快照

事件不是业务表的替代品：

- **快照**用于打开页面、分页和搜索。
- **事件**用于实时更新、审计和断线补偿。
- **游标**用于“从哪里继续”，不能用 timestamp 代替。
- **聚合版本**用于客户端拒绝过期写入，避免最后写入静默覆盖。

## 5. API 设计

### 5.1 通用 envelope

```json
{
  "request_id": "req_01J...",
  "workspace_id": "ws_personal",
  "data": {},
  "meta": {
    "cursor": "cur_...",
    "next_cursor": null,
    "server_time": "2026-08-14T10:20:00Z"
  }
}
```

错误统一：

```json
{
  "request_id": "req_...",
  "error": {
    "code": "approval_expired",
    "message": "approval is no longer valid",
    "retryable": false,
    "details": {"action_id": "action_..."}
  }
}
```

### 5.2 资源 API（建议新增 `/api/v4` facade）

| 方法 | 路径 | 语义 | 幂等 |
|---|---|---|---|
| `GET` | `/api/v4/today` | Today 聚合 read model | N/A |
| `GET` | `/api/v4/runs` | 运行列表/游标 | N/A |
| `GET` | `/api/v4/approvals` | 审批列表/筛选 | N/A |
| `POST` | `/api/v4/actions` | 提交 typed action；返回 dry-run/queued | `Idempotency-Key` |
| `GET` | `/api/v4/actions/{id}` | action 与 run 状态 | N/A |
| `POST` | `/api/v4/actions/{id}/cancel` | 取消尚未执行的 action | `Idempotency-Key` |
| `POST` | `/api/v4/approvals/{id}/decision` | approve/reject/modify | `Idempotency-Key` |
| `GET` | `/api/v4/questions` | 待回答问题 | N/A |
| `POST` | `/api/v4/questions/{id}/answer` | answer/reject | `Idempotency-Key` |
| `GET` | `/api/v4/agents` | Agent Bridge workspace 列表 | N/A |
| `GET` | `/api/v4/connectors` | connector 能力/健康 | N/A |
| `GET` | `/api/v4/events?after=...` | 事件重放 | N/A |
| `GET` | `/api/v4/sync/status` | Asset/业务同步状态 | N/A |

现有 `/api/notes`、`/api/meetings`、`/api/email/*`、`/api/assets/sync`、`/api/agents`、`/api/llm/*` 不立即删除；v4 facade 先聚合其结果并提供迁移头/版本。

### 5.3 Action 提交模型

```json
{
  "type": "email.send",
  "version": 1,
  "input": {
    "account_id": "acct_...",
    "to": ["person@example.com"],
    "subject": "会议跟进",
    "body": "..."
  },
  "mode": "dry_run",
  "source": {"kind": "assistant_run", "id": "run_..."},
  "client_context": {"device_id": "dev_...", "locale": "zh-CN"}
}
```

服务端响应至少包含：`action_id`、规范化输入摘要、风险等级、需要的 capabilities、policy decision、是否需要 approval、run_id、过期时间。

### 5.4 WebSocket/SSE 设计

保留现有 `backend/internal/websocket/hub.go` 和 `mobile_hub.go`，向新 envelope 兼容：

```json
{
  "event_id": "evt_01J...",
  "type": "approval.created",
  "aggregate": {"type": "action", "id": "action_...", "version": 3},
  "workspace_id": "ws_...",
  "occurred_at": "2026-08-14T10:20:00Z",
  "cursor": "cur_...",
  "payload": {}
}
```

客户端流程：

1. 建立 WSS，发送 workspace、device、最后 cursor。
2. 后端先发送 snapshot watermark，再推送增量事件。
3. 事件丢失/连接重建时调用 `/api/v4/events?after=cursor`。
4. 事件重复按 `event_id` 去重；过期 cursor 返回 `resync_required`，客户端重新拉取 read model。
5. session 事件可按 session 订阅，但 approval、task、run 状态按 workspace 订阅，避免只打开某个 session 才看得到紧急审批。

事件类型最小集：

```text
asset.changed              note.enriched
meeting.updated            task.updated
run.created                run.progress
run.succeeded              run.failed
approval.created           approval.updated
question.created           question.resolved
agent.updated              instance.health.changed
session.updated            tool.progress
mail.updated               finance.entry.updated
sync.progress              sync.conflict
connector.health.changed   audit.recorded
```

## 6. 安全与信任边界

### 6.1 后端必须做的检查

每个写入或 action 请求按以下顺序执行：

```text
JWT signature/expiry
  → user/device/session validity
  → workspace membership
  → resource ownership/scope
  → connector capability + health
  → action schema validation
  → policy/risk evaluation
  → idempotency key
  → approval binding (if required)
  → external call
  → audit + event
```

不能由前端决定：`workspace_id`、目标 API URL、provider admin token、SMTP credential、ACC tenant、OpenCode directory 是否可写、approval 是否有效。

### 6.2 敏感数据分级

| 等级 | 示例 | 默认处理 |
|---|---|---|
| S0 | 标题、状态、数量 | 可进入 read model，按 workspace scope。 |
| S1 | 普通笔记、邮件摘要、任务描述 | LLM 最小字段；可配置云端处理。 |
| S2 | 会议全文、邮件正文、票据图片 | 明确 workspace policy；默认本地优先/脱敏。 |
| S3 | Vault 密文/解密字段、OAuth/SMTP token | 禁止进入普通 LLM prompt；一次性显式授权。 |
| S4 | 外部发送、转账、远程执行、写文件 | 必须 approval；后端再次鉴权和审计。 |

### 6.3 SSRF 与 endpoint 安全

现有 `server` 已有 SSRF 测试和 LLM gateway 白名单代理。v4 不允许客户端提交任意 `apiBaseURL` 直连；connector target 必须来自 registry/connector store，且按协议、host allowlist、TLS、workspace 绑定检查。`AgentRef.Target` 也不得绕过 registry 的可信解析。

### 6.4 审计最小字段

```text
audit_id, request_id, user_id, device_id, workspace_id,
actor_type(user|assistant|system), action_id, connector,
target_ref, input_hash, redacted_summary, policy_decision,
approval_id, result_code, started_at, finished_at
```

不把密码、OAuth token、完整 Vault 明文或未脱敏邮件正文写入日志。

## 7. 兼容与演进策略

### 7.1 存储迁移

1. **并存**：老表继续读写，Asset 先承载新 kind。
2. **适配**：增加 `LegacyNoteAdapter`、`LegacyMeetingAdapter`、`LegacyVaultAdapter` 等内部接口，将老实体投影为 Asset/SourceRef。
3. **双写**：在 feature flag 下新写入同时写老表和 Asset，异步校验 hash/字段。
4. **切读**：按 workspace 灰度从 Asset read model 读取；差异进入 repair queue。
5. **冻结旧写**：确认指标稳定后，旧接口只读或返回迁移提示；不在本阶段删除表。

### 7.2 API 迁移

- 老路径保留至少一个兼容周期；通过 `X-Pocket-API-Version` 或 `/api/v4` 选择新 envelope。
- `instance_id`、旧 action 字段和 camelCase/snake_case 兼容在 facade 做规范化。
- 旧前端收到未知事件类型时忽略；新前端支持旧 `type/payload` WebSocket envelope。
- 所有新增 action 先支持 `mode=dry_run`，旧的直接 dispatch 不自动获得更高权限。

### 7.3 OpenCode/ACP 兼容

- `backend/internal/agent.AgentAdapter` 是稳定抽象；OpenCode HTTP 继续是第一实现。
- `PermissionCapable`、`QuestionCapable` 是可选接口，未实现时 UI 显示 capability 不支持，不调用不存在的 endpoint。
- ACP connector 通过 transport/capability handshake 选择 stdio、HTTP 或 WS；官方资料未确认的能力不写死。
- OpenCode registry 继续保留 discovered/registered/static/acc origin；新增 connector_id 和 observed_capabilities，不删除已有字段。

### 7.4 ACC 兼容

- 现有 `source=acc` 任务聚合先保持只读语义。
- connector 失败不能阻塞 local/opencode 任务；返回 source-specific error 和最后成功同步时间。
- ACC 外部 ID 永远与本地 task ID 分离，以 `external_ref` 映射；重复同步用 `(workspace_id, connector, external_id)` 幂等。
- ACC 写 action 不假设外部支持审批；Pocket 只在自身后端完成本地审批后提交，并把“远端是否再次审批”作为 connector capability 展示。

## 8. 实施切片与验收

### Slice 1：统一上下文与读模型

- 建立 `RequestContext{UserID, WorkspaceID, DeviceID, RequestID}`。
- Today/Approvals/Runs 先从现有 stores、permission/question manager、WebSocket 缓存聚合。
- 验收：跨 workspace 资源全部不可读；旧端点测试不回归。

### Slice 2：事件游标与重放

- 为已有 Hub 广播增加 event envelope；短期可用 PostgreSQL outbox，后续再独立事件存储。
- 移动端保存最后 cursor，断线调用 replay API。
- 验收：断网 60 秒后重连不丢 task/approval/run 最终状态；重复事件不重复 toast/执行。

### Slice 3：typed action/approval

- 先实现 `note.create/update`、`task.create/update`、`email.draft.create`、`email.send`、`agent.prompt`、`agent.interrupt`、`permission.reply`、`question.answer`。
- 所有 action 走 dry-run、policy、idempotency；副作用写 audit。
- 验收：外发/远程执行/权限回复均无法绕过后端；重复请求最多执行一次。

### Slice 4：Asset adapter 与同步

- 新捕获统一 Asset；老模块双写/迁移；同步冲突 read model 化。
- 验收：服务端抽样数据库无法读取 e2ee 正文；冲突有两个 revision 且可人工决策。

### Slice 5：ACC connector

- 只读列表/详情/状态 → action dry-run → 小范围写操作。
- 验收：无 capability/无 membership/过期 cursor/重复 external ID 均安全失败；local/opencode 仍可独立工作。

### Slice 6：全链路移动体验

- Today、Capture、Workspace、Agents、Approvals 五项导航上线；双栏复用同一 read model。
- 验收：语音→笔记→任务→agent、邮件→草稿→审批、会议→行动项三条流程有来源链和状态链。

## 9. 架构验收标准（Definition of Done）

1. 任一 request 都能追溯到 user、device、workspace、request_id 和 audit_id。
2. 任一 action 都能回答：谁发起、作用于哪个资源、通过哪个 connector、需要什么权限、是否审批、最终结果是什么。
3. 任一 Asset 都能回答：本地/云端谁权威、是否加密、client/server revision、是否 dirty、冲突如何处理。
4. 任一远程 Agent 都能回答：绑定哪个 instance、registry 来源、当前 health、capabilities、workspace、最近 heartbeat。
5. 任一 AI 结果都能回答：输入来源、模型/provider、生成时间、置信度/是否人工确认；不能把建议当事实。
6. 断线、超时、重复提交、过期审批、跨 workspace ID、connector 不支持能力均有确定错误码和可恢复路径。
7. 保留现有测试与兼容路径；任何迁移切片都可通过 feature flag 回滚到旧 store/endpoint。
