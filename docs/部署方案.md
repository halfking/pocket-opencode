## 一、方案

### 1.1 总体思路

本机已经跑着一批公用服务（PG17 / Redis / goacos / acc），按「**有就复用，没有才自建**」的原则部署 openpocket：

```
                      ┌──────────────────────────────────────────┐
   浏览器 ──────────► │ frontend  opencode-pocket-frontend      │
                      │   nginx :4175  同源反代 /api → pocketd    │
                      └───────────────────┬──────────────────────┘
                                          │
                      ┌───────────────────▼──────────────────────┐
                      │ pocketd    opencode-pocket               │
                      │   Go 静态二进制 :8088 → 宿主 :8090        │
                      └───────────────────┬──────────────────────┘
                                          │ host.docker.internal:5432
                      ┌───────────────────▼──────────────────────┐
                      │ 复用：acc-pg17 (PostgreSQL 17.10 / Citus) │
                      │   库 pocket / schema opencode_pocket      │
                      │   owner llm_gateway                       │
                      └──────────────────────────────────────────┘
```

### 1.2 公用服务复用盘点

部署前先探测本机已有的服务，逐个决定「复用 / 自建 / 不需要」。

| 服务 | 本机实况 | 处置 | 依据 |
| --- | --- | --- | --- |
| **PostgreSQL 17** | 容器 `acc-pg17`（`kx-citus-pg17:arm64`），`127.0.0.1:5432`，版本 17.10 | **复用** | openpocket 唯一持久化后端；已有 `acc_db` / `crm` / `pocket_test` 同宿主共存 |
| **Redis** | 容器 `nbjl-redis`（`kx-redis:7.4.9-arm64`），`127.0.0.1:16381` | **复用但不接入** | 全仓 `grep -i redis` 只命中一处 TODO 注释与一个分类器标签，openpocket 运行期不依赖 Redis，故不写入 `POCKET_REDIS_URL` |
| **MySQL** | 本机无实例（宿主无 3306 监听，docker 无相关容器） | **不部署** | openpocket 不使用 MySQL；镜像库只有 `mysql-8.0.42`（且非 8.4），无使用需求故不起 |
| **goacos** | 容器 `goacos` 健康（`127.0.0.1:8848`）；`https://goacos.itestu.cn` TLS 握手成功但 HTTP/2 流以 `PROTOCOL_ERROR` 中断 | **不需要** | openpocket 代码中**零引用** goacos/nacos（`grep -rn "goacos\|nacos" backend frontend deploy` 无命中） |
| **acc** | 容器 `acc-server` 健康（`127.0.0.1:4100`）；`https://acc.itestu.cn` 返回 302（可达） | **不需要** | openpocket 不调用 acc 服务 |
| **memora** | `https://memora.itestu.cn` 返回 404（可达，根路径无路由） | **可选，未接入** | 对应 `POCKET_KXMEMORY_BASE_URL`（笔记分类/SSOT），默认留空即关闭，不影响部署 |

> 说明：goacos/acc/memora 的 `itestu.cn` 域名按要求做了可达性验证（见 §3.4）。openpocket 当前代码不消费这三个服务，因此只验证、不接线；后续若开启 memora 集成，`POCKET_KXMEMORY_BASE_URL` 应指向 `https://memora.itestu.cn`。

### 1.3 数据库方案

- **不新建 PG 实例**，在共享的 `acc-pg17` 上单独开一个库，与其它项目并列：

  | 库 | owner | 归属 |
  | --- | --- | --- |
  | `acc_db` | `acc_app` | acc 项目 |
  | `crm` | `crm_user` | CRM 项目 |
  | `pocket_test` | `pocket_test` | openpocket 测试用（与生产库隔离） |
  | `pocket` | `llm_gateway` | **openpocket 生产库** |

- **schema**：`opencode_pocket`，不在部署期预建，交给后端 migration 创建并持有（避免和 migration 抢所有权）。部署后实测已由后端建出 **68 张表**。
- **账号**：使用目标规范中的主超级用户 `llm_gateway`（与 `deploy/bin/env.sh` 默认一致，密码仅经环境变量注入，不入库、不回显）。
- **幂等**：`pocket` 已存在则复用，重复部署不会重复建库、不会改动他人密码。

### 1.4 镜像方案（全离线）

硬性要求：基础镜像只能取自本地镜像库，不从网络下载。实测仓库自带的构建链**无法满足**，三处硬伤：

| 仓库默认 | 问题 | 本次处置 |
| --- | --- | --- |
| 构建器 `kx-base:go-vue-optimized` | 内含 Go **1.24.13**，低于 `backend/go.mod` 要求的 **1.27.1**，必然编译失败 | 改用镜像库里的 `kx-base/golang:1.27-alpine-arm64`（Go 1.27.1） |
| 运行时 `alpine:latest` | 镜像库**没有 arm64 的纯 alpine**（只有 `alpine:3.18-i386`，架构不符） | 本机**合成** `alpine:opp-runtime-arm64`（13.9 MiB） |
| 前端构建器 `node:22-bookworm-slim` / 运行时 `nginx:1.24-alpine` | 两者离线库均无 | 构建器改用宿主 Node 22；运行时改用库里的 `nginx:alpine`（1.27.5） |

**运行时基底的合成方式**（不 build、不 pull、不联网）：
从已就绪的 arm64 alpine 镜像 `redis:7-alpine` 导出 rootfs → 用 `--exclude` 剥掉 redis 负载 → `FROM scratch` + `ADD` 重新组装。产出 13.9 MiB 的纯 alpine，且自带 `wget` 与 CA 证书，因此 `Dockerfile.pocketd-offline` 的 runtime 阶段**无需执行 `apk add`**，构建链彻底不触网。

> `nginx` 版本偏离说明：仓库钉 `nginx:1.24-alpine` 是为规避 CentOS 7（kernel 3.10）上 nginx mainline 起不来的问题。本机是 Docker Desktop 的 Linux VM，无此约束，故使用离线库里的 1.27.5。

**最终镜像**：

| 镜像 | 大小 | 架构 | 来源 |
| --- | --- | --- | --- |
| `opencode-pocket:pocket-opp` | 120 MB | arm64 | 容器内 Go 1.27.1 交叉编译 + 合成 alpine 基底 |
| `opencode-pocket-frontend:pocket-opp` | 118 MB | arm64 | 宿主 Node 22 构建 dist + `nginx:alpine` |

### 1.5 脚本与执行顺序

```
./deploy-local.sh
   │
   ├─ 0) deploy/bin/prepare-offline-images.sh   离线镜像准备（探测镜像库 → load →
   │                                            架构校验 → 合成 alpine 基底 → 7 项能力自检）
   ├─ 0) deploy/bin/build-offline-images.sh     镜像缺失时才跑（容器内编译 Go + 宿主构建 dist）
   ├─ 1) deploy/bin/init-dirs.sh                建 10 个运行目录
   ├─ 2) deploy/bin/ensure-databases.sh         复用探测（PG 命中外部实例，不新建）
   ├─ 3) 生成 config/.env.local                 注入 POCKET_POSTGRES_DSN（密码不回显）
   └─ 4) deploy/bin/start.sh                    compose up --no-build → 健康检查 → 蓝绿切流
```

数据库首次开库用独立脚本（幂等、可单独重跑）：

```
OPP_PG_PASSWORD=<密码> ./deploy/bin/provision-local-pg.sh
```

### 1.6 资源需求

| 阶段 | 资源 |
| --- | --- |
| 镜像准备 | 磁盘 ≥ 8 GiB（实测可用 761 GiB）；待 load 离线包 ≈250 MiB；导入后镜像 ≈1.1 GiB；临时目录 ≈300 MiB |
| 镜像构建 | 内存峰值 ≈1.5–2 GiB（宿主需 ≥ 2 GiB，脚本会实测拦截）；磁盘 ≈1.5 GiB；耗时 后端 3–8 min + 前端 2–5 min |
| 运行 | 两个容器合计 ≈250 MB 内存；数据落 `~/kaixuan/openpocket/{data,logs,...}` |
| 网络 | **不需要**访问 Docker Hub；Go/npm 依赖优先走本地缓存，缓存不全才回落 `goproxy.cn` / npm registry |

### 2.5 测试结论

`go test -race ./...` 全仓跑通，仅 `backend/internal/server` 有 1 项失败：

```
--- FAIL: TestSttConfigListsBothRecommendedGroups
    推荐模型应为网关 3 + 外部 ≥7，实际 gateway=5 external=7
```

**该失败是 `origin/main` 上既有的，与本次部署改动无关**：本次工作区改动只有 `deploy-local.sh`、`deploy/bin/*`、`deploy/docker/*` 共 8 个文件，**未触碰任何 Go / 前端源码**（`git status --porcelain` 可核对）。失败原因是后端把网关推荐模型从 3 个增加到 5 个后，测试里的 `if gw != 3` 硬编码没有同步更新——测试注释本身写明「只守下限不写死上限」，网关侧却写死了，属于既有测试债务。

另有一项 `TestFrontendLLMGatewayDefaultsMatchBackend` 在「只挂载 `backend/` 到容器」时曾报 `frontend/src/constants/llm-gateway.ts: no such file`——那是测试执行环境（缺少仓库根目录）造成的假阳性，按 CI 的方式挂载整个仓库后该用例正常。

**处置（已与需求方确认）**：该失败属于既有问题且不影响部署与服务运行，**本次只合并部署相关的改动**，不在这个提交里顺手改产品测试契约。这条技术债单独立项跟进（建议把 `if gw != 3 || ext < 7` 按注释本意改成只守下限），本次不处理。

## 三、部署过程中发现并修复的问题

| # | 问题 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | 仓库构建器 `kx-base:go-vue-optimized` 内含 Go 1.24.13，低于 `go.mod` 要求的 1.27.1 | 后端必然编译失败 | 改用离线库的 `kx-base/golang:1.27-alpine-arm64` |
| 2 | 离线库无 arm64 纯 alpine | runtime 基底缺失 | 新增 `prepare-offline-images.sh`，从 `redis:7-alpine` 剥负载合成 13.9 MiB 基底，并加 7 项能力自检兜底 |
| 3 | macOS 导出 rootfs 带 `com.apple.provenance` 扩展属性 | `docker build ADD` 报 `lsetxattr ... no such file` | 打包前后统一 `--no-xattrs` + `xattr -cr` |
| 4 | `deploy-local.sh` 在补 PATH **之前**就 `docker image inspect` | 镜像明明存在却判定缺失，白白全量重建 | PATH 兜底统一提到 `env.sh`（所有 `deploy/bin/*.sh` 的单一来源） |
| 5 | `ensure-databases.sh` 使用 `${name^^}` | macOS 自带 bash 3.2 报 `bad substitution`，把一条警告变成部署硬失败 | 改为显式大写映射表 |
| 6 | bash 3.2 + `set -u` 下展开空数组 | `unbound variable` 部署中断 | 先判数组长度再传参 |
| 7 | 宿主无 `psql` / `redis-cli` / `mysqladmin` | 复用探测恒失败，会误判「没有 PG」而另起实例撞端口 | `database-detect.sh` / `check-databases.py` 增加 `docker exec` 兜底：借道「确实发布了该端口」的引擎容器 |
| 8 | 复用探测用目标库鉴权 | 首次开库时目标库尚不存在 → 必然失败 | 探测固定连维护库 `postgres` |
| 9 | `docker build --pull=never` | `--pull` 是布尔开关，该值非法 | 改 `--pull=false` |

## 四、运维手册

### 4.1 常用命令

```bash
# 状态 / 健康
./deploy/bin/status.sh

# 重新部署（镜像已存在则不重建）
OPP_PG_PASSWORD=<密码> ./deploy-local.sh

# 强制重建镜像后部署
OPP_PG_PASSWORD=<密码> ./deploy-local.sh --build

# 只更新前端（保留后端与数据）
./deploy-local.sh --frontend-only

# 只更新后端
./deploy-local.sh --backend-only

# 停服 / 回滚
./deploy/bin/stop.sh
./deploy-local.sh --rollback

# 日志
./deploy/bin/logs.sh
docker logs -f opencode-pocket-pocketd-local-openpocket
```

### 新增

| `deploy/bin/prepare-offline-images.sh` | 离线基础镜像准备：镜像库探测、资源需求与磁盘预检、离线包 sha256 校验、架构校验、合成 alpine 基底、7 项能力自检、结果汇总 |
