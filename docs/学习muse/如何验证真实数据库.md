# 真实 Postgres 验证：怎么跑

> 状态：**尚未执行过**。这份文档是跑法,不是结果。
> 详见 `evidence/` 下各阶段的「未验证」条目。

## 为什么需要它

P0–P4c 写下来的每一条 SQL 都**编译通过但从未执行**。DDL 沿用仓库既有的幂等范式
（`CREATE TABLE IF NOT EXISTS` + `ALTER ... ADD COLUMN IF NOT EXISTS`，ADR-005），
handler 与执行器都只被「假 client」的单元测试覆盖过。

风险不是「写得对不对」这种抽象问题，而是具体的三类：

1. **列名/参数错位** —— 编译期抓不到，只在第一次真实查询时报错。
   （`internal/task/store_contract_test.go` 已经能在无库的情况下抓 SELECT 列表与
   scan 目标数的错位，但抓不到 INSERT 的参数个数与列数不匹配。）
2. **唯一索引不存在** —— 幂等与 exactly-once 全靠它。
   最要命的是 `learning_reminders` 上的
   `idx_learning_reminders_idem (workspace_id, user_id, kind, item_id)`：
   **里程碑只播一次**这个保证，Go 代码里没有任何检查，完全依赖它。
3. **新增索引没建成** —— `idx_flashcard_revlog_user_reviewed` 是本轮为连续天数加的，
   不建成就是全表扫（性能问题，不影响正确性）。

## 跑法

需要一个能建 schema 的 Postgres（会 `CREATE SCHEMA` / `DROP SCHEMA`，
**不要指向生产库**）：

```powershell
# 1) 起一个库（任选其一）
docker run --rm -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:16
# 或本机已装的 postgres 服务

# 2) 跑全量集成测试
$env:POCKET_TEST_POSTGRES_DSN = "postgres://postgres:pw@localhost:5432/postgres?sslmode=disable"
cd backend
go test ./...

# 3) 看哪些真的跑了
go test ./... -v 2>&1 | Select-String "SKIP|PASS|FAIL"
```

每个测试用**独立 schema**（`search_path`），所以可以随便跑、不留痕、不互相污染。

## 没设 DSN 时会发生什么

测试会 **SKIP 而不是 PASS**：

```
--- SKIP: TestClaimMilestoneIsExactlyOnce
    store_pg_test.go:102: POCKET_TEST_POSTGRES_DSN not set; skipping learning integration test
```

这是刻意的。跳过不会被误读成「验过了」——`go test` 的输出里 SKIP 和 PASS 是两种状态，
CI 上看得到。

## 没有数据库也能查的那部分

不是所有 SQL 风险都必须等数据库。已用静态守卫覆盖的：

| 风险 | 守卫 | 文件 |
|---|---|---|
| SELECT 列数 ↔ `scanTask` 目标数错位 | `TestTaskColumnsMatchScanDestinations`（用记录型 stub row 真正调用 `scanTask`） | `internal/task/store_contract_test.go` |
| 扫描目标传值而非指针（静默丢列） | `TestScanTaskDestinationsArePointers`（反射判 `Kind()==Ptr`） | 同上 |
| `taskColumns` 重复列（计数对但整体错位） | `TestTaskColumnsHaveNoDuplicates` | 同上 |
| 工作项列被漏掉（UI 渲染空白） | `TestTaskColumnsIncludeWorkItemColumns` | 同上 |
| **INSERT 列数 ↔ 占位符数错位** | `TestTaskInsertColumnsMatchPlaceholders` | 同上 |
| 占位符编号有重复/断号（`$5` 被写两次） | `TestTaskInsertPlaceholdersAreSequential` | 同上 |

为让最后两条可查，`CreateTask` 与 `UpsertTask` 共用的列清单与 VALUES 已从内联字面量
抽成 `taskInsertColumns` / `taskInsertValues` / `taskUpsertValues` 三个常量。
（upsert 的 VALUES 多一层 `NULLIF`，所以是单独一份而不是复用。）

**仍然查不到的**：传给 `Exec` 的 Go 参数个数。pgx 是变参，静态无从比对——
这一类只能靠下面的门控测试在真实数据库上暴露。

> 这些守卫都做过「注入漂移后是否报警」的实测，不是靠「测试通过」推断它们有效。
> 例：给 `taskInsertColumns` 加一列后，测试精确报出
> `has 23 columns but taskInsertValues has 22 placeholders`，随后回滚。
