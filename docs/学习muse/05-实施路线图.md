## 4. P3 · 协作闭环（✅ 已完成，真库未验）

### 已落地

- `GET/PUT /api/tasks/{id}/participants` —— 名单读取与整份替换（PUT 语义），非参与者读私有项 **403**；
- `GET/POST /api/tasks/{id}/activity` —— 协作活动流 + 追加评论（`client-` 前缀 eventId 供移动端重试幂等）；
- `POST /api/tasks/{id}/delegate` —— 委派：落 participants + `owner_id` + 写 `assigned` 事件 + 发通知；
- `GET /api/tasks/{id}/approvals` —— 审批投影**只读**视图 + pending 计数（回复路径归 agent 上游）；
- `GET /api/tasks/{id}/children`、`POST /api/tasks/{id}/subtasks` —— 子任务与**派生**进度；
- `PATCH /api/tasks/{id}` 写前校验 `parentId`（不存在 / 跨 workspace / 成环一律 400）；
- 事件→通知映射、访问控制、进度聚合、环检测均为**纯函数**且有单测；
- 前端 `TaskCollaborationPanel` 挂进 `TaskDetailView`（参与者 / 委派 / 活动流 / 评论 / 审批 / 子任务 / 进度条）。

### 目标 = 普通工作项，不建新表

目标就是一条工作项，别的条目用 `parent_id` 指着它，进度**派生不落库**。
两个取值判断是刻意的：**无子任务 → 0% 而不是 100%**（没有子任务意味着这不是目标，
满进度条是撒谎）；**百分比向下取整**（2/3 显示 66，向上取整会让差一项的目标看起来快完成）。

只聚合**直接子任务**，孙任务不递归折进父任务——这是取舍，已在 evidence 写明。

### 路径被既有路由逼出来的两处改名

- 协作活动流是 `/activity` 不是 `/events`——`GET /api/tasks/{id}/events` 早已是 ACC 运行事件投影；
- 委派到人是 `{id}/delegate` 不是 `/delegate`——`POST /api/tasks/delegate` 早已是「经 ACC 建任务」。

### 本轮对账掉的一个设计错误

§4.2 的 `due_soon` 行与 `reminded` 行重复（提醒中枢写的是 `reminded`），并存会让 owner
在同一次触发里收到两条通知。已折叠，`created` / `due_changed` / `child_added` 明确为不发通知。

## 5. P4 · 提醒落地与契约变更（🟡 代码部分完成）

### 本轮补上的「生产者」

开工前先查了 `tasks.remind_at` 的实际使用情况：**列存在、写入与校验存在、
但没有任何东西消费它**。用户在任务上设了「提前 1 小时提醒」，存下来了，然后什么都不会发生。
`reminded` 事件类型、`work_item.reminder` 通知映射、免打扰顺延逻辑全是「有定义、无生产者」。

已补 `WorkItemReminderExecutor`（`Kind = work_item_reminder`）：

- **幂等靠事件主键**：`event_id` 由 `remind_at` 派生（`reminder:<remind_at>`），
  而 `work_item_events` 主键是 `(workspace, task, event_id)`，所以去重由**数据库保证**，
  而不是执行器里一句「我检查过没有」。
- **顺延而非丢弃**：落在免打扰窗口内的提醒不触发、不通知，改写 `remind_at` 到窗口结束。
  窗口默认 22:30→07:30 **跨午夜**，朴素的 `start <= x < end` 会全错，代码显式分两条分支。
- 23:50 顺延到的是**次日** 07:30，不是今天那个已过去的 07:30。
- 投递失败只记日志、**不让 run 失败**：事件已落库，冒泡 500 会让调度器重试一次已成功的写入。
- **陈旧上限兜住积压**：`remind_at` 超过 24h 的提醒**静默退役**（归零、不推送、计入 `stale`），
  判定顺序是 stale → quiet → fire。理由：batch 限流只压住速率、压不住总量——一万条积压
  就是一万条推送，而三天前的「提醒」已经不是提醒了。`SetStaleAfter(0)` 可关闭。
  被退役的工作项仍会作为「逾期」出现在任务列表里。
  > 顺带更正上一版的表述：当时写「会集中触发、积压规模未估量」偏夸大了。tick 5s × batch 50
  > 已经把速率压到 10 条/秒；真正的风险是**总量**而不是速率。

### 连续学习天数（P4c）

- **派生不落库**：每次从 `learning_items` 的活动日期重算（730 天窗口）。计数器在崩溃 /
  时区变更 / 漏 tick 后需要修复，重算是自愈的。
- **何时算断**：连续记录活过「最后一次学习日的次日」。昨晚学了、今早没打开 App，
  连续天数**仍是完整的**——朴素实现会在午夜清零，每天早上都给刚学过的人显示 0。
- **里程碑 exactly-once**：复用 `learning_reminders` 已有唯一索引
  `(workspace, user, kind, item_id)`，记成 `kind='streak'`、`item_id='milestone:N'` 的一行。
  去重由 PostgreSQL 保证。**本轮刻意不新增表**——在所有新 DDL 都还没在真库验过的背景下，
  再叠一张只会让未验证的面变大。
- **先 claim 再推送**：推送失败只是错过一次祝贺，而不是每天重复祝贺直到用户静音。
- **连续天数同时统计闪卡复习**：`flashcard_revlog` 原本只有 `(card_id, reviewed_at)` 索引，
  补了 `(user_id, reviewed_at)`（缺索引是性能问题，与「加新表」不是一个风险等级）。
  learning 包用结构化接口 `ReviewDayCounter` 接 flashcards，不产生包依赖。
  **两者合并成一条连续记录**，而不是分开统计——周一复习、周二收集，对用户是「连续两天」。
- **界面区分「0 天」与「查不到」**：拉不到就整块不渲染。

顺带发现：`LearningDigestExecutor` **此前零测试**（P0 交付时只被 build 与路由层覆盖）。
本轮给它加了里程碑分支，因此补了 12 个用例。
