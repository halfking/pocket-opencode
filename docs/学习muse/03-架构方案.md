## 1. 统一工作实体：Work Item（工作 = 任务，按类型分类）

### 1.1 核心决策

> **不做「工作」和「任务」两张表。** 用户明确要求二者是一体的，差别只是**类型**。
> 因此物理上继续用 `tasks` 表（增量加列，零迁移风险），逻辑上升级为 **Work Item**。

新增列（全部 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，向后兼容）：

| 列 | 类型 | 语义 |
|---|---|---|
| `type` | `TEXT NOT NULL DEFAULT 'other'` | 业务分类（枚举见 §1.2） |
| `owner_id` | `TEXT` | 负责人（user id，空 = 当前用户） |
| `assignees` | `JSONB NOT NULL DEFAULT '[]'` | 协作者 user id 数组 |
| `due_at` | `BIGINT` | 截止时间（unix 秒） |
| `remind_at` | `BIGINT` | 提醒时间（unix 秒，早于或等于 due_at） |
| `parent_id` | `TEXT` | 父任务（目标 → 任务 → 子任务，Muse 式层级） |
| `origin_kind` | `TEXT` | 来源域：`note/email/rss/meeting/agent/manual/import` |
| `origin_ref` | `TEXT` | 来源实体 id（溯源，点回原文） |
| `tags` | `JSONB NOT NULL DEFAULT '[]'` | 标签 |
| `visibility` | `TEXT NOT NULL DEFAULT 'private'` | `private/shared/workspace`（协作可见性） |

### 1.2 任务类型枚举（`type` + 分组 `type_group`）

分组让 UI 可以「按工作 / 生活 / 学习」三大类折叠，同时保留细分类：

| group | type |
|---|---|
| `work` | `dev` `ops` `project` `meeting` `doc` `comms` `admin` |
| `life` | `errand` `family` `finance` `health` |
| `learning` | `study` `research` `review` |
| `other` | `other`（默认） |

- 服务端以 `map[type]group` 白名单校验，**非法值 400**，不做静默兜底。
- 旧数据 `DEFAULT 'other'`，老客户端不传也不受影响。
- **命名债同时修正**：`workstream_id` 语义被占用为实例 ID（`server.go:1198`），本方案**不再复用它做分类**，
  新分类一律走 `type`；`workstream_id` 保持原样不动（Phase 4 再做解绑，避免动到 `source='opencode'` 投影链路）。

### 1.3 分类入口（三个，都落同一张表）

```
POST /api/tasks            {title, type, dueAt, ownerId, assignees, parentId, origin:{kind,ref}}
POST /api/tasks/from-note  {noteId, type?}          → origin_kind=note
POST /api/tasks/from-email {emailId, type?}         → origin_kind=email
POST /api/tasks/from-meeting {meetingId}            → origin_kind=meeting
```

这样「会议待办只落前端 SQLite」「邮件里的待办没人管」两个断链被一次补齐（Phase 2 实现）。

## 2. 学习核心：Learning Core

### 2.1 为什么需要它

现状（`02-现状盘点.md` §2）：闪卡**只会**来自手打 front/back；笔记、邮件、RSS 里的知识**进不来**；
调度真相在前端。Muse 的 M2（长期记忆 + 主动回访）要求「读过的材料会回来找你」——
这需要一个**来源无关**的中间层。

### 2.2 学习条目 `learning_items`

一张表承接四类来源（也承接 `meeting` / `chat` / `manual`，为 Phase 2 预留）：

| 列 | 语义 |
|---|---|
| `id` `workspace_id` `user_id` | 身份与租户（`user_id` 以 JWT 为准） |
| `source_kind` | `note` / `email` / `rss` / `meeting` / `chat` / `manual` |
| `source_id` | 来源实体 id（与 `source_kind` 组成逻辑唯一键） |
| `title` `summary` | 标题与摘要（LLM 可选生成） |
| `deck_id` | 关联卡组（可空 → 未成卡） |
| `stage` | `inbox`（已收集未处理）→ `learning`（学习中）→ `review`（复习中）→ `mastered` / `archived` |
| `importance` | 1–5，影响复习优先级与回顾排序 |
| `captured_at` `updated_at` `deleted_at` | 时间戳与墓碑 |

**关键点**：`(workspace_id, user_id, source_kind, source_id)` 唯一 → 同一封邮件重复「加入学习」不会产生重复条目。

### 2.3 学习提醒 `learning_reminders`

| 列 | 语义 |
|---|---|
| `kind` | `daily_digest`（每日回顾）/ `spaced_review`（到期复习）/ `deadline`（截止）/ `streak`（连续天数） |
| `rule_kind` / `rule_value` | `daily`(HH:MM) / `interval`(分钟) / `once`(unix 秒) |
| `next_due_at` | 下次触发时间（**提醒中枢的真相**） |
| `state` | `pending` / `sent` / `acked` / `snoozed` / `done` |
| `item_id` / `card_id` | 关联对象（可空 → 汇总型提醒） |

**幂等**：同 `(workspace_id, user_id, kind, item_id)` 唯一 → 重复建当日回顾不会刷屏。
这直接解决「每次请求都插一条提醒」的经典事故。

## 3. 记忆法则：服务端成为调度真相

### 3.1 决策（见 `06-ADR.md` ADR-002）

现状是**前端 `ts-fsrs` 算 due、后端只存**（`flashcards/cards.go:17-20`）。后果：
换端 / 离线 / 换人 时，同一张卡的 due 不一致，提醒算错。

**决策**：调度计算下沉到服务端（Go 侧 `internal/learning/scheduler.go`），实现 FSRS-5 形态的
`Schedule()` 纯函数（stability / difficulty / interval / state / due 五元组）。
前端保留 `ts-fsrs` 仅用于**本地乐观预览**，服务端返回值为唯一权威。

### 3.2 算法（FSRS-5 形态，与参考实现对齐）

`internal/learning/scheduler.go` 是纯函数，公式与 FSRS-5 参考实现一致
（对照物：本仓库前端正在使用的 `ts-fsrs` 5.4.2 `next_recall_stability`）：

```
R  = (1 + FACTOR · t/S) ^ DECAY                    // 遗忘曲线，DECAY=-0.5, FACTOR=19/81
S' = S · (1 + e^w8 · (11 - D) · S^-w9 · (e^{w10(1-R)} - 1) · hard · easy)
D' = w7·D0(4) + (1-w7)·(D - w6·(r-3))             // 阻尼难度更新，夹在 [1,10]
I  = S' / FACTOR · (R_target^{1/DECAY} - 1)         // 目标留存率下的间隔（天）
```

- 评分 r ∈ {1 Again, 2 Hard, 3 Good, 4 Easy}，与既有 `flashcard_revlog.rating` 一致。
- `hard = w15`（Hard 惩罚）、`easy = w16`（Easy 上界），与参考实现同语义：
  **FSRS-5 默认权重下这两个系数都 < 1**，Easy 的收益主要通过难度下降体现
  （D 越小 → 下一轮 `11 - D` 越大），而不是单步间隔暴涨。
- 目标留存率取 `flashcard_deck_config.desired_retention`（默认 0.9）；
  权重用 FSRS-5 17 维默认向量（`flashcards/types.go:57-60` 声明的同一向量；
  该 DDL 列为可空无 DB 默认，实际权重由客户端/卡组配置提供）。
- 状态机沿用既有 0=new / 1=learning / 2=review / 3=relearning，**不新增枚举**。
- 上述行为由 `scheduler_test.go` 逐条锁定（评分×状态矩阵、单调性、难度夹取、
  留存率方向、确定性、脏输入兜底）。

### 3.3 提醒闭环（符合记忆法则的定时提醒）

```
学习步骤间重复（FSRS 间隔）
      │
      ├──► 到期卡片 ──► learning_reminders(kind=spaced_review, next_due_at=到期)
      │                        │
每日回顾 ──► learning_reminders(kind=daily_digest, rule=daily HH:MM)
                               │
                     scheduledtask (cron/interval)
                               │
                    LearningDigestExecutor
                               │
                 notifycenter.Dispatch(learning.review.due)
                    ├─ websocket（前台，零延迟）
                    ├─ inbox（通知中心留存，可回看）
                    └─ apns/fcm（Phase 4 落地，当前 Noop）
                               │
                     免打扰（notification_rules.quiet_hours）
```

- 遵循记忆法则的三个可验证点：**到期才推**（`next_due_at > now` 不推）、
  **每日固定回顾**（艾宾浩斯式分散复习）、**免打扰**（睡眠时段不打扰，次日顺延）。
- `FlashcardReviewExecutor` 保持不变，作为**卡片到期**这一路的既有实现；
  新 `LearningDigestExecutor` 负责**学习域统一摘要**（到期卡数 + inbox 待处理 + 今日到期任务）。
  两者共用 notifycenter 规则，不重复造推送通道。

## 4. 协作任务

### 4.1 数据

| 表 | 列 | 说明 |
|---|---|---|
| `work_item_participants` | `workspace_id, task_id, user_id, role, created_at` | `role ∈ owner/assignee/watcher`；`(ws,task,user)` 唯一 |
| `work_item_events` | `workspace_id, task_id, event_type, actor_user_id, payload JSONB, created_at` | 活动流（审计 + 通知来源） |

- 协作基础沿用**已存在的** workspace 成员模型（`identity/store.go:108,117`，角色 `owner|invitee`），
  不新建团队体系。
- 任务可见性由 `visibility` 控制：`private`（仅参与者）/ `shared`（参与者 + workspace 成员可读）/ `workspace`。
- **读 ≠ 写**：能读到工作项不代表能改它的参与者或负责人（`CanReadWorkItem` / `CanWriteWorkItem`，
  纯函数 + 单测）。否则 workspace 里的任何人都能把别人的任务改派走。
- **创建者即 owner**：`tasks` 表没有 `created_by` 列，所以 `POST /api/tasks` 在 `ownerId` 为空时
  直接用 JWT 身份填 `owner_id`，并把创建者写进参与者表。授权与「委派落 owner」共用这一列，
  比新增一列更省事，也避免出现「无 owner 的私有任务谁都读不了」的死角。
- `shared` 与 `private` 当前的**可读集合相同**。这是刻意保留的：现在合并，将来要支持
  「共享给一个不同于参与者名单的集合」时改的只是规则而不是 schema。

### 4.2 事件 → 通知

| event_type | 通知 kind | 收件人 |
|---|---|---|
| `assigned` | `work_item.assigned` | 被指派人（仅一人） |
| `status_changed` | `work_item.status_changed` | 除操作者外的参与者 |
| `comment` | `work_item.comment` | 除发言者外的参与者 |
| `completed` | `work_item.completed` | 参与者（**含**操作者，关闭任务的人要收到回执） |
| `reminded` | `work_item.reminder` | `owner_id` |
| `created` / `due_changed` | — | **不发通知** |

**已对账修正（P3）**：本表原先还有一行 `due_soon → work_item.due_soon → 参与者`。
但提醒中枢在 `remind_at` 到点时写入的事件类型是 `reminded`，上表末行已经覆盖了它；
两行并存会让 owner 在同一次触发里收到两条通知。因此 `due_soon` 已折叠进 `reminded`，
代码以 `backend/internal/task/notify.go` 为准（`NotificationKind` / `NotifyRecipients`，
纯函数、有单测）。`due_changed`（改截止时间）判定为噪音，不通知。

**去重与风暴控制**：`reminded` 由提醒中枢按 `remind_at` 生成，**每任务每提醒点只发一次**
（`(task_id, remind_at, kind)` 唯一），不随轮询重复。

## 5. 通知中枢扩展

复用 `notifycenter`，新增两组事件源（`source=work_item` / `source=learning`）：

| source | kind | 触发 |
|---|---|---|
| `work_item` | `assigned` `due_soon` `status_changed` `comment` `completed` `reminder` | §4.2 |
| `learning` | `review.due` `digest.daily` `item.captured` `item.mastered` | §3.3 |

每组默认落一条 `notification_rules`（`channels=[websocket,inbox]`, `priority=normal`），
免打扰时段默认 `22:30–07:30`（可在设置里改）。

## 6. 整体形态

```
┌───────────────────────── 客户端 ─────────────────────────┐
│  /work   （统一工作：按 type_group 折叠 + 协作面板）        │
│  /study  （学习中心：今日回顾 / 到期复习 / inbox / 来源跳转）│
│  /inbox  （通知中心）                                     │
└───────────────┬─────────────────────────────────────────┘
                │ REST（JWT user_id 权威）
┌───────────────▼─────────────────────────────────────────┐
│ server：/api/tasks（+type/due/owner/assignees）           │
│         /api/learning/{items,reminders,schedule}          │
│         /api/notifications（既有）                        │
├──────────────────────────────────────────────────────────┤
│ 任务域 task      学习域 learning      闪卡 flashcards      │
│  ├ work_item_*  ├ learning_items     ├ flashcard_cards   │
│  │  (新增)      ├ learning_reminders ├ flashcard_revlog  │
│  └ tasks(扩展)   └ scheduler(FSRS)    └ server 权威调度   │
├──────────────────────────────────────────────────────────┤
│ scheduledtask（cron/interval/at + Executor 注册表）        │
│ notifycenter（规则 + 免打扰 + 收件箱 + 渠道）             │
└──────────────────────────────────────────────────────────┘
```

**边界原则**：学习域**不复制**笔记/邮件/RSS 的正文，只存**引用 + 摘要 + 阶段**（`source_kind/source_id`），
内容真源仍在各自主域，避免双写与不一致。

## 7. 与既有契约的兼容策略

| 既有事实 | 处理 |
|---|---|
| 契约冻结「FSRS 调度在客户端」（`docs/flashcards-contract.md:190-193`） | P0 **不推翻**：服务端调度作为**新增能力**（`/api/learning/schedule`）与**提醒侧**（复习到期数）使用；P2 随 Phase 迁移把写入真相切到服务端，并在契约里登记变更（见 ADR-002） |
| 前端 TS 有后端不返回的 `category` / `owner` | P0 让后端**真的返回** `type` / `ownerId`（P0 起字段名统一为 camelCase），消除幻觉字段 |
| 会议待办落前端 SQLite | Phase 2 迁移到 PG `tasks`（`origin_kind='meeting'`），保留本地写入作为离线回退 |
| 4 套待办存储 | 目标态收敛为 **`tasks` 唯一真源**；`scheduled_tasks` 保留为「触发器」语义（自动化），不算待办 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 服务端 FSRS 与前端 `ts-fsrs` 结果不一致 | 复习节奏漂移 | P0 只用于提醒与预览；Phase 3 切换写入真相时，同步把前端算法替换为服务端返回 |
| `ALTER` 加列在超大表上锁 | 迁移慢 | 全部 `ADD COLUMN IF NOT EXISTS`（PG 11+ 仅改元数据），且幂等 |
| 分类枚举过窄导致用户想自定义 | 反复改表 | 非法值 400 拒绝；`type` 允许 Phase 3 起扩展，不做自由文本兜底 |
| 提醒风暴 | 用户关闭通知 | `(reminder 唯一键)` + `due_count<=0 不推`（沿用 flashcard executor 既有行为）+ 免打扰 |
| 协作越权 | 数据泄露 | 所有新表带 `workspace_id`，读写一律 `Scoped` 形式；`visibility='private'` 时仅参与者可读（Phase 3 实现） |
