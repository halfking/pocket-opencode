## 为什么它们在仓里（而不是 /tmp）

**§919–§922 当时的变异脚本没有落盘** —— 提交信息与主文档只留了「全中」的汇总。
⇒ 下一轮想复核「当时绿 = 现在绿」时，只能**按判据描述重建**一批等价变异。
⇒ 重建出来的东西能证明「**判据现在还有牙**」，**证明不了「当时那批脚本真的跑过」**
（历史读数没有第二份副本）。

⇒ 所以这些脚本**落盘**在这里：下一轮要复核时，**跑它**，而不是再重建一遍。
⇒ **§936 起这条是硬规矩**：新写的变异批次必须落盘。

## 怎么跑

```bash
cd <仓库根>
python3 scripts/mutations/run_all.py      # 二十批依次跑
python3 scripts/mutations/s919.py         # 只跑某一批
```

退出码：

| 码 | 读法 |
|---|---|
| 0 | 全部批次都跑了，且每条变异都符合预期 |
| 1 | 至少一批**跑了**，但有变异没被抓住（或量具自证失败） |
| 2 | 至少一批**拒绝跑**（缺依赖，例如 §936/§937/§938/§939/§940/§941/§942 需要真 PG） |

⇒ 「拒绝跑」**不算**通过 ⇒ 退出码非 0 ⇒ 不会被误读成「全绿」。

## ⚠ 这些脚本会**就地改工作树**

这是「变异」的定义。三条自我保护（都在 `_harness.py` 里）：

1. **前置**：目标文件必须与 `HEAD` 一致（`git diff --quiet HEAD -- <file>`）
   ⇒ 你有未提交的改动时它**直接拒绝跑** ⇒ 不会把你的改动和变异混在一起。
2. **还原自证**：每条用例跑完立刻还原，并**逐字节**比对原文件 ⇒ 还原失败立刻退出。
3. **残留核对**：整批跑完比对 `git status --porcelain` 与前置快照**完全一致**
   ⇒ 任何一个字节的残留都会被抓到。

⇒ 跑完之后，工作树必须还是你交给我时的样子。

## 读法：三种用例

- **「必须红」** ⇒ 证明判据**有牙**（改坏了它会响）。
- **「负控 · 必须绿」** ⇒ 证明判据**不过度敏感**（语义等价的改动不该误报）。
- **「量具自检」** ⇒ 量的是**判据自己的盲区**（例如前端树缺失时 Go 那道门会被
  `t.Skipf` 跳过 ⇒ 变成空气门）⇒ **它不是「有牙」的证据**，是**局限**的证据。

⚠ `s936.py` 的 **M1b** 就是这种「量具自检」：在 D2 变异下，**8 行**数据集上的
跨 store 一致性判据**仍然绿** ⇒ ⇒ 它证明「一致性判据覆盖了 D2」这句话是**错的**
⇒ D2 是靠 **501 行**那条用例与 **SQL 形状守卫**抓住的。

⚠ `s937.py` 的 **N3** 也是这种「量具自检」：把尾读口径换成「整份 `[]rune` 展开再切」
⇒ **返回值逐字相同** ⇒ 所有判据**仍然绿** ⇒ ⇒ 它证明「本节判据量的是
**跨存储边界搬走了多少字节**，**量不到 store 内部的分配量**」⇒
⇒ 「尾读 = 零分配」这句话**没有判据** ⇒ 写下来，免得后人误以为有。

⚠ `s940.py` 的 **M2** 同样要这么读：它拆掉「按列类型决定转不转」之后
⇒ **精度判据全部仍然绿**（重复转换在**值上**是幂等的：epoch 一字不变）
⇒ ⇒ **只有**「第 2 次建 store 不得重写 notes 表」那条判据红
⇒ ⇒ ⇒ 「重复转换无害」与「重复转换很贵」是**两件事**，必须分开记。

⚠ `s940.py` 的 **N4** 也是「量具自检」：摘掉 advisory lock ⇒ 所有判据**仍然绿**
⇒ ⇒ ⇒ 「这把锁有用」这句话**没有并发判据支撑**（单实例判据看不见它）
⇒ ⇒ ⇒ 它防的是「多个实例同时启动 ⇒ 各自重写一遍全表」⇒ ⇒ **⛔ 未实测多实例并发**。

## 口径纪律（每一条都是踩出来的）

- **落盘 → 在变异状态下跑判据 → 还原 → 核对**。
  还原早于跑判据 ⇒ 测的是**没变异的文件** ⇒ 变异「全绿」⇒ **假通过**。
- **落盘自证**用「文件确实变了 **且** 新串在场」，
  **不能**用「旧串不在场」（旧串不在场可能只是锚点写错）。
- **锚点必须按实现的真实写法来**；出现次数必须**恰好**等于预期（不符 ⇒ 立刻中止，
  不猜）。
- **还原也要自证**（文件回到原样）。
- **「变异转红了」≠「变异验到了你想验的那条」** ⇒ 必须把**期望消息**也钉住
  （`must_contain`）⇒ 否则「红」可能是**另一条**断言红的。

## 已知局限

- §919–§922 这四批是**重建**的等价批次，**不是**当年那批脚本（见上）。
- 脚本里的锚点是**逐字**的 ⇒ 实现改了写法（哪怕语义没变）就要改脚本。
  这是刻意的：锚点一旦漂移，变异就变成**空操作**，而判据仍会显示「有反应」。
- `s919.py` 的 A16 是**量具自检**，它证明的是「这道门在某个前提下会变成空气门」。
- `s937.py` 同样需要真 PG ⇒ 在没有 PG 的机器上它**拒绝跑**（退出码 3）⇒
  ⇒ 「§937 的判据在 CI 上跑过」这件事**不成立**（CI 的 backend job 没有 PG）⇒
  ⇒ 真正在 CI 上守着的只有**不依赖 PG 的那几条**（尾读口径 / SQL 形状 / 内存版行为 /
  handler 侧读量与写量）。
- `s936.py` 需要真 PG ⇒ 在没有 PG 的机器上它**拒绝跑**（退出码 3）⇒
  ⇒ 「§936 的判据在 CI 上跑过」这件事**不成立**（CI 的 backend job 没有 PG）⇒
  ⇒ 真正在 CI 上守着的只有**不依赖 PG 的那几条**（口径 / SQL 形状 / 夹取 / handler）。
- `s938.py` 同样需要真 PG ⇒ 在没有 PG 的机器上它**拒绝跑**（退出码 3）⇒
  ⇒ 「§938 的判据在 CI 上跑过」这件事**不成立**（CI 的 backend job 没有 PG）⇒
  ⇒ 真正在 CI 上守着的只有**不依赖 PG 的那几条**（去重键 / 批内去重 / 提取口径），
  而**租户落点 / 归属 / 溯源 / 跨次幂等 / 两条路径互见**这五件事**只在有 PG 的机器上被守住**。
- `s939.py` 同样需要真 PG ⇒ 在没有 PG 的机器上它**拒绝跑**（退出码 3）⇒
  ⇒ 「§939 的判据在 CI 上跑过」这件事**不成立**⇒
